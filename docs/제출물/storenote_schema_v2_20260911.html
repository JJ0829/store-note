매장수첩 · 스키마 2차 버전

매장 경계를 스키마가 지키게 하기

v1에 대한 심사 지적 다섯 건은 표면상 따로지만 뿌리가 하나다 — v1은 "같은 매장 것끼리만 이어진다"와 "그때 그 값이 무엇이었나"를 애플리케이션 코드에 맡기고 있었다. 코드는 잊어버리고, DB는 안 잊는다. v2는 그 판단을 전부 DB 제약으로 내린다.

대상 Supabase · PostgreSQL 15+ 지적 5건 전부 반영 + 2건 추가 전체 DDL(표를 만드는 명령문) db/schema_v2.sql 2026-09-11

  8. 08적용 순서

먼저 밝혀 둘 것 세 가지

1. v1 의 DDL 원문(1차 설계 명령문)을 확보하지 못한 채 썼다. 저장소·세션 기록·아티팩트·Downloads·Documents를 전부 검색했고 어디에도 없었다 (일반 채팅에서 만들어진 것으로 보인다). 그래서 v2는 피드백이 지목한 테이블 이름과 제품 도메인을 근거로 재구성한 것이다. v1과 대조가 필요하다 — 특히 컬럼 이름과 PK 타입(uuid로 가정).

2. SQL(데이터베이스에 시키는 말) 문법 검증을 하지 못했다. 이 작업 환경에 PostgreSQL·Docker·Supabase CLI가 전부 없다. 한 번도 실행해 보지 않은 명령문이다. Supabase 브랜치에서 먼저 실행해 봐야 한다.

3. 이것은 현재 배포 준비 중인 앱의 스키마가 아니다. 지금 도는 매장수첩은 RDB가 없고 data/seed.json + localStorage로 돈다. 이 문서는 그다음 단계다.

말 풀이 — 이 문서에 나오는 낱말

아래 열두 개만 알면 이 문서를 끝까지 읽을 수 있다. 순서대로 읽을 필요는 없고, 본문에서 막힐 때 돌아와 보면 된다.

낱말뜻왜 나오나
데이터베이스
DB		 자료를 담아두는 창고. 지금은 엑셀 여러 장이 서로 연결된 것이라고 보면 된다 매장 자료가 전부 여기 들어간다
테이블
표		 창고 안의 표 한 장. 거래처 표, 품목 표, 판매 표처럼 종류마다 하나씩 이 문서는 그 표들을 어떻게 짤지 정한다
SQL
에스큐엘		 데이터베이스에 시키는 말. "이 표를 만들어라", "이 줄을 찾아라" 회색 칸 안의 글자가 전부 이것이다
DDL
디디엘		 SQL 중에서 표의 모양을 만드는 쪽. create table로 시작하는 것들 이 문서가 내놓는 결과물이 DDL이다
스키마
schema		 표 전체의 설계도. 어떤 표가 있고 어떤 칸이 있고 서로 어떻게 이어지는지 v1 → v2 는 이 설계도의 판 번호다
외래키
FK · foreign key		 "이 칸은 저쪽 표의 저 줄을 가리킨다"고 DB에 알려주는 것. 가리키는 줄이 없으면 DB가 아예 안 받는다 지적 1번이 통째로 이 얘기다
복합 외래키 외래키인데 칸 두 개를 묶어서 본다. "품목 번호"만이 아니라 "품목 번호 + 매장 번호"가 같이 맞아야 통과 이게 매장 경계를 지키는 핵심 장치다
제약
constraint		 DB가 스스로 지키는 규칙. 어기면 저장 자체가 안 된다. 프로그램이 깜빡해도 DB는 안 깜빡한다 v2의 거의 모든 수정이 제약을 거는 일이다
RLS
줄 단위 접근 통제		 로그인한 사람이 자기 매장 줄만 보이게 DB가 직접 걸러주는 기능. 프로그램을 안 거치고 DB에 바로 물어봐도 남의 것은 안 나온다 지적 4번. 다섯 건 중 제일 위험한 것
뷰
view		 저장하지 않고 물어볼 때마다 계산해 주는 가짜 표. 원본이 바뀌면 자동으로 따라 바뀐다 "이 발주가 이행됐나"를 뷰로 계산한다 (지적 3번)
트리거
trigger		 무슨 일이 생기면 자동으로 도는 작은 프로그램 심사가 대안으로 언급했는데, 제약보다 약하다 (1번 끝)
마이그레이션 이미 자료가 들어 있는 창고의 설계도를 바꾸는 작업. 순서를 틀리면 중간에 막힌다 맨 아래 "적용 순서"가 그것이다

v2에서 달라진 것

1~5번은 받은 지적이고, A·B는 지적에 없었지만 같은 뿌리라서 같이 고친 것이다. 둘 다 이 제품에서 실제로 원가를 조용히 틀리게 만드는 지점이다.

#지적무엇이 뚫려 있나무엇으로 막나

순서는 의미가 있다. 1번이 나머지 전부의 전제다 — 2·3·5번이 새로 만드는 표들도 전부 같은 복합 키 규칙을 따라야 하고, 4번 RLS는 1번이 없으면 "내 매장 행만 보인다"까지는 되지만 "내 매장 행이 남의 매장을 가리키는 것"은 못 막는다.

A

재료를 이름으로 잇지 않는다 — items가 마스터가 된다

이건 심사가 지적하지 않았지만 1번과 같은 뿌리다. "관계를 코드가 판단한다"는 점이 똑같고, 결과는 더 조용하다.

현재 앱의 원가는 findItemByName(items, ing.name) 한 줄로 이어진다 — 레시피의 재료 이름과 거래처 품목 이름을 문자열로 맞춘다. 앞뒤 공백만 무시하므로 "우유"와 "흰우유"는 남남이다. 그러면 그 재료가 원가에서 빠지고, 원가율이 실제보다 낮게 나온다. 점주는 그 숫자로 판매가를 정한다.

v2에서는 품목이 하나의 실체이고 레시피는 그 id를 가리킨다. 이름으로 맞추는 코드가 아예 사라진다. 더해서 매장 안에서 품목 이름 중복을 막는다 — "우유"가 두 개 있으면 마스터가 마스터가 아니다.

items — 재료 원본 명단

create table items (
  id       uuid primary key default gen_random_uuid(),
  store_id uuid not null references stores(id),
  supplier_id uuid,
  name     text not null,

  -- purchased: 사 오는 것 / made: 매장에서 만드는 부재료 (르방·청·시럽·크림폼)
  kind text not null default 'purchased'
       check (kind in ('purchased','made')),

  base_unit   text not null references units(code),
  base_family text not null,
  ...
  constraint uq_items_id_store unique (id, store_id),
  constraint uq_items_name     unique (store_id, name),   -- ★ 이름 중복 금지
  constraint fk_items_supplier_same_store
    foreign key (supplier_id, store_id) references suppliers (id, store_id)
);

kind = 'made'가 필요한 이유

카페·베이커리에서는 바에서 만드는 부재료가 다시 재료가 된다. 르방은 식빵의 재료이고, 수제청은 에이드의 재료다. 품목을 "사는 것"으로만 두면 이걸 표현할 수 없고, 원가가 그 지점에서 끊긴다.

B

g과 ml을 DB가 막는다

밀가루는 0.55, 우유는 1.03이다. 밀도를 모르면 무게와 부피는 못 바꾼다. 바꾸면 원가가 틀리는데 사람이 못 알아챈다 — 숫자가 그럴듯하게 나오기 때문이다.

현재 앱은 이걸 코드에서 막고 있다. v2에서는 계열을 데이터로 두고 외래키로 강제한다. 레시피 줄의 단위 계열과 품목 기준단위의 계열이 다르면 삽입 자체가 거부된다.

units — 무게·부피 계열을 표로 둔다

create table units (
  code    text primary key,          -- g · kg · ml · L · 개
  family  text not null check (family in ('weight','volume','count')),
  to_base numeric(20,8) not null,
  constraint uq_units_code_family unique (code, family)   -- ★ 복합 FK 대상
);

-- 품목은 (기준단위, 계열) 짝으로 참조하고, 그 짝을 다시 노출한다
alter table items
  add constraint fk_items_unit_family
      foreign key (base_unit, base_family) references units (code, family),
  add constraint uq_items_id_store_family
      unique (id, store_id, base_family);

-- ★ 레시피 줄은 (품목, 매장, 계열) 세 칸으로 참조한다
--   → 같은 매장 + 같은 계열이 아니면 못 들어간다
alter table menu_recipe_lines
  add constraint fk_mrl_item_same_store_and_family
      foreign key (item_id, store_id, unit_family)
      references items (id, store_id, base_family);

한 제약이 두 가지를 동시에 막는다

위 외래키 하나가 1번(다른 매장 재료)과 B(계열 불일치)를 같이 막는다. store_id와 family가 같은 키 안에 들어 있기 때문이다. 제약을 따로 두 개 걸 필요가 없다.

받은 지적 다섯 건

1

매장 경계 — 단일 외래키로는 못 막는다

받은 지적 items, 레시피, 판매·폐기·입고·제조 기록, 실사 및 계획 데이터에 복합 외래키나 트리거를 적용해 동일 매장 데이터만 연결되도록 보장해 주세요.

items.supplier_id → suppliers.id(품목의 거래처 칸이 거래처 표를 가리킨다)는 "존재하는 거래처인가"만 본다. 그 거래처가 어느 매장 것인지는 보지 않는다. 그래서 A매장 품목에 B매장 거래처를 붙여도 DB가 통과시킨다. 실수로도 되고, API에 숫자 하나만 바꿔 보내도 된다.

해법은 참조에 매장을 함께 싣는 것이다. 자식과 부모가 같은 store_id를 갖는지까지 외래키가 검사하게 만든다. 지적에 나온 그 한 줄이 정확히 이것이다.

원리 — 두 단계

아래 회색 칸은 DB에 시키는 말이다. 뜻만 읽으셔도 된다 — 실행은 개발 쪽에서 한다.

패턴

-- ① 거래처 표에 '번호+매장' 짝이 하나뿐임을 표시한다 (아래 ②가 이걸 필요로 한다)
alter table suppliers
  add constraint uq_suppliers_id_store unique (id, store_id);

-- ② 품목이 '거래처번호 + 자기 매장번호' 두 칸으로 가리키게 한다
alter table items
  add constraint fk_items_supplier_same_store
  foreign key (supplier_id, store_id) references suppliers (id, store_id);

이제 items.store_id와 suppliers.store_id가 다르면 삽입 자체가 거부된다. 애플리케이션이 무엇을 보내든 상관없다.

NULL 은 그대로 허용된다

복합 외래키는 기본값 MATCH SIMPLE이라 구성 컬럼 중 하나라도 NULL이면 검사를 건너뛴다. store_id는 NOT NULL이므로, supplier_id가 NULL인 품목(거래처 미지정)은 지금처럼 그냥 들어간다. 의도한 동작이고, 따로 손댈 것이 없다.

적용 전에 — 이미 어긋난 데이터부터 찾는다

제약을 거는 순간 기존 위반 행이 있으면 ALTER 자체가 실패한다. 먼저 세어 본다.

검사 · 읽기만 한다

select count(*) as 위반건수
from items i
join suppliers s on s.id = i.supplier_id
where s.store_id <> i.store_id;

고쳐야 할 표를 DB가 스스로 찾아내게 하기

테이블이 열 개가 넘고 컬럼 이름이 제각각이다. 손으로 적으면 빠뜨린다. 아래 명령을 돌리면 "고쳐야 할 곳" 목록과 고치는 명령문이 한꺼번에 나온다. 실제 표 이름을 몰라도 되므로, 이름이 제 추정과 달라도 그대로 쓸 수 있다.

생성기 · 실행하면 SQL 문자열이 나온다

-- store_id 를 가진 테이블끼리 이어진 단일 컬럼 FK 를 전부 찾아
-- 복합 FK 로 바꾸는 ALTER 문을 만들어 준다
with fk as (
  select
    c.conname,
    src.relname  as child,
    tgt.relname  as parent,
    (select attname from pg_attribute
      where attrelid = c.conrelid and attnum = c.conkey[1]) as child_col
  from pg_constraint c
  join pg_class src on src.oid = c.conrelid
  join pg_class tgt on tgt.oid = c.confrelid
  join pg_namespace n on n.oid = src.relnamespace
  where c.contype = 'f'
    and n.nspname = 'public'
    and array_length(c.conkey, 1) = 1
),
scoped as (
  select f.* from fk f
  where exists (select 1 from information_schema.columns
                where table_name = f.child  and column_name = 'store_id')
    and exists (select 1 from information_schema.columns
                where table_name = f.parent and column_name = 'store_id')
)
select
  format('alter table %I add constraint uq_%s_id_store unique (id, store_id);',
         parent, parent) as step1_parent,
  format('alter table %I add constraint fk_%s_%s_same_store '
         'foreign key (%I, store_id) references %I (id, store_id) not valid;',
         child, child, child_col, child_col, parent) as step2_child,
  format('alter table %I validate constraint fk_%s_%s_same_store;',
         child, child, child_col) as step3_validate
from scoped
order by child;

not valid(앞으로 들어올 것만 검사)로 먼저 붙이고 나중에 validate(과거 것까지 검사)하는 이유는 잠금 시간을 줄이기 위해서다(검사하는 동안 매장에서 저장이 안 된다). 바로 검증하면 전체 테이블을 훑는 동안 쓰기가 막힌다. not valid는 앞으로 들어오는 행만 검사하고, validate는 약한 락으로 과거 행을 훑는다.

자식에 store_id가 없는 테이블

make_recipes·menu_recipes·sales_lines 같은 연결·명세 테이블은 store_id가 없을 수 있다. 먼저 넣어야 한다. 정규화 관점에서는 중복이지만, 그 중복이 제약을 살 수 있게 해주는 대가다.

추가 · 백필 · 고정

alter table make_recipes add column store_id uuid;

update make_recipes mr
   set store_id = i.store_id
  from items i
 where i.id = mr.item_id;

alter table make_recipes alter column store_id set not null;

alter table make_recipes
  add constraint uq_make_recipes_id_store unique (id, store_id);

트리거가 아니라 복합 외래키여야 하는 이유

지적은 "복합 외래키나 트리거"라고 했지만 둘은 같은 강도가 아니다.

트리거는 읽고 나서 판단한다. 그 사이에 부모 행의 store_id가 바뀌거나 지워지면 통과해 버린다 — 동시 트랜잭션에서 실제로 일어난다. 외래키는 참조 무결성을 잠금 수준에서 지키므로 그런 틈이 없다. 그리고 선언이라서 스키마만 봐도 규칙이 보인다 — 트리거는 찾아 읽어야 한다.

트리거는 자식에 store_id를 도저히 넣을 수 없을 때만 쓴다. 지금 구조에서는 넣을 수 있다.

2

원가는 "지금 값"이 아니라 "그날 값"으로 계산돼야 한다

받은 지적 item_prices 추가로 매입가 이력은 해결됐지만 per_unit, yield_count, 면세 여부 등도 과거 원가 계산에 영향을 줍니다. 이 값들도 적용일 기준으로 이력 관리하고, 레시피에서 재료를 제거하는 경우를 표현할 수 있도록 effective_to, is_active 또는 레시피 버전 구조를 추가해 주세요.

맞는 지적이고, 실무에서 이게 제일 아프다. 매입가만 이력으로 두면 "3월 원가율"을 다시 뽑았을 때 3월 가격 × 지금 규격이 섞인 숫자가 나온다. 우유 1000ml 팩이 900ml로 바뀌었거나, 1배합 수율이 6개에서 8개로 바뀌었거나, 면세였던 품목이 과세로 돌아섰으면 그 숫자는 어느 시점의 것도 아니다. 더 나쁜 건 틀렸다는 표시가 아무 데도 안 뜬다는 것이다.

2-1. 품목의 "규격"을 통째로 기간별로 남긴다

가격만 따로 두지 말고 원가 계산에 들어가는 값 전부를 한 버전 행에 담는다. 그래야 "그날 이 품목은 이랬다"가 한 줄로 재현된다.

신설 · item_prices 를 대체한다

create extension if not exists btree_gist;

create table item_versions (
  id           uuid primary key default gen_random_uuid(),
  store_id     uuid not null,
  item_id      uuid not null,

  -- 원가에 들어가는 값 전부
  unit_cost    numeric(12,2) not null,   -- 매입가 (1 팩 값)
  per_unit     numeric(12,4) not null,   -- 팩당 수량 (1000ml)
  unit         text          not null,   -- ml · g · 개
  yield_count  numeric(12,4),            -- 1배합 산출 개수
  is_tax_free  boolean       not null default false,
  tax_rate     numeric(5,4)  not null default 0.10,

  -- 적용 구간. 끝이 null 이면 "현재 유효"
  validity     daterange not null default daterange(current_date, null, '[)'),
  note         text,
  created_at   timestamptz not null default now(),

  constraint uq_item_versions_id_store unique (id, store_id),
  constraint fk_item_versions_item_same_store
    foreign key (item_id, store_id) references items (id, store_id),

  -- ★ 같은 품목의 구간이 겹치지 않게 DB 가 막는다
  constraint ex_item_versions_no_overlap

effective_from + effective_to 두 칸보다 daterange가 나은 이유

두 칸으로 두면 구간이 겹치거나 비는 것을 DB가 못 막는다. 같은 품목에 "3/1~" 과 "2/15~" 가 둘 다 살아 있어도 통과하고, 그러면 어느 값을 쓸지 조회문이 마음대로 고른다. daterange + EXCLUDE 제약은 그 상태를 아예 만들 수 없게 한다.

조회 · 그날의 값을 꺼낸다

create or replace function item_as_of(p_item uuid, p_on date)
returns item_versions
language sql stable as $fn$
  select * from item_versions
   where item_id = p_item and validity @> p_on
   limit 1
$fn$;

2-2. 레시피는 판 번호로 — "쓰는 중/안 쓰는 중" 표시만으로는 부족하다

지적이 준 선택지 셋 중 버전 구조를 고른다. 이유가 있다.

  • is_active만 두면 재료를 뺀 사실은 남지만 언제 뺐는지가 안 남는다. 3월 원가를 다시 뽑을 때 그 재료를 넣어야 할지 알 수 없다.
  • effective_to를 줄마다 두면 표현은 되는데, "3월 15일자 레시피 전체"를 한 번에 집는 게 어렵다. 줄마다 구간이 달라서 매번 재조립해야 한다.
  • 버전으로 두면 판매·제조 기록이 버전 id 하나만 들고 있으면 된다. 그 시점 레시피가 통째로 고정된다 — 재료를 뺀 것도 자연히 표현된다 (다음 버전에 그 줄이 없다).

신설

create table recipe_versions (

2-3. 그래서 과거 원가가 재현된다

검증 · 어느 날짜를 넣어도 그날 숫자가 나온다

select
  rv.recipe_id,
  sum(l.amount * iv.unit_cost / nullif(iv.per_unit, 0)) as 재료비
from recipe_versions rv
join recipe_version_lines l on l.recipe_version_id = rv.id
join lateral (
  select * from item_versions v
   where v.item_id = l.ingredient_item_id
     and v.validity @> :as_of          -- ★ 지금 값이 아니라 그날 값
   limit 1
) iv on true
where rv.store_id = :store
  and :as_of >= rv.valid_from
  and (rv.valid_to is null or :as_of < rv.valid_to)
group by rv.recipe_id;

매장수첩이 이미 지키고 있는 규칙을 여기서도 지킨다

단가를 못 구한 재료를 0원으로 세지 않는다. 위 조회문의 join lateral은 해당 날짜 버전이 없으면 그 줄을 떨어뜨린다 — 즉 재료비가 조용히 작아진다. 실제 구현에서는 left join lateral로 바꾸고 iv.id is null인 줄을 "못 구함"으로 따로 세어 화면에 같이 내보내야 한다. 0원으로 세면 원가율이 실제보다 낮게 나오고, 점주가 그 숫자로 판매가를 정한다.

3

계획과 실행을 잇는다 — 날짜 한 칸으로는 부족하다

받은 지적 발주와 제조 계획의 확정일만 있고 실제 입고·제조 예정일 및 실제 기록과의 연결이 아직 없습니다. 계획일과 실행 예정일을 구분하고, received_lines.order_plan_id와 baked_lines.bake_plan_id를 추가해 어떤 계획이 실제로 이행됐는지 추적할 수 있게 해주세요.

날짜가 셋인데 칸이 하나였다. 이건 카페·베이커리에서 특히 중요하다 — 리드타임이 이 업종의 핵심이고, 오늘 걸어두는 일의 절반이 내일을 위한 것이기 때문이다. "금요일에 주말치까지 몰아서 주문한다"가 표현되려면 주문한 날과 도착할 날이 따로 있어야 한다.

날짜뜻어디 있나
planned_on계획을 세운 날 (지금 있는 "확정일")계획 헤더
expected_on들어올/만들어질 예정일 — 거래처 마감·배송요일·리드타임으로 계산계획 라인
occurred_on실제로 들어온/만든 날실행행

계획 라인에 예정일을 둔다

alter table order_plans add column expected_on date;
alter table bake_plans  add column expected_on date;

comment on column order_plans.expected_on is
  '입고 예정일. 거래처 cutoff 를 넘겨 주문하면 하루 밀리고, 배송 안 하는 요일은 건너뛴다';

실행행이 계획 라인을 가리킨다

지적대로 order_plan_id·bake_plan_id를 붙이되, 1번의 복합 키 규칙을 그대로 따른다. 안 그러면 이번엔 남의 매장 계획에 우리 입고가 붙는다.

  • NULL 을 허용한 채로 둔다. 계획 없이 급하게 받은 입고가 실제로 있다 — 쿠팡으로 메운 것 같은. 그걸 못 넣게 하면 사람이 장부를 안 쓴다.
  • 1:N 이다. 계획 한 줄이 여러 번에 나눠 들어올 수 있다. 그래서 계획 쪽에 received_line_id를 두지 않고 실행 쪽에 계획 id를 둔다.

이행 상태는 저장하지 않고 계산한다

status 칸을 두면 실행이 들어올 때마다 사람이 갱신해야 하고, 반드시 어긋난다. 뷰로 만들면 원장과 절대 안 어긋난다.

뷰 · 이행률

create or replace view v_order_fulfillment as
select
  p.store_id,
  p.id            as order_plan_id,
  p.item_id,
  p.planned_on,
  p.expected_on,
  p.qty                                   as 계획수량,
  coalesce(sum(r.qty), 0)                 as 입고수량,
  p.qty - coalesce(sum(r.qty), 0)         as 미입고,
  min(r.occurred_on)                      as 첫입고일,
  case
    when coalesce(sum(r.qty), 0) = 0
     and p.expected_on < current_date          then '미이행'
    when coalesce(sum(r.qty), 0) = 0            then '대기'
    when coalesce(sum(r.qty), 0) < p.qty        then '부분입고'
    when coalesce(sum(r.qty), 0) = p.qty        then '완료'
    else '초과입고'
  end as 상태
from order_plans p
left join received_lines r
       on r.order_plan_id = p.id
      and r.store_id = p.store_id
group by p.store_id, p.id, p.item_id, p.planned_on, p.expected_on, p.qty;

'미이행'과 '초과입고'가 따로 잡히는 게 이 뷰의 값어치다. 전자는 내일 아침에 물건이 없다는 뜻이고, 후자는 대개 같은 걸 두 번 시킨 것이다. 둘 다 지금은 아무 데도 안 뜬다.

4

RLS — 요청이 보낸 매장 번호를 믿지 않는다

받은 지적 Supabase Auth를 사용하지만 각 테이블의 RLS 정책이 보이지 않습니다. 로그인 사용자의 users.store_id를 기준으로 자기 매장의 데이터만 조회·등록·수정할 수 있도록 전체 테이블에 RLS를 적용하고, 서버에서도 요청으로 받은 매장 ID를 그대로 신뢰하지 않도록 해주세요.

이게 다섯 건 중 가장 위험한 항목이다. 1~3번은 잘못된 숫자가 나오는 문제지만, 이건 남의 매장 원가·매출·거래처 단가가 그대로 보이는 문제다. 카페에서 레시피와 매입 단가는 영업비밀이다.

4-1. "이 사람은 어느 매장인가"를 판정하는 함수

users 테이블에도 RLS를 켜면, users를 조회하는 정책이 다시 users의 정책을 부르면서 자기가 자기를 계속 불러서 멈춰버린다(무한 재귀). security definer 함수로 한 번 끊는다.

신설 · 이 함수가 유일한 매장 판정 지점이다

create or replace function public.current_store_id()
returns uuid
language sql
stable
security definer                      -- ★ users 의 RLS 를 우회해 재귀를 끊는다
set search_path = public, pg_temp     -- ★ search_path 를 고정하지 않으면 탈취 경로가 된다
as $fn$
  select store_id from public.users where id = auth.uid()
$fn$;

revoke execute on function public.current_store_id() from public;
grant  execute on function public.current_store_id() to authenticated;

더 빠른 대안 — JWT 클레임

위 함수는 행마다가 아니라 구문마다 한 번 평가되지만(stable), 그래도 조회가 하나 더 붙는다. 매장이 바뀌는 일이 드물다면 가입 시 app_metadata.store_id에 넣고 (auth.jwt() -> 'app_metadata' ->> 'store_id')::uuid로 읽는 게 더 빠르다. 단 매장을 옮기면 토큰을 새로 발급해야 반영된다 — 그 트레이드오프를 알고 고를 것.

4-2. 모든 표에 한 번에 건다

적용 · store_id 를 가진 public 테이블 전부

do $do$
declare t text;
begin
  for t in
    select table_name
      from information_schema.columns
     where table_schema = 'public' and column_name = 'store_id'
  loop
    execute format('alter table public.%I enable row level security', t);
    execute format('alter table public.%I force  row level security', t);

    execute format(
      'create policy store_isolation on public.%I '
      'for all to authenticated '
      'using (store_id = public.current_store_id()) '
      'with check (store_id = public.current_store_id())', t);
  end loop;
end
$do$;

가장 흔한 실수 — with check를 빼먹는 것

using만 쓰면 읽기와 삭제만 막히고 새로 넣는 것(INSERT)은 그대로 통과한다. using은 이미 있는 행을 걸러내는 조건이고, with check는 새로 쓰는 행을 검사하는 조건이다. 둘 다 없으면 남의 매장 이름으로 데이터를 심을 수 있다.

force row level security도 같이 켠다 — 이게 없으면 테이블 소유자에게는 RLS가 적용되지 않는다.

4-3. 서버 쪽 — 진짜 위험은 여기다

서버는 앱과 DB 사이에서 일하는 프로그램이다. RLS를 아무리 잘 걸어도 서버가 잘못 만들어져 있으면 무의미해진다.

  • service_role 키(모든 문을 여는 관리자 열쇠)는 RLS를 통째로 무시한다. 이 키로 도는 코드 경로가 하나라도 요청 본문의 store_id를 그대로 쓰면, 위에 건 정책이 전부 무의미해진다. 서버 코드에서 store_id는 요청이 아니라 세션에서만 나와야 한다.
  • 요청 본문의 store_id는 받지도 말 것. 받아서 검사하는 것보다 아예 안 받고 서버가 채우는 편이 안전하다. 검사는 빠뜨릴 수 있고, 안 받으면 빠뜨릴 것이 없다.
  • RLS를 켜고 정책을 안 만들면 아무도 못 읽는다. 기본이 거부라서 안전한 방향으로 실패한다 — 다만 앱이 통째로 멈추므로 브랜치에서 먼저 켜 본다.

확인 · 정책이 안 걸린 테이블 찾기

select c.relname as 테이블,
       c.relrowsecurity  as rls켜짐,
       c.relforcerowsecurity as force,
       count(p.polname)  as 정책수
from pg_class c
join pg_namespace n on n.oid = c.relnamespace
left join pg_policy p on p.polrelid = c.oid
where n.nspname = 'public' and c.relkind = 'r'
group by c.relname, c.relrowsecurity, c.relforcerowsecurity
having c.relrowsecurity = false or count(p.polname) = 0
order by c.relname;

이 명령을 돌렸을 때 아무것도 안 나와야 4번이 끝난 것이다(한 줄이라도 나오면 그 표가 안 잠긴 것). 심사에 그대로 캡처해서 낼 수 있다.

5

추천의 근거를 그때 그대로 얼려 둔다

받은 지적 현재는 추천 수량만 저장하고 당시 사용한 판매량·재고·가격·알고리즘 버전은 남기지 않습니다. 계산 방식이나 원장 데이터가 바뀌면 과거 추천 이유를 다시 확인할 수 없으므로, 추천 실행 정보와 입력값 스냅샷 또는 최소한 계산 버전과 추천 근거를 저장해 주세요.

"그때 다시 계산해 보면 되지 않나"가 안 되는 이유는 원장이 움직이기 때문이다. 판매가 정정되고, 2번에서 만든 단가 이력이 소급 입력되고, 알고리즘이 바뀐다. 그리고 "왜 그때 12개를 시켰나"를 묻는 순간은 거의 항상 사고가 난 다음이다 — 재고가 터졌거나, 폐기가 났거나. 그때 재현이 안 되면 원인을 영영 못 찾는다.

새 표 · 추천을 한 번 돌릴 때마다 한 줄

create table recommendation_runs (
  id           uuid primary key default gen_random_uuid(),
  store_id     uuid not null,
  ran_at       timestamptz not null default now(),
  ran_by       uuid,                       -- auth.uid()

  algo_version text not null,              -- 'order-v3.2' — 코드에서 상수로 박아 보낸다
  params       jsonb not null default '{}',-- 안전재고일수 · 리드타임 · 반올림 단위
  horizon_from date not null,              -- 무엇을 근거로 본 기간
  horizon_to   date not null,

  constraint uq_reco_runs_id_store unique (id, store_id)
);

create table recommendation_inputs (
  run_id     uuid not null,
  store_id   uuid not null,
  item_id    uuid not null,

  -- ★ 그때 실제로 쓴 값. 지금 원장을 다시 읽으면 안 되는 이유가 이 칸들이다
  sold_qty        numeric(12,4) not null,   -- 기간 판매량
  waste_qty       numeric(12,4) not null default 0,
  on_hand         numeric(12,4) not null,   -- 계산 시점 재고
  unit_cost       numeric(12,2),            -- 그때 단가
  item_version_id uuid,                     -- ★ 2번의 규격 버전을 그대로 가리킨다
  lead_days       int,
  safety_days     numeric(6,2),

  recommended_qty numeric(12,4) not null,
  reason          text,                     -- 사람이 읽는 한 줄

  primary key (run_id, item_id),
  constraint fk_reco_inputs_run_same_store
    foreign key (run_id, store_id)  references recommendation_runs (id, store_id),
  constraint fk_reco_inputs_item_same_store
    foreign key (item_id, store_id) references items (id, store_id)
);

-- 계획이 어느 실행에서 나왔는지
alter table order_plans add column run_id uuid;
alter table order_plans
  add constraint fk_order_plans_run_same_store
  foreign key (run_id, store_id) references recommendation_runs (id, store_id);

alter table bake_plans add column run_id uuid;
alter table bake_plans
  add constraint fk_bake_plans_run_same_store
  foreign key (run_id, store_id) references recommendation_runs (id, store_id);

reason 한 칸이 나머지 전부보다 실전에서 쓸모 있다

점주가 보는 것은 숫자 열 개가 아니라 한 문장이다. '최근 14일 하루 평균 3.2개 · 현재고 2개 · 리드타임 2일 · 안전재고 1일 → 12개' 처럼 계산 결과가 아니라 계산 과정을 문장으로 남긴다. 입력 스냅샷은 개발자가 보는 것이고, 이 한 줄은 점주가 추천을 믿을지 말지 정하는 근거다.

  • algo_version은 코드에서 상수로 보낸다. DB가 추측하면 안 된다. 계산식을 고칠 때 이 문자열을 같이 올리는 것이 규칙이 된다.
  • params는 jsonb(자유롭게 담는 칸)로 둔다. 파라미터는 계속 늘어난다 — 늘 때마다 컬럼을 추가하면 과거 행에 NULL이 쌓인다.
  • 입력 스냅샷은 지워도 되는 데이터다. 보존 기간(예: 1년)을 정해 두고 오래된 recommendation_inputs는 지운다. runs와 reason만 남겨도 대부분의 질문에 답할 수 있다.

적용 순서

순서를 바꾸면 중간에 막힌다. 특히 RLS는 마지막이다 — 켜는 순간 앱이 조회를 못 하게 되므로, 앱 코드 수정과 같이 나가야 한다.

단계할 일되돌릴 수 있나
0Supabase 브랜치(연습용 복사본)를 만들어 거기서 전부 먼저 돌린다—
1위반 데이터 조사 (읽기만)읽기라 위험 없음
2자식 테이블에 store_id 추가 · 백필 · NOT NULL컬럼 drop
3가리켜지는 표에 UNIQUE (id, store_id)(번호+매장 짝은 하나뿐)constraint drop
4복합 외래키를 걸고(앞으로 것만) → 과거 것까지 검사constraint drop
5item_versions 신설 · item_prices 이관옛 표를 남겨둔 채 진행
6레시피 버전 신설 · 현재 레시피를 v1 로 적재표 drop
7계획↔실행 FK · 이행 뷰drop
8추천 실행·스냅샷 표drop
9RLS — 앱 코드 수정과 같이 배포disable row level security

5번에서 item_prices를 바로 지우지 않는다. 새 표로 옮기고, 두 표의 값이 같은지 한동안 비교해 보고, 그다음에 지운다. 이력 데이터는 한 번 잃으면 되살릴 방법이 없다.

v1과 대조해야 하는 것 — 아직 확인 못 한 항목

v1 DDL 원문을 못 찾은 채로 썼기 때문에 아래는 추정이다. 원문이 확보되면 30분 안에 맞출 수 있다.

  • 테이블·컬럼 실제 이름 — menus·daily_sales·qty·occurred_on은 지어 쓴 이름입니다
  • PK 타입 — uuid로 썼습니다. bigint면 전부 바꿔야 합니다
  • 각 자식 테이블에 store_id가 이미 있는지 — 없으면 추가·백필이 먼저입니다
  • item_prices의 현재 컬럼 구성 — item_versions로 이관하는 문을 정확히 쓰려면 필요합니다
  • order_plans·bake_plans가 헤더+라인 두 표인지 — 한 표로 보고 썼습니다
  • 추천 계산식의 실제 입력 항목 — recommendation_inputs의 칸을 그것에 맞춰야 합니다
  • SQL 문법 검증 — 이 환경에 PostgreSQL·Docker·Supabase CLI가 없어 한 번도 실행해 보지 못했습니다
