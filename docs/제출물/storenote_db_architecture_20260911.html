같은 매장인지를 프로그램이 아니라 DB 가 판단한다

1차 설계는 「같은 매장 것끼리만 이어진다」를 프로그램이 지키게 두었다. 프로그램은 사람이 고치고, 사람은 한 자리를 빼먹는다. 2차 설계는 그 판단을 데이터베이스가 직접 한다 — 연결선이 (id, store_id) 두 칸으로 이어지므로, 옆 매장 것을 가리키는 줄은 저장 자체가 거절된다.

★ 오늘의 정본은 어디인가

가장 먼저 답할 것

이 문서는 표 37개짜리 PostgreSQL 설계를 길게 다룬다. 그래서 오해를 살 수 있어 먼저 못 박는다 — 그 데이터베이스는 아직 없다. 스키마는 실제 PostgreSQL 에 올려 검증까지 끝낸 목표 설계이고, 오늘 도는 앱에는 서버 데이터베이스가 없다. 런타임 의존성은 지금도 next · react · react-dom 셋뿐이다.

한 줄로

오늘 운영 데이터의 정본은 「그 태블릿의 브라우저 저장소」다. 서버는 레시피·프렙·포지션을 읽어서 보여줄 뿐이고 아무것도 쓰지 않는다. 그래서 매장 데이터가 태블릿마다 따로 쌓인다 — 이것이 지금 구조의 가장 큰 한계이고, 옮기는 첫 번째 이유다.

마지막 줄을 「파일에 저장한다」로 읽으면 안 된다

/api/log 는 지금 로컬 파일에 한 줄씩 덧붙인다. 그런데 배포하면 그 파일이 남지 않는다 — 서버 파일 시스템은 요청 사이에 보존되지 않기 때문이다. 즉 배포본에서 지표는 0건이 된다. 이것은 「파일에 저장하는 설계」가 아니라 「아직 저장할 곳이 없다」는 뜻이다. 운영 데이터를 서버 파일 시스템에 두는 구조는 목표 설계에 없다.

데이터가 서버 데이터베이스로 올라가는 순간 이 논리는 무효가 된다. 그때는 로그인과 줄 단위 통제가 기능보다 먼저다. WBS 의 10.2 · 10.3 이 배포 뒤에 묶여 있는 이유가 이것이고, 레시피에 실매장 수치를 넣는 일도 같은 줄에 묶인다.

지금 도는 앱은 데이터베이스가 없다. 읽는 것은 파일 하나(data/seed.json), 쓰는 것은 그 태블릿의 브라우저 저장소다. 이 문서는 그 다음의 설계이고, 고칠 코드가 한 층이 되도록 처음부터 나눠 뒀다.

★ 이 설계의 한 줄

심사 지적 1번

1차 설계의 연결선은 번호 하나였다. 그러면 데이터베이스는 「그 번호가 있는가」만 보고 「어느 매장 것인가」는 안 본다. 매장이 여러 곳이 되는 순간, 옆 매장의 단가가 우리 원가에 섞여도 DB 는 아무 말을 안 한다.

차이는 「검사를 어디서 하나」다. 왼쪽은 앱이 매번 매장을 확인해야 하고, 확인을 빼먹은 한 곳이 조용히 틀린다. 오른쪽은 빼먹을 자리가 없다.

2차 · 3차 피드백에서 더 고친 것

「같은 매장은 보지만 같은 대상은 안 보던」 관계가 있었다 — 매장만 맞추고 품목·메뉴가 어긋나도 되는 이음이다. 세 칸 외래키 20개로 바꿨다.

3차에서는 설명에만 있던 규칙 세 가지를 데이터베이스가 알게 했다. 문서에 적혀 있고 코드가 모르는 규칙은 규칙이 아니다.

DB 로 내리지 않은 것 — 그리고 그 이유

영업일 경계(새벽 4시) · 자정을 넘는 마감조 · 리드타임 계산 · 인건비 추정은 앱(src/lib/)에 남겼다. 매장마다 다르고 바뀌면 과거 기록의 해석까지 바뀌는 규칙이라서, DB 제약으로 굳히면 과거 줄이 갑자기 위법이 된다.

대신 그 계산들은 전부 순수 함수라 테스트로 덮여 있다. 「DB 가 막는 것」과 「테스트가 막는 것」의 경계가 이 선이다.

★ g 과 ml 을 DB 가 막는다

자체 발견

밀가루는 1g 이 0.55ml 이고 우유는 1g 이 1.03ml 다. 밀도를 모르면 g 과 ml 은 바꿀 수 없다. 그런데 바꿔버리면 원가가 조용히 틀리고 사람은 못 알아챈다 — 숫자가 그럴듯하게 나오기 때문이다.

층무엇을 하나없으면
units.family
weight · volume · count		 단위마다 계열을 못 박는다g 과 ml 이 같은 칸에 들어온다
참조에 계열을 끼워 넣음 레시피 줄이 품목을 가리킬 때 계열까지 함께 가리킨다 DB 가 «있는 단위인가»만 보고 «바꿀 수 있는 단위인가»는 안 본다
제약 3곳 추가
2차 피드백		 규격 · 산출량 · 제조 수량의 계열 일치 같은 규칙이 세 자리에서만 빠져 있었다 — 전수로 훑어서 찾았다
src/lib/units.ts 계열이 다르면 계산하지 않고 화면에 «단위가 안 맞습니다» 0 으로 세거나 그냥 더한다

같은 규칙을 두 층에 넣은 것은 중복이 아니다. DB 는 저장을 거절하고, 앱은 사람에게 말을 한다. 둘 중 하나만 있으면 데이터는 맞는데 화면이 침묵하거나, 화면은 친절한데 데이터가 틀린다.

검증 — 검사 6종

그림이 아니라 실행

ERD 는 그림이라 틀려도 그려진다. 그래서 설계를 실제 PostgreSQL 18 에 올려서 막히는지 본다. 데이터베이스를 따로 설치하지 않는다 — PGlite(파일 없이 도는 PostgreSQL)라 npm 만 있으면 누구나 재현한다.

검사무엇을 보나이 검사가 잡는 실수
counts:db스키마에서 숫자를 직접 센다 (표 · 외래키 · 정책 …) 손으로 센 숫자. 손으로 세는 한 반드시 낡는다
verify:db스키마를 실제로 올리고, 막아야 하는 INSERT 가 정말 막히는지 제약을 적어만 두고 동작은 확인 안 한 것
audit:db심사 지적 한 줄당 제약 1:1 지적을 «반영했다»고 적고 어디에 반영했는지는 없는 것
sweep:db규칙마다 적용돼야 할 자리를 전수로 ★ 「그 자리만 고치는」 실수. 지적받은 한 곳만 고치고 같은 모양의 나머지를 놔둔 것
dbml:db그림(DBML) ↔ SQL 대조 SQL 에만 넣고 그림에 안 넣은 것 — 심사위원이 보는 것은 그림이다
docs:db문서에 적힌 숫자가 지금 값과 같은가 · 모순되는 문장이 남았는가 ★ 3차 심사의 첫 지적. 스키마가 아니라 문서가 틀렸다

뒤의 두 개가 3차 심사에서 생겼다

3차 지적의 첫 줄은 스키마가 아니라 문서를 가리켰다 — 상단과 하단이 서로 다른 숫자를 말하고 있었다. 고쳐도 또 낡는다. 숫자는 커밋마다 바뀌는데 문서는 안 바뀌기 때문이다. 그래서 기계가 센다(counts:db) 그리고 기계가 대조한다(docs:db). 이 문서의 머리글 숫자도 그 대조 대상이다.

sweep:db 가 여섯 중 제일 중요하다. 1차·2차에서 실제로 반복된 실수가 「지적받은 자리만 고치기」였다. 관계 몇 곳 중 지적된 곳만 바꾸면 검사는 통과하는데 설계는 여전히 틀려 있다.

재현하려면 한 줄이 더 필요하다 — 숨기지 않는다

이 검사들은 @electric-sql/pglite 를 쓰는데 package.json 에 아직 올라가 있지 않다. 새로 내려받은 저장소에서 npm run check 를 돌리면 DB 검사 앞에서 멈춘다. 설계의 결함이 아니라 선언의 누락이고 한 줄로 고쳐진다 — npm i -D @electric-sql/pglite.
