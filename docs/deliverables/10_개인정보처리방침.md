# 0장. 지금 이 서비스의 실제 상태

**방침을 정확하게 쓰려면 이걸 먼저 확정해야 한다.** 흔한 처리방침 템플릿을 그대로 붙이면
없는 항목을 쓰게 되고, **과다 기재도 그 자체로 위반이다.**

## 0-1. 구조

| 사실 | 근거 |
|---|---|
| **서버 데이터베이스가 없다.** 매장 콘텐츠는 저장소 안의 정적 파일이다 | `data/seed.json` · `src/lib/repo.ts` |
| **회원가입·로그인이 없다.** 사용자 계정 개념 자체가 없다 | 인증 라우트 0건, `src/app/` 전수 확인 |
| **동의 화면·동의 체크박스가 없다** | 코드 0건. → "이용자 동의를 받아 수집한다"고 쓰면 거짓이다 |
| **이용자 데이터는 브라우저 저장소에만 있다.** 서버로 보내지 않는다 | `localStorage` **13개 키(계열)** + `sessionStorage` **2키**. 3-2장 표. ⚠️ 2026-09-04에 5 → 13으로 늘었다 (0-2-A장) |
| 서버로 가는 유일한 경로는 **`/api/log`** (익명·가명 이용 기록) | `src/app/api/log/route.ts` |
| `/api/media`는 `public/media/` **파일명 목록만** 돌려준다. 개인정보 없음 | `src/app/api/media/route.ts:12-21` |
| 서버는 **IP·User-Agent·Referer·쿠키를 기록하지 않는다** | `src/app/api/log/route.ts:18` — `request`는 `.json()`에만 쓰인다. 미들웨어 없음 |
| 메일은 **`mailto:`로 이용자의 메일 앱을 열 뿐이다.** 서비스가 대신 보내지 않는다 | `src/components/RosterView.tsx:105-107` |
| **사진·영상 업로드 기능이 없다** | `src/` 전체에 `<input type="file">` 0건. `ShootBoard.tsx`는 파일명 복사만 한다 |

→ **따라서 현행 구조에서 서비스가 "개인정보처리자"로서 수집·보관하는 범위는 매우 좁다.**
이 방침에서 가장 정직하고 강력한 문장은 **"우리는 거의 아무것도 수집하지 않는다"**이며, 실제로 코드가 그렇다.

## 0-2. 그러나 — 직원 개인정보를 다루는 기능이 있다

**이 점을 흐리면 안 된다.**

근무표 기능(`src/lib/roster.ts`)은 직원의 **섹션·이름·이메일·전화번호**와 **날짜별 근무 배정**을 다룬다.

```ts
// src/lib/roster.ts:11-19
export type Staff = {
  id: string;
  section: string;   // 제빵 / 바 / 홀 / 주방
  name: string;
  email: string;
  phone: string;
};
```

- 저장 위치: `localStorage` 키 `sop:roster` (`src/lib/roster.ts:29`)
- **서버로 전송되지 않는다.** `loadRoster()`를 호출하는 파일은 `RosterView.tsx` 하나뿐이고,
  `RosterView.tsx`에는 `/api/log` 호출이 없다.
- **입력하는 사람과 정보주체가 다르다.** 직원이 자기 정보를 넣는 화면이 없고 **운영자(점주)가 대신 입력**한다
  (`src/components/RosterView.tsx:60-78`).
- 이름만 필수다. `if (!name.trim()) return;` (`RosterView.tsx:61`). 섹션·이메일·전화번호는 비어도 저장된다.
  `<input>`에 `required` 속성이 없다.

**법적 귀속 정리 (중요) — ❓ 이 판단은 아직 확정된 것이 아니다:**

| 데이터 | 개인정보처리자 (잠정) | 이 판단의 근거 | 방침에서의 위치 |
|---|---|---|---|
| 직원 이름·이메일·전화번호·근무배정 | **매장(점주) 본인** ❓ | **코드 사실만 확인됨** — 서비스가 이 데이터를 전송받지 않는다 (`RosterView.tsx`에 `/api/log` 호출 0건). **법적 근거는 아직 확인하지 못했다** | 서비스의 "수집 항목"이 **아니다** → 1-2장 |
| `/api/log` 이용 기록 | 서비스 운영자 | 서비스 서버가 실제로 받아 파일에 기록한다 (`api/log/route.ts:27`) | 서비스의 수집 항목 → 1-1장 |

> ## ❓ 이 귀속 판단에는 조문·해석례 근거가 없다 — **전문가 확인 1순위 쟁점**

>   스스로 또는 다른 사람을 통하여 개인정보를 처리하는 자) 정의에 점주가 해당하는가
>   — 출처: https://casenote.kr/법령/개인정보_보호법/제2조 (2차 출처. 원문 대조 필요)
> - 도구 제공자가 법 **제26조**의 **수탁자**에 해당하지 않는 기준은 무엇인가
>   (서버 보관이 없어도 "처리"에 해당할 여지가 있는지)
>   — 출처: https://casenote.kr/법령/개인정보_보호법/제26조 (2차 출처)

> 그 경우 법 제30조 제1항 **제1호(처리 목적)**, **제3호의2(파기절차·방법)**,

## 0-2-A. ⚠️ 2026-09-04 — 운영 기능 7종이 추가되면서 수집 프로필이 크게 바뀌었다

**이 절이 이번 개정의 핵심이다.** 0-1·0-2를 쓸 때의 전제가 그대로가 아니다.

추가된 화면: **원가 · 근태 · 출퇴근 · 매출 · 발주 · 거래처 · 근로계약서**
(`src/app/{cost,attendance,sales,order,vendors,contracts}` · `src/lib/{cost,attendance,sales,orders,vendors,contracts,settings,ownerGate,units,store}.ts`)

### 무엇이 새로 다뤄지는가

| 새 데이터 | 개인정보인가 | 왜 중요한가 |
|---|---|---|
| **출퇴근 기록** (직원별 날짜·출근시각·퇴근시각·휴게시간) | **그렇다.** 특정 개인의 근로시간이다 | 근로기준법상 **임금 산정의 기초 자료**다. 0-2의 "이름·연락처"보다 민감도가 높다 |
| **근로계약 조건** (계약기간·**시급**·소정근로시간·근무요일·서면교부 여부·4대보험 가입 여부) | **그렇다** | **시급은 급여다.** 동료끼리도 보면 안 되는 정보다 |
| **근태 판정** (지각 분수·결근·연장근로·법정휴게 미달) | **그렇다** | 인사상 불리한 처분의 근거가 될 수 있다 |
| **인건비 추정액** (직원별 주간 금액) | **그렇다** | 위 둘의 계산 결과다 |
| 매출·원가·판매가·거래처 단가·발주 내역 | **아니다** | 개인정보가 아니라 **영업비밀**이다. → 부록 A #21 |

### 그래서 달라지는 것

1. **0-2의 쟁점이 훨씬 무거워졌다.** "직원 개인정보를 점주가 처리한다"는 잠정 판단(#17)은
   이름·연락처 수준일 때보다 **판단 오류의 대가가 커졌다.** 근로시간·시급까지 포함되면
   그 파일은 사실상 **임금대장에 준하는 개인정보파일**이다. → 부록 A #18
2. **주민등록번호 칸을 만들지 않았다.** 근로계약서 관리 기능을 넣으면서 가장 먼저 결정한 것이다.
   근거는 `src/lib/contracts.ts:1-24` 주석에 코드와 함께 남겼다. → 1-3장
3. **보관 의무가 처음 생겼다.** 지금까지 이 서비스에는 "지워도 되는 데이터"만 있었다.
   출퇴근·계약 정보는 **다른 법령이 3년 보존을 요구한다.** → 3-5장 (신설)
4. **화면 잠금이 처음 생겼다** (`src/lib/ownerGate.ts`). 다만 **접근 통제가 아니라 가리개다.**
   과대 기재하지 않도록 7-1장에 그대로 적었다. → 부록 A #20

### 서버 전송은 여전히 없다

새 화면 7개 어디에도 `/api/log` 호출이 없다. 확인:

```

grep -rn "fetch(" src/lib/{cost,attendance,sales,orders,vendors,contracts,settings}.ts   → 0건
```

→ **1-1장(서비스가 서버로 수집하는 항목)은 바뀌지 않는다.** 늘어난 것은 전부 1-2장(기기 저장)이다.
이 점은 이번 개정에서 유일하게 안심할 수 있는 부분이다.

## 0-3. 어느 버전을 말하는 방침인가 — 두 버전의 수집 프로필이 정반대다

| | Next.js 앱 (`src/`) | 단일 파일 버전 (`presentation/프렙노트.html`) |
|---|---|---|
| 배포 상태 | **로컬 `npm run dev`만. Vercel 미배포** | **Claude Artifact로 시연용 1회 게시 = 현재 외부 접근 가능한 유일한 버전** |
| 서버 전송 | `/api/log` 있음 | **없다.** `fetch`/`sendBeacon` 0건 (grep 확인) |
| 가명 식별자 `sop:sid` | 있음 | **없다.** `sessionId` 0건 |
| 외부 요청 | **0건.** 폰트는 기기 스택만 (`src/app/globals.css:3-6`) | **Google Fonts 로드** → 열람자 IP가 미국으로 (`프렙노트.html:11-13`) |
| 저장 키 이름 | `sop:roster` 등 | **다르다** — `roster`, `roster:mode`, `recipes:mine`, `prep:…`, `list:…` |

즉 **서버 수집이 있는 버전은 외부에 없고, 외부에 있는 버전은 서버 수집이 없는 대신 IP가 국외로 나간다.**
방침 본문에 **적용 범위(어느 버전·어느 배포 환경)를 반드시 명시**해야 한다. → 부록 D 빈칸 [B-1]

> ⚠️ 추가 사실: 정식 배포(Vercel)에서는 `/api/log`의 파일 쓰기가 막혀 **조용히 실패한다**
> (`src/app/api/log/route.ts:28-30` 빈 catch). "수집한다"고 써 놓고 실제로는 아무것도 쌓이지 않는 상태가 될 수 있다.

# 1장. 수집하는 개인정보 항목

**아래 표는 코드에서 확인한 것과 정확히 일치한다. 여기에 없는 항목은 이 방침에 쓰면 안 된다.**

## 1-1. 서비스가 서버로 수집·보관하는 항목

수집 경로는 `/api/log` 하나뿐이다 (`src/app/api/log/route.ts`).

| 항목 | 수집 시점 | 저장 위치 | 필수·선택 | 보관 기간 | 파기 시점 |
|---|---|---|---|---|---|
| **기기 식별값** `sessionId` (난수) | 체크리스트·프렙·레시피 화면을 열거나 조작할 때 | 서버 `data/events.jsonl` | 필수. **현재 거부 수단 없음 ⚠️** (아래 참조) | **[ ] 미정 ⚠️** | **[ ] 파기 코드 없음 ⚠️** |

| **수집 시각** `at` (ISO 8601) | 서버가 기록할 때 자동 부여 | 서버 `data/events.jsonl` | 필수 | **[ ] 미정 ⚠️** | **[ ] 파기 코드 없음 ⚠️** |

전송 지점 11곳 전부 확인: `ChecklistView.tsx:77,267` · `PrepView.tsx:158,168,188` ·
`RecipeDetail.tsx:54,90` · `TrainingMode.tsx:101,117,132,219`.
이벤트 이름 10종 (`view`, `survey`, `prep_view`, `prep_check`, `prep_scale`, `recipe_view`,
`recipe_scale`, `training_start`, `critical_confirm`, `training_complete`) —
`data/events.jsonl` 58줄의 실제 필드와 교차 확인했고 위 표 외의 필드는 0건이었다.

**`sessionId`에 대해 정직하게 적어야 하는 것:**

- 생성식: `Math.random().toString(36).slice(2) + Date.now().toString(36)`
  (`ChecklistView.tsx:20-31`, `PrepView.tsx:26-38`, `RecipeDetail.tsx:17-29`)
- `localStorage` 키 `sop:sid`에 저장되어 **영구 재사용된다. 만료·삭제 경로가 코드에 없다.**
- 이름·이메일과 연결하는 코드는 **없다** (grep 확인: `/api/log` payload 11곳에 `name`/`email`/`phone` 0건).
- **그러나 "완전 익명"이라고 단정하지 말 것.** 체크리스트 링크가 개인 휴대폰으로 공유되면
  `sop:sid`는 사실상 **1인 1:1로 고정된 영구 가명 식별자**가 된다.
  → 방침 문구는 **"익명"이 아니라 "가명 처리된 이용 기록"**으로 쓰는 것이 안전하다.
- **교육 모드(태블릿, `/t/…`) 4개 이벤트는 `sessionId`를 보내지 않는다** (`TrainingMode.tsx:30-39`).
  11개 전송 지점 중 7곳에만 붙는다. 화면별로 구분해 쓸 근거가 된다.

> ## ⚠️ 수집을 **거부할 수단이 코드에 없다** — 법 제30조 제1항 제7호를 아직 못 쓴다
>
> 법 제30조 제1항 제7호는 "인터넷 접속정보파일 등 개인정보를 자동으로 수집하는 장치의
> **설치·운영 및 그 거부**에 관한 사항"을 요구한다
> (출처: https://casenote.kr/법령/개인정보_보호법/제30조 — 2차 출처).
>
> **초안은 "브라우저 삭제로 거부할 수 있다"고 적었는데, 이건 거부가 아니라 재수집이다.**
> `getSessionId()`는 `sop:sid`가 없으면 **그 자리에서 새 난수를 만들어 다시 저장한다**
> (`ChecklistView.tsx:20-31` · `PrepView.tsx:26-38` · `RecipeDetail.tsx:17-29`).
> 사이트 데이터를 지워도 **다음 화면 로드에서 새 식별값이 발급되고 수집이 계속된다.**
>
> 그리고 전송에 조건이 없다. `ChecklistView.tsx:77`의 `log("view", …)`는
> `useEffect` 마운트 시 **아무 조건 없이** 나간다.
> `src/` 전체에서 동의·거부·opt-out·doNotTrack 관련 코드는 **0건**이다 (grep 확인).
>
> → **거부 수단을 만들기 전에는 제7호 문구(거부 방법)를 방침에 쓸 수 없다.**
> 쓰면 없는 기능을 있다고 적는 것이 된다. → 부록 A #7

> ⚠️ **코드가 이 표를 보장하지 않는다.** `src/app/api/log/route.ts:23`은 받은 JSON을
> `{ ...body, at }`으로 그대로 저장한다. 스키마 검증·화이트리스트가 없어 **누구든 임의 JSON을 POST할 수 있다.**
> 방침에 항목을 열거하려면 **서버측 화이트리스트를 넣는 것이 안전하다.** → 부록 A #9

## 1-3. 수집하지 않는 항목 (템플릿 복사 방지용)

아래는 **코드에 존재하지 않는다.** 방침에 쓰면 거짓이자 과다 기재다.

주민등록번호 · 생년월일 · 나이 · 성별 · 주소 · 계정 id·비밀번호 ·
결제·금융정보 · 위치정보 · 쿠키 · 광고식별자 · IP주소 · User-Agent ·
접속 로그(웹서버 로그) · **사진·영상 업로드** · 직원의 자기 입력 데이터 ·
**은행 계좌번호** · **4대보험 취득 신고 정보**.

> ## ★ 주민등록번호 — 근로계약서 기능이 생겼는데도 칸을 만들지 않았다
>
> 2026-09-04에 **근로계약서 관리 화면을 추가했다.** 종이 근로계약서에는 통상 주민등록번호와
> 주소가 들어가므로, 이 기능을 만들면서 가장 먼저 결정해야 했던 것이 이 항목이었다.
>
> **결론: 입력 칸을 아예 만들지 않았다.** 근거는 법 **제24조의2**다 —
> 주민등록번호는 법령에 구체적 근거가 있을 때만 처리할 수 있고,
> 그 근거가 있더라도 **암호화하여 저장**해야 한다(같은 조 제2항).
> 지금 구조는 `localStorage`에 `JSON.stringify`로 평문 저장이므로 **그 요건을 맞출 수 없다.**
> 칸을 만들어 두면 점주가 채우고, 그 순간 위반이 된다.
>
> 코드와 화면 양쪽에 이유를 남겨 놨다 — 나중에 누군가 "편의상" 추가하는 것을 막기 위해서다:
> - `src/lib/contracts.ts:1-24` 파일 머리 주석
> - `src/components/ContractView.tsx` 화면 하단 고정 안내문
> - 단일 파일: `presentation/app.html` `renderContracts()` 말미
>
> **대신 이 화면은 계약서 원본을 보관하지 않는다.** 추적하는 것은
> "누구와 · 언제부터 · 시급 얼마 · 서면 교부했는가 · 언제까지 보관해야 하는가"뿐이다.
> 원본은 앱 밖(종이 또는 잠긴 폴더)에 둔다.
>

# 2장. 수집·이용 목적

## 2-1. 서비스가 수집하는 항목 (1-1)

| 항목 | 목적 |
|---|---|
| `sessionId` (가명 기기 식별값) | 같은 기기의 이용 흐름을 이어 보기 위함. **한 사람이 여러 번 연 것과 여러 사람이 한 번씩 연 것을 구분하지 못하면 지표 자체가 의미가 없다** |
| 화면 종류·항목 id·배수 | 어떤 포지션·레시피·프렙 항목이 실제로 쓰이는지 파악 → 콘텐츠 개선 |
| `durationSec`, `confirmedCount`, `totalTasks`, `runId` | 교육 1회에 실제로 얼마나 걸리는지 측정 |
| `askedSenior` (설문) | **검증 대상 가설** — "체크리스트·영상만으로 선배에게 묻는 횟수가 줄어드는가" |
| `recoverable` | 되돌릴 수 없는 프렙 항목의 누락률 파악 (리드타임 사고 예방) |
| `at` (시각) | 위 지표를 기간별로 보기 위함 |

수집 근거는 **서비스 개선·통계 목적의 이용 기록 분석**이다.
❓ 이 목적이 개인정보 보호법 제15조 제1항 중 어느 호(동의 / 정당한 이익 등)에 해당하는지는 전문가 검토가 필요하다.
**계정도 동의 화면도 없는 구조에서 "동의를 받았다"고 쓸 수는 없다.**

> ## ⚠️ 목적을 적는 것으로는 적법근거가 생기지 않는다 — 시행 전 조치 대상이다
>
> **목적(제30조 제1항 제1호)과 처리의 적법근거(제15조 제1항 각 호)는 다른 것이다.**
> 방침에 목적을 써도 근거가 서는 것이 아니다.
> 지금은 동의 화면이 **0건**이고(0-1장), 거부 수단도 **0건**이다(1-1장).
> 이 상태로 근거가 정해지지 않은 채 1장·2장을 공개하면
> **"목적은 적혀 있는데 근거가 없는 방침"**이 된다.
>
> 근거를 세우지 못하면 선택지는 **둘뿐이다:**
> 1. 화면에 **수집 고지 + 거부 수단**을 붙인다 (부록 A #7과 함께)
> 2. 근거가 확정될 때까지 **`/api/log` 호출을 끈다**
>
> → 부록 A **#6** · 부록 C-3 **#9** · 부록 D **[B-20]** (같은 쟁점을 세 곳에서 가리킨다)

## 3-1. ⚠️ 화면 문구부터 틀렸다 — "날짜가 바뀌면 초기화됩니다"는 사실이 아니다

체크리스트와 프렙 화면은 이렇게 안내한다:

> "체크 상태는 이 휴대폰에만 저장되며 날짜가 바뀌면 초기화됩니다."
> — `src/components/ChecklistView.tsx:296`, 유사 문구 `:281`, `src/components/PrepView.tsx:480`

**코드는 그렇게 동작하지 않는다.** 저장 키에 날짜가 들어 있을 뿐이다:

```
sop:{shareSlug}:{YYYY-MM-DD}    // ChecklistView.tsx:62
prep:{slug}:{YYYY-MM-DD}        // PrepView.tsx:133
```

날짜가 바뀌면 **새 키를 읽는 것**이고, **어제 키는 삭제되지 않는다.**
즉 **덮어쓰기도 삭제도 아니고, 매일 키가 하나씩 무기한 누적된다.**

- `PrepView.tsx`에는 `removeItem` 호출이 **0건**이다 → **프렙 체크 기록은 화면에서 지울 방법이 아예 없다.**
- `ChecklistView.tsx:97-104`의 "체크 전부 지우기"는 **오늘 날짜 키 하나만** 지운다.
- 실제로 삭제되는 유일한 항목은 교육 모드의 `sop:run:{slug}`다
  (`sessionStorage`. `removeItem` `TrainingMode.tsx:83`, 교육 완료 시 `save(null)` `:139`).

**→ 방침에 "날짜 기준으로 초기화된다"고 쓰면 안 된다. 화면 문구도 함께 고쳐야 한다.** → 부록 A #3

## 3-5. ★ 신설 — 근로기준법의 보존 **의무**와 개인정보보호법의 파기 **의무**가 부딪친다

**이번 개정에서 새로 생긴 문제이고, 이 방침에서 가장 조심해서 써야 하는 부분이다.**

지금까지 이 서비스의 데이터는 전부 "지워도 되는 것"이었다. 출퇴근 기록과 근로계약 조건은 다르다.

### 두 법이 서로 반대를 요구한다

| | 요구 | 근거 |
|---|---|---|
| 근로기준법 | 근로계약서·임금대장 등을 **3년간 보존해야 한다** | **제42조** (계약 서류 보존) · **제48조** (임금대장) ❓ 원문 대조 필요 |
| 개인정보보호법 | 보유기간이 지나거나 목적을 달성하면 **지체 없이 파기해야 한다** | **제21조 제1항** |

직원이 퇴사한 다음 날 "내 근로시간 기록을 지워 달라"고 요구하면, 그대로 지우면 근로기준법 위반이고
안 지우면 개인정보보호법 위반처럼 보인다.

### 해소 방향 (❓ 전문가 확인 필요 — 부록 A #19)

법 제21조 제1항에는 **단서**가 있다 — *"다른 법령에 따라 보존하여야 하는 경우에는 그러하지 아니하다."*
그리고 같은 조 **제3항**은 그 경우 **해당 개인정보를 다른 개인정보와 분리하여 저장·관리**하도록 한다.

> ❓ 조문 원문은 국가법령정보센터에서 최종 확인해야 한다. 이 문서가 인용한 것은 2차 출처다.

따라서 잠정적인 답은 **"지우지 않는다. 대신 분리 보관하고, 3년이 지나면 파기한다"**이다.

### 그런데 코드가 그걸 못 한다

| 필요한 것 | 현재 |
|---|---|
| 보존 대상과 그 외를 **분리 저장** (제21조 제3항) | ✗ `sop:punch`·`sop:contracts`가 `sop:roster`·`sop:sales`와 **같은 저장소에 나란히 있다** |
| 보존 기간 **경과 후 자동 파기** | ✗ 파기 코드 0건. 무기한 누적 |
| **퇴사일** 기록 (3년 기산점) | ✗ 필드가 없다. `Contract.endDate`는 계약 종료일이지 퇴사일이 아니다 |
| 보존 만기 **표시** | △ 계약서 화면에만 있다 (`keepUntil()` — 종료일 + 3년). 출퇴근 기록에는 없다 |

`src/lib/contracts.ts`의 `keepUntil()`이 만기일을 계산해 화면에 띄우기는 한다.
**그러나 그건 "사장님이 원본 종이를 언제까지 갖고 있어야 하는지" 안내일 뿐이고,
앱 안의 데이터를 그때 지워 주지는 않는다.** 이 차이를 방침에 정확히 써야 한다.

### 방침에 쓸 문구 (초안)

> 출퇴근 기록과 근로계약 조건은 **다른 법령(근로기준법)이 보존을 요구하는 정보**입니다.
> 이 정보는 이용자의 기기에만 저장되며 서비스 서버로 전송되지 않습니다.
> **보존 기간의 관리와 기간 경과 후의 파기는 매장(사업주)의 책임입니다.**
> 서비스는 계약 종료일로부터 3년이 되는 날을 화면에 안내하는 기능만 제공하며,
> **기간이 지난 데이터를 자동으로 지우지는 않습니다.**
> 기기의 데이터를 전부 지우려면 브라우저의 "사이트 데이터 삭제"를 사용하십시오.

**🚫 쓰면 안 되는 문구:** "보유기간 경과 시 지체 없이 파기합니다" —
파기 코드가 0건이므로 거짓이다. 3-3장(서버 기록)과 같은 함정이다.

## 4-2. ⚠️ 가장 심각한 문제 — 메일 본문에 전 직원의 이메일·전화번호가 평문으로 들어간다

**이것이 이 서비스에서 개인정보가 실제로 외부로 나가는 유일한 경로다.**
서비스가 보내는 것이 아니라 **이용자가 직접 보내지만, 그 본문을 만드는 것은 우리 코드다.**

### 무슨 일이 일어나는가

`src/lib/roster.ts:141-148` — `buildEmailBody()`가 `data.staff` **전체를 필터 없이** 돌며
메일 본문의 `[ 직원 명단 ]` 표에 이메일·전화번호를 그대로 넣는다:

```ts
// src/lib/roster.ts:141-148
for (const s of data.staff) {
  out.push(
    pad(s.section || "-", 8) +
      pad(s.name, 12) +
      pad(s.email || "-", 26) +
      (s.phone || "-"),
  );
}
```

`src/components/RosterView.tsx:103-107`은 이 본문을 `mailto:?bcc=…`로 넘긴다.

### 왜 문제인가

**`bcc`는 수신자 헤더만 가린다. 본문은 모든 수신자가 그대로 본다.**

→ 근무표 메일을 받은 직원 **1명이 나머지 전 직원의 이메일과 전화번호를 전부 얻는다.**
→ **bcc의 보호 효과가 실질적으로 무효다.**
→ 점주는 이 동작을 모를 수 있다. 화면이 "숨은참조로 보호된다"고 말하고 있기 때문이다.

**화면 안내 문구가 자기 모순이다** — 같은 화면 안에서:

| 위치 | 문구 | 판정 |
|---|---|---|
| `RosterView.tsx:380-381` | "직원 명단(섹션·이름·이메일·전화번호)이 들어간다" | **정확** |
| `RosterView.tsx:383-384` | "받는 사람은 숨은참조로 넣어서 직원끼리 서로 주소가 보이지 않습니다" | **사실과 다름** |

**복사 기능은 더 넓다.** `RosterView.tsx:111-118`의 `copyText()`는 같은 본문을 클립보드에 복사하고
**"단톡방에 붙여넣으세요"**라고 안내한다. 단체 대화방은 확산 범위가 넓고 **회수가 불가능하다.**

**시연 게시본에도 동일한 결함이 있다** — `presentation/프렙노트.html:1120`, `:1197`,
`presentation/app.html:1111`, `:1188`. **현재 외부에서 접근 가능한 버전이 이쪽이다.**

### 🔴 권고 사항 (시행 전 필수)

| # | 조치 | 효과 |
|---|---|---|
| 1 | **`buildEmailBody()`에서 이메일·전화번호 열을 기본 제외한다** | 근본 해결. 근무표 발송 목적에 명단 연락처는 필요하지 않다 |

신분증 사본 제출·서면 우편 접수 같은 절차를 요구하면 **제38조 제4항 위반 소지가 크다.**

## 6-3. 사업자등록 전이어도 의무가 있다

## 7-4. ⚠️ 2026-09-18 심사 발표 관련

**시연에 실제 직원의 이름·이메일·전화번호를 넣지 말 것.**
근무표 화면은 실명·이메일·전화번호를 다루고, 발송 기능은 그 명단 전체를 메일 본문에 넣는다.
**심사장 화면에 실제 개인정보가 노출되면 그 자체가 사고다.**

> ⚠️ **"가명 시드로 교체"는 실행할 수 없는 지시다 — 교체할 시드가 없다.**
> 저장소에 근무표 시드가 **존재하지 않는다.** `data/seed.json`에 `staff` 문자열이 **0건**이고,
> `src/lib/roster.ts:40`과 `:54`는 저장된 값이 없으면 `{ staff: [], assign: {} }`를 돌려주며,

> `store.get("roster", { staff: [], assign: {} })`로 **빈 배열에서 시작한다.**
> **실명은 시연 기기의 브라우저 `localStorage`에만 손으로 입력돼 있다.**
>
> **실제로 해야 하는 일:** 시연 기기에서 근무표 화면의 직원을 **× 버튼으로 전부 삭제**하거나
> **브라우저 사이트 데이터를 지운 뒤**, 가명(예: 김바리·박제빵)과 `example.com` 주소로 **다시 입력한다.**
> 대상은 파일이 아니라 **시연 기기 브라우저**다 (`sop:roster` / 단일 파일은 `roster`). → 부록 A #1

**2026-09-04 추가 — 시연 전에 지워야 할 것이 늘었다.**

기존에는 근무표(`sop:roster`) 하나만 신경 쓰면 됐다. 이제 다음도 시연 화면에 뜬다:

### 제6조의2 (일부 화면의 잠금번호 안내)

매출·원가·거래처 단가·근로계약 조건 화면에는 **잠금번호를 설정할 수 있습니다.**
이는 **같은 기기를 쓰는 다른 이용자가 실수로 열람하는 것을 막기 위한 것**이며,
브라우저를 닫으면 다시 잠깁니다.

**다만 이 잠금은 다음을 보장하지 않습니다.**

- 저장된 정보 자체는 **암호화되지 않습니다.** 기기를 사용할 수 있는 사람은 브라우저의
  개발자 도구 등으로 잠긴 화면의 정보를 확인할 수 있습니다.
- 근무표 화면(직원 이름·연락처)에는 잠금이 적용되지 않습니다.

**따라서 직원의 근로조건·연락처가 저장된 기기는 잠금번호와 별개로,
기기 자체의 화면 잠금과 물리적 관리가 필요합니다.**

잠금번호는 **번호 그대로 저장되지 않고 되돌릴 수 없는 요약값으로만 저장**됩니다.
다만 **번호를 잊은 경우 재설정하는 기능이 없으므로**, 잊으면 브라우저의 사이트 데이터를
삭제해야 하고 그 경우 저장된 기록이 함께 사라집니다.

### 제7조 (정보주체와 법정대리인의 권리·의무 및 행사방법)

이용자와 직원은 **열람·정정·삭제·처리정지**를 언제든지 요구할 수 있습니다
(개인정보 보호법 제35조부터 제37조까지). 대리인을 통해서도 요구할 수 있습니다(제38조 제1항).

**1. 기기에 저장된 정보 (직원 명단·근무표·레시피·체크 기록)**

이 정보는 서비스 서버가 아니라 **매장의 기기에만 있으므로, 매장 관리자에게 요청**하시면 됩니다.

- **명단에서 본인 삭제** — 근무표 화면에서 이름 옆 × 버튼 (근무 배정도 함께 삭제됩니다)
- **근로계약 조건 삭제** — 근로계약서 화면의 "이 계약 정보 지우기"
- **출퇴근 시각 정정** — 출퇴근 화면에서 시각을 직접 고칠 수 있습니다
- **기기의 모든 정보 삭제** — 브라우저의 "사이트 데이터 삭제"를 실행하면 전량 즉시 삭제됩니다
- **화면에서 지울 수 없는 항목** — 아래 항목은 현재 화면에 삭제 기능이 없습니다.
  삭제가 필요하면 브라우저의 사이트 데이터 삭제를 이용하십시오.

  | 지울 수 없는 것 | 비고 |
  |---|---|
  | **출퇴근 기록** | 시각을 고칠 수는 있으나 기록 자체를 지우는 기능이 없습니다 |
  | 지난 날짜의 체크리스트 기록 | 오늘 기록만 화면에서 지울 수 있습니다 |
  | 프렙 체크 기록 | 화면에 삭제 기능이 없습니다 |
  | 발주 체크 기록 | 화면에 삭제 기능이 없습니다 |
  | 매출 기록 | 값을 0으로 고칠 수만 있습니다 |
  | 기기 식별값 | 화면에 삭제 기능이 없습니다 |

> ⚠️ **브라우저의 사이트 데이터를 지우면 출퇴근·근로계약·매출·거래처 기록이 함께 사라집니다.**
> 출퇴근 기록과 근로계약 조건은 근로기준법상 3년 보존 대상이므로,
> **지우기 전에 매장에서 따로 보관할 방법을 마련하십시오.**

**2. 서버에 저장된 이용 기록**

제10조의 문의처로 요청하시면 처리합니다.
계정이 없어 본인 확인이 어려우므로, **기기 식별값을 알려주시면** 해당 기록을 특정해 삭제할 수 있습니다.
*(※ 기기 식별값을 이용자가 확인할 수 있는 화면은 **[ ] 준비 중**입니다 — 부록 D [B-18])*

**3. 수수료** — 열람·정정·삭제·처리정지 요구에 **수수료와 우송료를 청구하지 않습니다.**

**4. 이의제기** — 요구가 거절된 경우 제10조의 문의처로 이의를 제기할 수 있습니다.
접수 후 처리 결과를 알려드립니다.

**5. 권익침해 구제** — 개인정보 침해신고센터 · 개인정보 분쟁조정위원회
(`privacy.go.kr`, 국번 없이 **182**), 개인정보보호위원회(`pipc.go.kr`).

### 제8조 (개인정보를 자동으로 수집하는 장치의 설치·운영 및 거부)

서비스는 **쿠키와 광고식별자를 사용하지 않습니다.**
다만 이용 현황 파악을 위하여, 이용자의 브라우저 저장소에 **임의의 기기 식별값을 저장**하고
화면을 열거나 조작할 때 이를 이용 기록과 함께 전송합니다.

**현재 이 수집을 거부할 수 있는 설정을 제공하지 않습니다.**
브라우저의 사이트 데이터를 삭제하면 저장된 식별값은 지워지지만,
**다음 접속 시 새 식별값이 발급되어 수집은 계속됩니다.**

*(⚠️ 부록 A #7을 처리하기 전에는 이 문장을 그대로 둘 것.
거부 수단이 생기면 그 방법을 여기에 적고 위 두 줄을 지운다. 없는 기능을 있다고 적으면 안 된다.)*

### 제9조 (만 14세 미만 아동의 개인정보)

서비스는 만 14세 미만 아동의 개인정보를 수집하지 않으며,
연령을 확인하는 절차나 회원가입 절차를 두고 있지 않습니다.
근무표 기능에 만 14세 미만인 사람의 정보를 입력하지 않도록 안내합니다.
만 14세 미만 아동의 정보가 입력된 것을 확인한 경우, 매장 관리자는 즉시 해당 정보를 삭제해야 합니다.
만 14세 미만 아동의 법정대리인은 아동의 개인정보에 대해 열람·정정·삭제·처리정지를 요구할 수 있습니다.

### 제11조 (안전성 확보 조치)

서비스는 개인정보의 안전한 처리를 위하여 다음 조치를 하고 있습니다.

1. **수집 최소화** — 서버가 받는 것은 제1조 제1항의 이용 기록뿐이며, 직원의 이름·연락처를 서버로 보내지 않습니다.
2. **식별정보 분리** — 서버 기록에 이름·이메일·전화번호를 포함하지 않고, 임의의 기기 식별값만 사용합니다.
3. **자유 입력 미수집** — 서버로 전송되는 항목에 자유 입력 문장이 없습니다. 설문도 고정된 선택지뿐입니다.
4. **접속 정보 미기록** — 서비스는 IP 주소·브라우저 정보·쿠키를 기록하지 않습니다.
5. **대리 발송 없음** — 메일은 이용자의 메일 앱을 여는 방식이며, 서비스가 대신 보내지 않습니다.
6. **공용 기기 격리** — 교육 화면의 진행 상태는 탭을 닫으면 사라지며 다음 이용자에게 남지 않습니다.
7. **삭제 확인** — 직원 삭제 시 확인 창을 표시합니다.

**아직 갖추지 못한 조치** *(사실대로 적습니다 — 부록 A #7·#9·#11로 개선 예정)*

- 화면 접근을 제한하는 **PIN·잠금 기능이 없습니다.** 기기를 사용할 수 있는 사람은 근무표를 볼 수 있습니다.
- 브라우저에 저장되는 정보는 **암호화되지 않습니다.**
- 누가 언제 명단을 열었는지에 대한 **접속 기록을 남기지 않습니다.**

> **기기 관리를 함께 부탁드립니다.** 매장의 태블릿·PC에 화면 잠금을 설정하고,
> 공용 기기에서 이용한 후에는 브라우저의 사이트 데이터 삭제를 이용하십시오.
