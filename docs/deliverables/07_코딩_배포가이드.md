## 2. 코드 스타일 — 관찰된 규칙의 성문화

**이 장은 제안이 아니다.** 아래 항목은 전부 `src/` 실측 결과이고, 예외가 있으면 예외까지 적었다. 새 코드는 이대로 쓴다.

### 2-1. 서버/클라이언트 경계 — 폴더가 곧 규칙이다 (예외 0건)

| 규칙 | 실측 |
|---|---|
| `src/components/*.tsx`는 **1행이 `"use client";`**, 2행 빈 줄, 3행부터 import | **21/21** (2026-09-04에 13 → 21. 추가: `ui`, `OwnerGate`, `AttendanceView`, `ContractView`, `SalesView`, `CostView`, `OrderView`, `VendorView`) |
| `src/app/**/page.tsx`는 **전부 서버 컴포넌트** | **16/16** (2026-09-04에 10 → 16). `grep -rln "use client" src/app --include=page.tsx` → **0건** |

즉 규칙은 한 문장이다.

> **페이지는 데이터만 읽어 넘긴다. 상태는 전부 컴포넌트가 가진다.**

대표 예: `src/app/p/[slug]/page.tsx`가 `getPositionBySlug()`로 데이터를 읽고 `<ChecklistView position={…} storeName={…} />` 한 줄만 반환한다.

**새 화면을 만들 때:**
1. `src/app/<경로>/page.tsx` — 서버 컴포넌트. `src/lib/repo.ts`에서 읽어 props로 넘긴다
2. `src/components/<이름>.tsx` — `"use client"`. `useState`·`localStorage`·`fetch`는 전부 여기
3. **페이지에 `"use client"`를 붙이지 말 것.** 붙이는 순간 `repo.ts`(`node:fs` 사용)를 못 부른다

### 2-2. import 순서 (11/13 일치)

```
react (훅)
  ↓
next/* (Link 등)
  ↓
@/components/*
  ↓
@/lib/*
  ↓
import type { … } from "@/lib/types"      ← 항상 마지막
```

표준 예 — `src/components/ChecklistView.tsx:3-6`:

```tsx
import { useCallback, useEffect, useMemo, useState } from "react";

import MediaSlot from "@/components/MediaSlot";
import type { Position, Step } from "@/lib/types";
```

**규칙 3가지**

| 규칙 | 이유 |
|---|---|
| 타입 전용 import는 반드시 `import type` | `tsconfig.json:13` `isolatedModules: true`. 안 쓰면 빌드가 깨질 수 있다 |
| 내부 참조는 `@/` 별칭 | `tsconfig.json:17` `paths: { "@/*": ["./src/*"] }`. `../../` 상대경로를 쓴 곳이 `src/app/` 전체에 0건 |
| 예외: `src/lib/` 안에서 같은 폴더를 부를 때만 `./` | `repo.ts:11` `from "./types"`, `localRecipes.ts` 동일 |

**⚠ 예외 2건 (정직하게 적어둔다)**

`RosterView.tsx:4-5`와 `ShootBoard.tsx:4-5`가 `@/lib/copyText`를 `@/components/BackButton`보다 **위에** 둔다.

### 2-5. 주석 — 이 프로젝트에서 가장 지킬 값어치가 있는 규약

**전부 한국어다. 그리고 "무엇을"이 아니라 "왜, 안 그러면 무슨 일이 나는가"를 적는다.**

용도별로 3+1종이 나뉘어 있다.

| 형태 | 용도 | 대표 예 |
|---|---|---|
| `/* ---- * … * ---- */` **배너 블록** | 파일 머리 / 큰 섹션. **설계 판단의 근거를 적는다** | `src/lib/types.ts:1-16`, `NowPanel.tsx:7-12`, `ShootBoard.tsx:8-` |

| `{/* ---------- 프렙 ---------- */}` | JSX 섹션 구분자 | `src/app/page.tsx:33, 36` |

**왜 이걸 규약으로 올리는가.** 실제로 이런 주석들이다.

`src/app/api/media/route.ts:6-11`:

**이 주석들은 지우면 복구가 안 된다.** 코드를 읽어서는 "요청 500개로 개발 서버가 멈췄다"를 알 수 없다. 다음 사람이 `/api/media`를 파일별 확인 방식으로 "최적화"하는 것을 막아주는 건 이 세 줄뿐이다.

1. **왜 이렇게 했는지를 적는다.** 코드가 무엇을 하는지는 코드를 읽으면 안다
2. **되돌리면 무슨 일이 나는지를 적는다.** 위 두 예가 그렇다

## 2-A. 2026-09-04에 새로 생긴 규약 4개

운영 기능 7종을 만들면서 생긴 관례다. **하나는 모르면 "고쳐서" 깨뜨린다.**

### 2-A-1. ★ `src/lib/`의 **런타임** import는 `.ts` 확장자를 붙인다

```ts
// src/lib/cost.ts
import type { Recipe } from "./types.ts";                        // 타입
import { unitPrice, findItemByName } from "./vendors.ts";        // ★ 런타임
```

**왜** — `node --test`가 `tests/*.test.ts`에서 `../src/lib/cost.ts`를 직접 import한다.
Node의 ESM 해석기는 **확장자를 유추하지 않는다.** 확장자 없이 쓰면 이렇게 죽는다:

```
Error [ERR_MODULE_NOT_FOUND]: Cannot find module '.../src/lib/store'
    imported from .../src/lib/vendors.ts
```

**실제로 겪었다.** 새 lib 6개를 확장자 없이 쓰고 테스트를 돌리자 5파일이 한꺼번에 실패했다.

**되는 이유** — `tsconfig.json`에 `"allowImportingTsExtensions": true`가 있고
(`noEmit` 프로젝트에서만 켤 수 있다), Next의 번들러는 정확한 파일명을 먼저 찾으므로 그대로 통한다.

> ### ⚠️ 이걸 "정리"하지 말 것
> `./store.ts` → `./store` 로 바꾸는 것은 자연스러운 정리처럼 보인다.
> **그러면 그 파일을 쓰는 테스트 전부가 죽는다.** 화면은 멀쩡해서 눈치채기 어렵다.
>
> **적용 범위:** `src/lib/*.ts`의 상대 경로 import (현재 **7파일**).
> `src/app/`·`src/components/`는 `@/` 별칭을 쓰고 번들러만 해석하므로 확장자를 붙이지 않는다.
> **기존 lib 파일 중 타입 전용 import만 있는 것들**(`localRecipes.ts`, `leadTime.ts` 등)은
> 확장자가 없어도 안 깨진다 — 타입 import는 컴파일 때 사라져서 Node가 볼 일이 없다.
> 그래서 이 함정이 그동안 안 보였다.

버튼·입력칸 높이가 화면마다 다르면 바로 오조작이 된다.**

> ⚠️ **기존 화면(S-01 ~ S-10)은 아직 `ui.tsx`를 쓰지 않는다. 지금 규약이 두 벌이다.**
> 새 화면만 옮겼다. → `02_화면설계서.md` 11절 #1-A

**`NumField`가 `type="number"`를 쓰지 않는 이유** — 태블릿에서 입력칸 위에서 스크롤하면
값이 바뀌는 사고가 있다. `text` + `inputMode="decimal"`로 숫자 키패드만 띄우고,
쉼표를 제거한다(`28,000`을 붙여 넣는 사람이 많다).

### 2-A-3. lib 파일 머리에 **"왜 이렇게 했는가"**를 적는다

새 lib 10개 전부 파일 첫 줄부터 주석 블록으로 시작한다. 규칙은 하나다 —
**되묻게 되는 결정에는 이유를 남긴다.**

```ts
/* ------------------------------------------------------------------ *
 * 단위 환산.
 *
 * ★ 규칙 하나만 지킨다: 계열이 다르면 계산하지 않는다.
 *
 * g과 ml은 서로 안 바꾼다. 물이면 1:1이지만 밀가루는 0.55쯤이고
 * 우유는 1.03, 오일은 0.92다. 밀도를 모르는 채 바꾸면 조용히 틀린 값이
 * 나오고, 사람은 그게 틀린 줄 모른다. **틀린 원가율은 빈 칸보다 나쁘다.**
 * ------------------------------------------------------------------ */
```

**이 주석이 실제로 일을 했다** — 문서를 쓰면서 `ownerGate.ts:1-19`의
"이건 보안이 아니라 가리개다"를 근거로 `06_보안설계.md` V-19를 세웠고,
`contracts.ts:1-24`의 주민등록번호 결정을 `10_개인정보처리방침.md` 1-3장에 그대로 인용했다.

**머리 주석의 끝 줄 위치를 문서가 인용하므로**(`ownerGate.ts:1-19` 등) 주석을 늘리면
문서의 인용도 어긋난다. 확인 방법:

```bash
awk '/^ \* ---.*\*\/$/{print FILENAME": 1-"FNR; nextfile}' src/lib/*.ts
```

> ⚠️ **`NR`이 아니라 `FNR`이다.** `NR`은 파일이 여러 개일 때 줄 수가 누적돼서
> 두 번째 파일부터 값이 틀린다. (이 문서를 쓰면서 실제로 틀렸다 — `contracts.ts`가
> `1-24`인데 `1-42`로 나왔다.) 그리고 `exit`이 아니라 `nextfile`이어야 전 파일을 훑는다.

### 2-A-4. 저장은 `store.ts`의 `loadJson`/`saveJson`을 지나간다

**왜** — 화면마다 `try/catch`를 복사하면 한 군데서만 빼먹어도 그 화면만 조용히 죽는다.

저장소의 값은 이전 버전이 쓴 것일 수 있다(`roster.ts:46`의 `role` → `section` 하위 호환이 그 사례).

## 5. CI 파이프라인

### 5-1. 선행 조건

**§4-1(원격 저장소)이 끝나기 전에는 이 장을 실행할 수 없다.** GitHub Actions는 GitHub 저장소가 있어야 돈다.

### 5-2. 무엇을 검사할 것인가 — 넣을 게 두 개뿐이다

| 후보 | 넣나 | 이유 |
|---|---|---|
| **타입 검사** | ✅ | 유일하게 동작하는 게이트(§1-2). 현재 exit 0 |
| **빌드** | ✅ | 타입이 통과해도 빌드는 깨질 수 있다(정적 생성 단계에서 `seed.json` 파싱 등). CI에서는 `.next` 충돌 걱정이 없다 |
| 린트 | ❌ | ESLint 미설치. `npm run lint`를 CI에 넣으면 **대화형 프롬프트에서 워크플로가 멈춘다**(§1-1) |
| **테스트** | ⚠ **커밋되면 넣는다** | HEAD 기준 0건이라 아래 YAML에서는 주석 처리해 뒀다. 08번의 `tests/` 6개가 커밋되면 **주석을 풀기만 하면 된다** |
| 자동 배포 | ❌ | §6-4 참조. 배포 대상이 정해지지 않았다 |

### 5-3. 워크플로 전문

`.github/workflows/check.yml` — **이 한 개면 된다.**

```yaml
# ------------------------------------------------------------------ #
# 매장수첩 — 코드 검사                                                #
#                                                                    #
# 검사는 둘뿐이다. 타입과 빌드.                                       #
#   - 린트를 넣지 않은 이유: ESLint가 설치돼 있지 않다.                #
#     package.json 의 "lint": "next lint" 를 여기서 부르면            #
#     ESLint 설치 여부를 묻는 대화형 프롬프트가 떠서 워크플로가        #
#     타임아웃까지 멈춘다. 넣지 말 것. (07번 §1-1)                    #
#   - 테스트는 맨 아래에 주석으로 준비해 뒀다. 08번(테스트 자동화)의   #
#     tests/ 가 커밋되면 그 두 줄의 주석만 풀면 된다.                  #
#                                                                    #
# ⚠ 빌드 동시 실행 주의                                               #
#   이 워크플로의 `npm run build` 는 GitHub 러너 안에서 도는          #
#   깨끗한 체크아웃이므로 로컬 .next 와 아무 관계가 없다. 안전하다.    #
#   위험한 건 그 반대다 — CI가 통과했다고 로컬에서 확인용으로          #
#   `npm run build` 를 같이 돌리는 것.                                #
#   개발 서버(next dev)나 다른 에이전트/워크플로가 도는 중에           #
#   빌드하면 같은 .next 를 동시에 쓰게 되어 매번 다른 오류가 난다      #
#   (_app.js.nft.json 없음 / clientReferenceManifest 불변식 위반 /    #
#    /_not-found 모듈 못 찾음). 코드 문제로 착각하기 쉽다.             #
#   → 복구법과 증상은 11번 6-4. 로컬 빌드 규칙은 07번 §7-0.           #
#                                                                    #
# concurrency: 같은 브랜치에 push 가 연달아 오면 앞의 실행을          #
#   취소한다. 러너 분을 아끼고, 순서가 뒤집힌 결과를 안 본다.          #
# ------------------------------------------------------------------ #
name: check

on:
  push:
    branches: [master]
  pull_request:

concurrency:
  group: check-${{ github.ref }}
  cancel-in-progress: true

jobs:
  typecheck-and-build:
    runs-on: ubuntu-latest
    timeout-minutes: 10

    steps:
      - uses: actions/checkout@v4

      # 22 인 이유: package.json 의 engines 가 ">=22.18" 이다(08번).
      # 앱의 요구가 아니라 테스트의 요구다 — Node 내장 --test 로
      # .ts 파일을 러너 패키지 없이 직접 돌리기 때문. (07번 §3-4)
      # engines 를 바꾸면 이 줄도 같이 바꿀 것.
      - uses: actions/setup-node@v4
        with:
          node-version: "22"
          cache: "npm"

      # package-lock.json 을 그대로 재현한다.
      # npm install 은 잠금 파일을 갱신해버려 CI 재현성이 깨진다.
      - run: npm ci

      # .next 를 만들지 않는다. 이 프로젝트의 유일한 품질 게이트.
      - name: 타입 검사
        run: npx tsc --noEmit

      # ↓ 08번의 tests/ 가 커밋되면 이 두 줄의 주석을 푼다.
      #   빌드보다 앞에 둔다 — 더 빨리 끝나고, 실패 원인이 더 좁다.
      # - name: 테스트
      #   run: npm test

      # 타입이 통과해도 정적 생성 단계에서 깨질 수 있다
      # (/, /p/[slug], /prep/[slug], /r/[slug], /t/[slug] 가 빌드 시점에 생성된다).
      - name: 빌드
        run: npm run build
```

> **왜 `npx tsc --noEmit`을 그대로 두고 `npm run typecheck`를 안 쓰나.** 08번이 추가 중인 `typecheck` 스크립트가 **아직 커밋되지 않았다.** 커밋된 뒤에 `run: npm run typecheck`로 바꾸는 게 더 낫다 — 검사 명령이 `package.json` 한 곳에만 있게 된다. 지금 바꾸면 워크플로가 HEAD에서 깨진다.

**의도적으로 넣지 않은 것**

| 안 넣은 것 | 이유 |
|---|---|
| 매트릭스 빌드 (Node 18/20/22) | 실행 환경이 매장 PC 한 대다. 러너 시간만 3배 |
| 캐시 커스터마이징 | `setup-node`의 `cache: npm`으로 충분하다 |
| 아티팩트 업로드 | 배포를 CI가 하지 않으므로 `.next`를 보관할 이유가 없다 |
| `npm audit` | 04번(라이선스 감사)이 별도 문서로 관리 중이다. CI에서 중복 실행하면 새 취약점 발표일마다 빨간불이 켜져 신호가 무뎌진다 |
| Windows 러너 | 개발은 Windows지만 코드에 OS 의존이 없다. `node:path`로 경로를 조립한다(`repo.ts:26`, `api/log/route.ts`) |

### 5-4. 이 워크플로가 통과해도 확인되지 않는 것

**CI 초록불을 "정상"으로 읽으면 안 된다.** 아래는 러너가 절대 못 잡는다.

| 못 잡는 것 | 어디서 잡나 |
|---|---|
| 화면이 실제로 뜨는지, 클릭이 되는지 | §9-A(커밋 전) · §7-5(배포 후) · 11번 10장 |
| `/api/log`가 실제로 기록을 남기는지 | 11번 10장 "기록이 쌓이는지" |
| 평문 HTTP에서 복사 버튼이 죽는 문제 | 11번 6-5 |
| 문구가 사실과 다른 것 | 사람이 읽는 수밖에 없다. 커밋 `282c0a9`의 2·4번이 그 유형이었다 |
| CSP 적용 후 콘솔 위반 | §8-4 |

## 7. 배포 절차

### 7-0. 🚨 모든 절차보다 먼저 — 빌드는 단독으로 돌린다

**이 규칙 하나가 이 장 전체에서 가장 자주 어겨진다.**

```
빌드 전에 반드시:
  1. 개발 서버(next dev)를 껐는가
  2. 다른 에이전트·워크플로가 도는 중이 아닌가
```

둘 중 하나라도 아니면 **매번 다른 오류가 난다.** `_app.js.nft.json` 없음 / `clientReferenceManifest` 불변식 위반 / `/_not-found` 모듈 못 찾음 — 전부 같은 병이다. `.next`를 두 프로세스가 동시에 쓰는 것.

**코드 문제로 착각하기 쉽다.** CLAUDE.md에 2026-09-03에 실제로 당한 기록이 있고, 11번 6-4가 증상과 복구법을 정리해 두었다.

**대신 이걸 쓴다.**

```bash
npm run typecheck
# HEAD 기준이면:  node node_modules/typescript/bin/tsc --noEmit
```

`.next`를 건드리지 않으므로 개발 서버를 켜둔 채 얼마든지 돌려도 된다. 커밋 전 검사는 **전부 이것으로 한다.**

> ⚠ 경로만 쓴 `node_modules/typescript/bin/tsc --noEmit`은 **PowerShell에서 조용히 아무 일도 안 한다.** 앞에 `node `를 붙일 것 (§1-2).

### 7-1. 개발 중 — 커밋 한 번의 절차

```bash
# 1. 타입 (개발 서버 켜둔 채 가능)
npm run typecheck
#    HEAD 기준이면:  node node_modules/typescript/bin/tsc --noEmit
#    경로만 쓰면 PowerShell에서 조용히 통과한다 — 앞의 node 를 빼지 말 것 (§1-2)
#    08번의 tests/ 가 커밋된 뒤에는 여기에  npm test  도 함께

# 2. 브라우저에서 바뀐 화면을 실제로 눌러본다
#    타입이 못 잡는 결함이 이 프로젝트 결함의 대부분이다 (§1-2)

# 3. 의도한 파일만 들어갔는지 확인
git status
git diff --stat

# 4. 커밋 (§4-2 형식)
git add <파일들>
git commit
```

**`git add .`을 쓰지 않는다.** `public/media/`와 루트 쓰레기 파일(§1-3)이 아직 트래킹 중이라 의도치 않은 것이 딸려 온다.

### 7-2. (가) 시연 배포 — 발표용 단일 파일

**배포랄 게 없다. 파일을 옮기는 것이 전부다.**

```bash
# 1. 발표에 쓸 노트북으로 파일을 복사한다 (USB / 메일 / 클라우드)
presentation/매장수첩.html

# 2. 그 노트북에서 더블클릭해 연다
# 3. 인터넷을 끊고 한 번 더 연다   ← 06번 V-12 (폰트 CDN)
```

**되돌리기:** 파일 하나이므로 이전 버전 파일로 덮어쓰면 끝이다. **발표 전날 버전을 별도 파일명으로 하나 더 보관해 둘 것.**

**⚠ 이 파일은 `src/`에서 자동 생성되지 않는다.** 손으로 만든 사본이다. `data/seed.json`이나 컴포넌트를 고쳐도 이 파일은 안 따라간다. **양쪽을 고쳐야 할 때가 있다는 것을 잊지 말 것** — 예: 06번 V-01의 `esc()` 적용은 단일 파일 3개에만 해당한다.

### 7-3. (나) 정식 배포 — 매장 PC

**⚠ 실행 전 D-007 상태를 확인한다 (§6-4).**

```bash
# ── 매장 PC에서, 최초 1회 ──────────────────────────────
# 0) 되돌릴 지점을 적어둔다. 태그가 0개라 이게 유일한 표식이다
git rev-parse HEAD              # → 이 해시를 종이에 적는다

# 1) 의존성 (잠금 파일 그대로 재현)
npm ci

# 2) 환경변수 — 고정 IP를 먼저 정한 뒤에
#    .env.local 에  NEXT_PUBLIC_SITE_URL=http://<고정IP>:3000

# 3) 개발 서버가 꺼져 있는지 확인하고 (§7-0)
npm run build

# 4) 기동
npm start
```

태블릿에서 `http://<PC의 LAN IP>:3000`으로 접속한다. `next start`가 별도 옵션 없이 LAN 주소를 열어준다(11번 4장에서 실행 로그로 확인됨).

**내용만 고쳤을 때 (레시피·프렙·시드)**

```bash
# 서버를 멈추고
npm run build
npm start
```

**빌드를 다시 하지 않으면 화면이 안 바뀐다** (§6-1). 사장님에게 넘길 때는 이 두 줄을 배치 파일 하나로 감싸주는 게 현실적이다.

### 7-4. 롤백

**태그가 0개이므로 롤백 수단은 커밋 해시뿐이다.** 그래서 §7-3의 0번(해시 적어두기)이 절차의 첫 줄이다.

| 상황 | 방법 | 주의 |
|---|---|---|
| **커밋 하나만 되돌린다** (권장) | `git revert <해시>` → `npm run build` → `npm start` | 이력이 남는다. 원격에 push했어도 안전하다. **§4-2의 "한 커밋에 한 가지"가 여기서 값을 한다** |
| 여러 커밋 전으로 돌아간다 | `git revert <시작해시>..<끝해시>` | 순서 주의. 충돌이 나면 하나씩 |
| **긴급 — 지금 당장 화면만 살린다** | 되돌리는 대신 **`presentation/매장수첩.html`을 연다** | 서버 없이 뜬다. 체크가 저장되지 않지만 화면은 전부 나온다 |
| 설정 하나만 되돌린다 (예: 보안 헤더) | `git revert <그 커밋>` | §8-3이 이 변경을 단독 커밋으로 요구하는 이유 |

**`git reset --hard`를 쓰지 않는다.** 원격이 생긴 뒤에는 push한 이력을 부수고, 지금은 커밋이 이 PC에만 있어서 되돌릴 수 없다.

**롤백해도 안 돌아오는 것**

| | 왜 |
|---|---|
| `data/events.jsonl` | `.gitignore` 대상. **git이 안 갖고 있다.** 58건이 가설 검증의 유일한 근거다(06번 V-04) — **배포 직전에 따로 복사해 둘 것** |
| 태블릿 브라우저 안의 데이터 | 체크 기록·추가한 레시피·근무표. 서버에 없다 (11번 9장) |
| 손으로 고친 단일 파일 | 자동 생성이 아니다 (§7-2) |

### 7-5. 배포 후 즉시 확인 (3분)

```bash
# 1) 응답 헤더 — §8 적용 후라면 반드시
curl -I http://<IP>:3000

# 2) 홈이 뜨는지
curl -s -o /dev/null -w "%{http_code}\n" http://<IP>:3000
```

브라우저에서:
- [ ] 홈 → 프렙 → 레시피 → 근무표 → 교육 모드까지 눌러서 이동되는가
- [ ] **개발자 도구 콘솔에 CSP 위반 0건인가** (§8-4)
- [ ] 체크를 하나 누르고 새로고침 → 유지되는가
- [ ] `data/events.jsonl`에 새 줄이 붙는가 (`tail -1 data/events.jsonl`)

마지막 항목이 핵심이다. **이게 안 되면 배포는 성공했지만 제품의 목적(가설 검증)은 실패한 것이다.**

## 8. 보안 헤더 적용

### 8-1. 무엇을 적용하나

06번 §5-4(870-960행)가 설계한 응답 헤더를 `next.config.ts`에 넣는다. **현재 `next.config.ts`는 9줄이고 헤더 설정이 0건이다** (06번 V-10).

각 헤더가 막는 것:

| 헤더 | 무엇을 막나 |
|---|---|
| `Content-Security-Policy` | 주입된 스크립트가 실행되는 것. 이 앱의 실질 위협은 저장형 XSS다(06번 V-01) |
| `X-Content-Type-Options: nosniff` | 브라우저가 파일 내용을 보고 타입을 멋대로 추측해 실행하는 것 |
| `Referrer-Policy: strict-origin-when-cross-origin` | 외부 사이트로 나갈 때 **체크리스트 슬러그가 들어간 전체 URL**이 새는 것 |
| `X-Frame-Options: DENY` | 남의 페이지가 이 화면을 iframe에 넣고 클릭을 가로채는 것(클릭재킹) |
| `Permissions-Policy` | 카메라·마이크·위치를 페이지가 요구하는 것. **촬영 모드를 만들면 `camera=(self)`로 되돌려야 한다** |
| `Strict-Transport-Security` | 다음 접속부터 평문 HTTP로 내려가는 것 (HTTPS 환경에서만 의미) |
| `X-Robots-Tag: noindex, nofollow` | 검색엔진 색인. 라우트 metadata의 `robots`가 **6곳에만 걸려 있고**(루트·`/prep/`·`/t/`·`/p/`·`layout.tsx`는 미적용, 06번 V-09) 정적 파일에는 아예 안 붙는다 — **`X-Robots-Tag`는 그 둘을 한꺼번에 덮는다** |

### 8-2. 코드 (`next.config.ts` 전체 교체)

> **아래는 06번 §5-4의 코드를 한 글자도 바꾸지 않고 옮긴 것이다.** 문서 간 불일치를 만들지 않기 위해서다. 각 지시자를 그렇게 고른 이유는 06번 §5-4에 있다.
>
> 기존 `images: { remotePatterns: [] }`가 그대로 유지되므로 잃는 것이 없다.

```ts
import type { NextConfig } from "next";

const dev = process.env.NODE_ENV === "development";

/**
 * CSP 주의 — 'unsafe-inline'을 script-src에 둔 이유:
 *   App Router가 RSC 페이로드를 인라인 <script>로 주입한다.
 *   정식 배포 후 middleware.ts에서 요청별 nonce를 발급해
 *   'nonce-XXX' 'strict-dynamic' 으로 바꾸고 'unsafe-inline'을 제거할 것.
 *
 * 'unsafe-eval' 은 dev 전용이다 — next dev 청크가 eval-source-map을 쓴다.
 *   프로덕션 빌드에는 붙지 않으므로 배포본 CSP는 약해지지 않는다.
 *
 * 폰트 — Next 앱은 외부 폰트를 쓰지 않으므로 font-src 'self' 로 충분하다.
 *   단일 파일 버전(presentation/)은 이 설정의 적용 대상이 아니다.
 */
const csp = [
  "default-src 'self'",
  "script-src 'self' 'unsafe-inline'" + (dev ? " 'unsafe-eval'" : ""),
  "style-src 'self' 'unsafe-inline'",
  "img-src 'self' data: blob:",
  "media-src 'self'",
  "font-src 'self'",
  "connect-src 'self'",
  "frame-ancestors 'none'",
  "form-action 'self'",
  "base-uri 'self'",
  "object-src 'none'",
  "upgrade-insecure-requests",
].join("; ");

const nextConfig: NextConfig = {
  // 체크리스트 사진을 외부 호스트로 옮기면 여기에 도메인을 추가한다.
  images: { remotePatterns: [] },

  // X-Powered-By: Next.js 를 내보내지 않는다
  poweredByHeader: false,

  async headers() {
    return [
      {
        // 정적 파일(/app.html 등)까지 포함해 전 경로에 적용된다
        source: "/:path*",
        headers: [
          { key: "Content-Security-Policy", value: csp },
          { key: "X-Content-Type-Options", value: "nosniff" },
          { key: "Referrer-Policy", value: "strict-origin-when-cross-origin" },
          { key: "X-Frame-Options", value: "DENY" },
          {
            key: "Permissions-Policy",
            // 촬영 모드를 만들면 camera=(self) 로 되돌릴 것
            value:
              "camera=(), microphone=(), geolocation=(), payment=(), usb=()",
          },
          {
            key: "Strict-Transport-Security",
            value: "max-age=63072000; includeSubDomains",
          },
          {
            // D-007 미이행분(V-09) — 정적 파일까지 한꺼번에 덮는다
            key: "X-Robots-Tag",
            value: "noindex, nofollow",
          },
        ],
      },
    ];
  },
};

export default nextConfig;
```

### 8-3. 절차 — 06번에 없는 3가지

06번은 **무엇을 넣을지**를 설계했다. 여기는 **언제, 어떻게 넣을지**다.

**(1) 적용 시점은 발표 후다. 발표 전에 넣지 않는다.**

06번 §7-2 3번이 이 항목을 "정식 배포 전"으로 분류하고 **"발표 전 항목이 아니다"**라고 명시했다. 이유는 하나다 — **9/18 라이브 시연 경로가 `npm run dev`인데, `headers()`는 개발 서버에도 적용된다.** dev 분기(`'unsafe-eval'`)를 빠뜨린 채 넣으면 하이드레이션이 CSP에 막혀 **화면이 죽는다.**

발표 30분 전에 화면이 안 뜨면 원인을 찾을 시간이 없다.

**(2) 고치면 개발 서버를 재시작해야 반영된다.**

`next.config.ts`는 핫리로드 대상이 아니다. 고치고 새로고침만 하면 **"적용했는데 헤더가 안 붙네"**로 30분을 쓴다.

```bash
# 서버를 끄고 다시
npm run dev
```

**(3) 이 변경만 단독 커밋으로 넣는다.**

```bash
git add next.config.ts
git commit          # 다른 파일을 같이 넣지 않는다
```

**이유:** 태그가 0개라 롤백 수단이 `git revert <해시>` 하나뿐이다(§7-4). 헤더 때문에 화면이 죽었을 때 한 번의 revert로 정확히 그것만 되돌릴 수 있어야 한다. 다른 변경이 섞이면 그게 안 된다.

### 8-4. 적용 후 필수 검증

06번 §5-4가 **"이 확인 없이 발표 당일에 적용하지 말 것"**이라고 못 박은 항목이다.

```bash
# 1) 개발 서버를 재시작하고
npm run dev
```

브라우저에서:
- [ ] 홈이 뜨는가
- [ ] **개발자 도구 콘솔에 CSP 위반 메시지가 0건인가**
- [ ] 체크 토글이 눌리는가 (하이드레이션이 살아 있다는 뜻)
- [ ] 프렙·레시피·근무표·교육 모드로 이동되는가

```bash
# 2) 프로덕션에서도 (개발 서버를 끈 뒤 — §7-0)
npm run build && npm start
curl -I http://localhost:3000
```
- [ ] 응답에 위 7개 헤더가 전부 보이는가
- [ ] `X-Powered-By`가 **사라졌는가** (`poweredByHeader: false`)
- [ ] CSP의 `script-src`에 `'unsafe-eval'`이 **없는가** (프로덕션이므로 안 붙는 게 정상)

### 8-5. 적용 대상이 아닌 것

| 대상 | 왜 |
|---|---|
| `presentation/*.html` (시연본) | 서버를 안 거친다. `file://` 또는 Artifact 호스트의 자체 CSP를 탄다. 그리고 이 파일들은 인라인 `<script>`/`<style>`과 `style="…"` 속성을 다수 쓰므로 정적 파일에 nonce를 못 붙인다 — `unsafe-inline` 없이는 시연본이 깨진다 (06번 §5-4) |
| `public/app.html` | **삭제 대상이다** (06번 V-05). 삭제하면 이 질문 자체가 사라진다 |

### 8-6. 나중에 되돌려야 하는 두 줄

| 언제 | 무엇 |
|---|---|
| **정식 서비스 시작 시** | `X-Robots-Tag: noindex, nofollow` **제거.** 지금 넣는 건 D-007이 검색 차단을 조건으로 걸었기 때문이다. 안 지우면 서비스가 검색에 영원히 안 잡힌다 |
| **촬영 모드를 만들 때** | `Permissions-Policy`의 `camera=()` → `camera=(self)`. 안 바꾸면 `<input capture>`가 카메라를 못 연다 |

**둘 다 잊기 쉽다.** §10의 릴리스 이력에 적어둔다.

## 10. 릴리스 이력 관리

### 10-1. 지금 문제 — 태그가 0개다

```bash
git tag        # → 출력 없음
```

**"발표 때 쓴 버전"을 가리킬 방법이 없다.** 커밋 해시 7자리를 종이에 적어두는 게 현재의 유일한 수단이고(§7-3 0번), 그게 없으면 롤백 대상을 찾느라 `git log`를 훑어야 한다.

`package.json:3`의 `"version": "0.1.0"`은 첫 커밋 이후 한 번도 안 올라갔다.

### 10-2. 규칙 — 태그는 "실제로 밖으로 나간 것"에만 붙인다

브랜치는 안 판다(§4-3). 태그는 다르다 — **되돌릴 지점을 만드는 게 목적**이라 값이 확실하다.

| 언제 | 태그 | 예 |
|---|---|---|
| 발표·시연에 쓴 버전 | `demo-<YYYYMMDD>` | `demo-20260918` |
| 매장에 실제로 넣은 버전 | `v0.<n>.0` | `v0.2.0` |
| 그 외 | 붙이지 않는다 | |

```bash
git tag -a demo-20260918 -m "9/18 정부지원사업 심사 발표에 사용한 버전"
git push origin demo-20260918        # 원격이 생긴 뒤
```

`-a`(annotated)를 쓴다. 날짜·작성자·메시지가 같이 남는다.

**태그를 붙이는 시점은 "배포 직전"이다.** §7-3의 0번(`git rev-parse HEAD`)을 태그로 대체할 수 있게 된다.

### 10-3. 릴리스 노트 — 파일 하나로 충분하다

`CHANGELOG.md`를 루트에 둔다. **커밋 메시지가 이미 충실하므로(§4-2) 자동 생성으로도 초안이 나온다.**

```bash
git log --format='- %s (%h)' <이전태그>..HEAD
```

**최소 형식**

```markdown
# 변경 이력

## demo-20260918 — 2026-09-18
발표·시연에 사용한 버전.

**바뀐 것**
- (커밋 제목들)

**알려진 제약**
- 단일 파일 시연본은 새로고침 시 체크가 초기화된다
- /api/log 미동작 (서버 없음)

**되돌리려면**
git revert <해시>
```

**"알려진 제약"란이 이 프로젝트에서 가장 중요하다.** 11번·12번이 "아직 안 됩니다"를 정직하게 적어온 관행과 같은 것이고, 심사·인수인계 양쪽에서 되받히지 않는 유일한 방법이다.

### 10-4. 버전 번호

`package.json`의 `version`은 **매장에 실제로 넣을 때만** 올린다. 개발 중에 올리는 건 의미가 없다 — npm에 배포하지 않고, `private: true`다.

| 무엇이 바뀌었나 | 올림 |
|---|---|
| 화면·기능 추가 | `0.1.0` → `0.2.0` |
| 결함 수정만 | `0.1.0` → `0.1.1` |
| **데이터 구조 변경 (저장소 키·시드 스키마)** | `0.x` → `0.(x+1).0` + **CHANGELOG에 마이그레이션 필요 여부를 반드시 적는다** |

마지막 줄이 중요하다. 저장소 키를 바꾸면 **태블릿에 쌓인 체크·레시피·근무표가 사라진다**(§2-7). 그건 사용자가 알아야 하는 변경이다.
