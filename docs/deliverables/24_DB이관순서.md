| 검증 | PGlite(PG18) **동작 55 · 대조 27 · 훑기 11** + 올린 뒤 실물(PG17.6)에서 **게이트 2개 0행** |

**그릇은 다 만들었고 아직 아무것도 안 옮겼다.** 매출·시급·단가·레시피·출퇴근은
전부 그 태블릿 안에 있다. 아래 1~7 단계는 **그것을 옮기는 일**이다.

> 💡 **표를 한 번에 올린 것은 의도한 것이다.** 아래 단계는 «표를 만드는 순서» 가
> 아니라 **«앱을 옮기는 순서»** 다. 표는 비어 있고 RLS 가 전부 막고 있어서
> 한꺼번에 올려도 새는 곳이 없다 — 오히려 §2 아래의 "가리켜지는 쪽이 먼저"
> 문제를 통째로 피한다(한 파일이 위에서부터 순서대로 돌기 때문이다).

## 0-A. ★ 2026-09-13 — 권한을 빠뜨려서 로그인이 «안 된 것처럼» 보였다

1단계를 끝내고도 화면의 배지가 **「로그인」 그대로**였다. 로그인은 되고 있었다.

```
① 로그인            → Supabase 인증 성공 (auth.users.last_sign_in_at 남음)
② 토큰 쿠키 저장    → 정상
③ users 표 조회     → permission denied     ← 여기
④ 못 읽었으니 anon  → 화면은 로그인 전과 똑같다
```

**`0003_schema_v2` 가 RLS 와 정책은 다 만들었는데 `grant` 를 안 했다.**
정책은 «어느 줄을» 을 정하고 권한은 «그 동작을 아예 할 수 있는가» 를 정한다.
실측으로 표 38개 중 `authenticated` 가 SELECT 할 수 있던 것은 `events` 하나뿐이었다.

★ **아무 오류도 안 뜬다.** `whoAmI()` 가 실패를 `{state:"anon"}` 으로 삼키기 때문이다
(화면이 멈추면 안 되므로). 그래서 **로그인이 실패한 것처럼 보인다** — 서버 기록만
보면 «성공» 으로 읽히는데 화면은 «실패» 다. 둘 다 봐야 알 수 있었다.

→ `db/migrations/0005_grants.sql` 로 고쳤다. `alter default privileges` 도 같이 넣어서
**앞으로 표를 더해도 같은 함정에 안 빠진다.**

## 1. 순서를 잘못 잡으면 생기는 사고 셋

이 세 가지가 아래 차례를 결정했다. 순서는 취향이 아니다.

### (가) RLS 는 로그인이 있어야 선다 — 그래서 로그인이 1번이다

`schema_v2.sql` §11 의 격리 정책은 `current_store_id()` 를 읽고, 그 함수는
**`auth.uid()`**, 즉 **로그인한 사람**에서 매장을 찾는다.

**지금 앱에는 로그인이 없다.** 로그인 없이 표부터 올리면 `auth.uid()` 가 늘 `null` 이라
정책이 **아무 줄도 허용하지 않거나**(화면이 빈다), 급한 마음에 정책을 풀면
**익명 키 하나로 모든 매장의 매출·시급이 열린다.**

> ⚠️ 지금 `events` 표가 익명 키를 받는 것은 **넣기만 되고 읽기가 안 되기 때문**이다.
> 매출·시급이 든 표에는 같은 방식을 **절대 쓰면 안 된다.**

### (나) 데이터가 서버가 아니라 **그 태블릿 한 대** 안에 있다

이관은 "서버에서 서버로" 가 아니다. **그 기기에서 한 번, 사람이 한다.**
그 태블릿을 초기화하거나 브라우저 저장소를 비우면 **그걸로 끝이다.**

유일한 통로는 이미 있다 — **`/backup` 의 JSON 내보내기.**
이관 도구는 **그 JSON 을 먹는 것**으로 만든다. 새 통로를 만들지 않는다.

### (다) 출퇴근·근로계약은 법정 3년 보존이다

근로기준법 제42조. 이관 중 유실은 **사고가 아니라 위반**이다.
그래서 5단계는 **옮기기 전·후 건수가 같다**를 통과하지 못하면 다음으로 안 간다.

## 2. 차례 — 각 단계는 그 자체로 배포 가능해야 한다

`main` 은 항상 배포 가능해야 하므로, **한 단계 = 한 브랜치 = 한 PR** 로 끊는다.
단계 중간에 멈춰도 앱이 도는 상태여야 한다.

**표는 이미 다 있으므로 각 단계는 「코드를 옮기고 데이터를 넣는 일」이다.**

| 단계 | 쓰기 시작하는 표 | 같이 고치는 코드 | 끝났다고 말할 수 있는 조건 |
|---|---|---|---|
| **0** | — | — | ✅ **끝.** 표 38개 · 게이트 2개 0행 |
| **1** | `stores` · `users` (+`units` 이미 참) | 로그인 화면 · 세션 | 사장님이 로그인하면 **자기 매장 id 가 나온다.** 화면은 아직 전부 localStorage |
| **2** | `suppliers` · `items` · `item_versions` | `src/lib/vendors.ts` 의 load/save | 거래처·단가가 서버에서 온다. **다른 화면은 안 건드린다** |

## 2-A. 1단계 — 로그인 (2026-09-13 · 코드는 들어갔다)

**앱 쪽은 끝났다.** 남은 것은 **계정과 매장 한 줄**을 만드는 일이고, 그건 사람이 한다.

| 들어간 것 | |
|---|---|
| `src/lib/serverSession.ts` | Supabase Auth 를 **REST 로** 부른다 (SDK 안 깖 — 런타임 의존성 3개 그대로) |
| `/api/auth/login` · `logout` · `me` | 토큰은 **httpOnly 쿠키**에만. 화면으로 안 나간다 |
| `/login` · `SessionBadge` | 첫 화면 오른쪽 위에 «누구로 열려 있나» |
| `tests/serverSession.test.ts` | 토큰 유출 · 비밀번호 저장 · 실패 이유 노출을 못 박는다 |

### 왜 매장을 앱에서 못 만드나

`stores` 에는 **읽기 정책만 있고 넣기 정책이 없다.** 일부러다 — 아무나 매장을
만들 수 있으면 **남의 매장 이름으로 계정을 파는 길**이 열린다. 첫 매장은
운영자가 대시보드에서 만든다.

### 누르는 순서

**① 계정 만들기** — Supabase → **Authentication → Users → Add user**
이메일·비밀번호를 넣고 **Auto Confirm User 를 켠다**(안 켜면 메일 인증 전까지 로그인이 안 된다).

**② 매장과 계정을 잇기** — SQL Editor 에서 아래를 돌린다.
`⟨⟩` 세 칸만 바꾼다.

```sql
with s as (
  insert into public.stores (name, slug)
  values ('⟨매장 이름⟩', 'main')
  returning id
)
insert into public.users (id, store_id, name, role)
select u.id, s.id, '⟨부를 이름⟩', 'owner'
from auth.users u, s
where u.email = '⟨①에서 넣은 이메일⟩';
```

**③ 확인** — 앱 첫 화면 오른쪽 위가 「로그인」 → 누르고 들어가면
**「⟨매장 이름⟩ · ⟨부를 이름⟩」** 으로 바뀐다.

> ⚠️ 「**매장 연결 안 됨**」이 빨갛게 뜨면 ②가 안 된 것이다. 로그인은 됐는데
> `users` 행이 없다는 뜻이고, 그 상태로는 어떤 표에도 한 줄도 못 넣는다.

### ⚠️ 로그인은 선택이다 — 시연이 막히면 안 된다

환경변수가 없거나 로그인을 안 해도 **앱은 지금까지와 똑같이 돈다.**
배지도 안 뜬다. `STORE_PIN` 없으면 열리는 것, `SUPABASE_URL` 없으면 파일에
쌓는 것과 같은 규율이다 — **9/18 데모데이에서 로그인 화면이 길을 막으면 안 된다.**

---

### 줄을 넣는 순서는 여전히 지켜야 한다

표는 다 있지만 **줄은 가리켜지는 쪽이 먼저**다. 아니면 외래키가 거부한다.
`stores` → `users` → `suppliers` → `items` → `item_versions` → … 순서는
[`이관_매핑.md`](../이관_매핑.md) §4 에 있다.

★ 그리고 **1단계 전에는 어떤 표에도 줄이 안 들어간다** — `store_id` 가 있어야
하는데 그 값은 `stores` 에서 나오고, 읽으려면 로그인이 있어야 한다.

## 3. 데이터를 실제로 옮기는 법

```
태블릿 ──[/backup 의 JSON 내보내기]──> 파일 ──[이관 스크립트]──> Supabase
```

1. **그 태블릿에서 `/backup` 으로 JSON 을 받는다.** CSV 말고 JSON 이다 —
   엑셀에서 한 칸만 고쳐도 시각·요일이 깨져 근태와 인건비가 조용히 틀린다.
2. **재료 이름 ↔ 품목 이름 대조표를 0건으로 만든다** ([`이관_매핑.md`](../이관_매핑.md) §1-3).
   **이게 제일 오래 걸린다.** 짝을 못 찾은 것이 한 건이라도 남으면 2단계를 시작하지 않는다.
3. 단계마다 **그 단계의 덩어리만** 넣는다. 한 번에 다 넣지 않는다.
4. 넣은 뒤 **건수와 합계를 양쪽에서 세어 맞춘다.**

> ⚠️ **한 번만 하는 일이 아니다.** 이관하는 동안에도 매장은 돈다.
> 이관일 이후 태블릿에 쌓인 것이 있으면 그건 **두 번째 이관**이다.
> 그래서 이관은 **영업 끝난 뒤**에 하고, 끝나면 그 기기에서 바로 서버 쪽을 쓴다.

## 4. 되돌리기

| 단계 | 되돌리는 법 |
|---|---|
| 1~7 공통 | **앱을 이전 배포로 되돌린다.** localStorage 는 그대로 남아 있으므로 화면이 다시 돈다 |
| DB 쪽 | 그 단계의 표를 `drop` 한다. **앞 단계 표는 건드리지 않는다** |
| 5단계(법정) | ⛔ **`drop` 하기 전에 `/backup` JSON 이 손에 있는지 먼저 확인한다** |
| `/backup` 되돌리기 | **서버까지 같은 내용으로 덮어쓴다** (2026-09-16). 태블릿만 되돌리는 길은 없다 — 로그인 안 했을 때만 태블릿에 남는다. 그러니 되돌리기 전에 「전체 백업」 을 받는 것은 서버를 위해서도 필요하다 |

그래서 **localStorage 를 지우는 코드는 마지막 단계까지 넣지 않는다.**
서버가 확실해질 때까지 브라우저 쪽이 보험이다.

## 5. 게이트 — 이게 빈 결과여야 그 단계가 끝난 것이다

`schema_v2.sql` §12 의 두 조회문을 **단계마다** 돌린다.

1. **RLS 가 안 걸린 표** — 한 줄도 안 나와야 한다
2. **매장을 건너는 참조** — 한 줄도 안 나와야 한다

그리고 사람이 직접 하는 확인 하나:

3. **다른 매장 계정으로 로그인해서 조회하면 0행이어야 한다.**
   정책이 걸렸다는 것과 실제로 막힌다는 것은 다른 말이다.
   `db/verify.js` 가 PGlite 에서 이미 이걸 하지만, **올린 뒤에 실물에서 한 번 더 한다.**

## 6. 아직 안 정해진 것

| 무엇 | 왜 지금 못 정하나 |
|---|---|
| **로그인을 누구에게 주나** | 사장님만인가, 직원도인가. 직원에게 주면 `users` 가 `staff` 와 겹친다 — 스키마는 **둘을 나눠** 뒀다(알바는 대부분 로그인 안 한다). 화면 설계가 먼저다 |
| **매장 PIN 과 로그인의 관계** | 지금 레시피는 매장 PIN 이 막는다(`ServerStoreGate`). 로그인이 생기면 둘 중 하나는 없어져야 한다 — **둘 다 두면 직원이 두 번 입력한다** |
| **이관 시점** | 실증 매장이 정해진 뒤다. 지금 넣을 실데이터가 없다 |
| **요금제** | 지금은 무료 등급으로 돈다(`events` + `media`). 표 37개와 파일이 쌓이면 다시 본다 |
