## 1. 개인정보에 해당하는 항목

이것이 **전부**다. 이 표에 없는 개인정보는 이 서비스에 존재하지 않는다.

| 필드 | 어디서 입력받나 | 어디에 저장되나 | 누가 볼 수 있나 | 근거 |
|---|---|---|---|---|
| **직원 이름** (`name`) | 근무표 화면 `/roster`의 "이름" 입력칸 | 브라우저 localStorage 키 `sop:roster` | ① 그 기기를 쓰는 사람 전원 ② 근무표 메일·카톡을 받은 사람 전원 | `src/lib/roster.ts:15`, `src/components/RosterView.tsx:204-208` |
| **직원 이메일** (`email`) | 같은 화면 "이메일" 입력칸 (`type="email"`) | 같음 | 같음 | `roster.ts:17`, `RosterView.tsx:209-216` |
| **직원 전화번호** (`phone`) | 같은 화면 "전화번호" 입력칸 (`type="tel"`) | 같음 | 같음 | `roster.ts:18`, `RosterView.tsx:217-224` |
| **직원 소속 섹션** (`section`) | 같은 화면. 버튼(제빵/바/홀/주방) 또는 직접 입력 | 같음 | 같음 | `roster.ts:13`, `RosterView.tsx:177-201` |
| **직원별 근무 배정** (`assign`) | 근무표 표의 드롭다운 (조 이름 또는 휴무) | 같음 | 같음 | `roster.ts:22`, `RosterView.tsx:334-351` |

### 이 항목들에 대해 반드시 알아야 하는 사실

**입력하는 사람과 정보주체가 다르다.** 직원이 자기 정보를 넣는 화면이 없다. **매장 운영자가 직원 정보를 대신 입력한다.**
→ 코드 어디에도 정보주체(직원)에게 동의를 받는 화면·문구·체크박스가 없다. `grep`으로 확인했다.
→ 처리방침에 "이용자로부터 동의를 받아 수집한다"고 쓰면 **거짓이 된다.** 실제 구조를 그대로 써야 한다.

**직원 이메일은 비워둘 수 있다.** 비면 메일 발송 대상에서 빠진다 (`RosterView.tsx:97`, `roster.ts:16`). 즉 필수 항목이 아니다.
**전화번호는 어디에도 쓰이지 않는다.** 저장·표시·메일 본문에만 들어가고, 문자 발송이나 전화 연결 기능은 코드에 없다.
→ **수집 목적이 없는 항목이다.** 개인정보 최소수집 원칙(개인정보 보호법 제16조 ❓ 조항번호 확인 필요) 관점에서 **필드를 없애는 쪽을 먼저 검토할 것.** 남긴다면 처리방침에 목적을 적을 수 있어야 한다.

### 개인정보가 **아닌데** 개인정보로 오해하기 쉬운 것

| 항목 | 왜 개인정보가 아닌가 |
|---|---|
| 매장 이름 (`store.name`) | 시드 파일의 고정 값 `"○○ 베이커리 카페"`. 이용자가 입력하는 칸이 없다 (`data/seed.json:4`) |
| `sop:sid` (익명 세션 id) | 난수. 이름·이메일과 연결하는 코드가 없다. **단, 4장의 유보 사항을 반드시 읽을 것** |
| 시드 데이터의 `"name"` 필드들 | 전부 메뉴·재료·조 이름이다 (`아메리카노`, `강력분`, `오픈조` …). 사람 이름은 하나도 없다 — `grep`으로 전수 확인 |

### 4-2. 서버가 **기록하지 않는** 것

`route.ts:18`에서 `request`는 `.json()`을 부르는 데만 쓰인다. **IP·User-Agent·Referer·쿠키를 읽는 코드가 없다.** 미들웨어도 없다 (`src/middleware.ts` 부재 확인).
❓ **확인 필요:** 웹서버·호스팅(Vercel 등)의 접속 로그는 이 코드 밖의 층이다. 정식 배포 시 그 층에서 IP가 남는지 확인해 처리방침에 반영해야 한다. 현재는 미배포다.

### 4-3. `sessionId` 생성 방식과 개인 식별 가능성

```
sid = Math.random().toString(36).slice(2) + Date.now().toString(36)
```
(`ChecklistView.tsx:20-31`, `PrepView.tsx:26-38`, `RecipeDetail.tsx:17-29` — 세 곳에 같은 코드가 복사되어 있고, 세 곳 모두 같은 키 `sop:sid`를 쓴다.)

- 브라우저별로 **한 번 만들어 localStorage에 계속 재사용**한다. 만료 없음.
- localStorage를 못 쓰면 `"no-storage"` 고정 문자열을 보낸다.
- 이름·주민번호·기기 고유 식별자를 섞지 않는다.

**이름·이메일과 연결하는 코드가 있는가 → 없다.** `grep`으로 확인한 근거:
- `sop:roster`를 읽는 함수는 `loadRoster()` 하나뿐이고, 그것을 부르는 파일은 `RosterView.tsx` 하나뿐이다.
- `log()` 호출 11곳의 payload에 `name`·`email`·`phone`이 들어가는 곳은 **0곳**이다.
- `RosterView.tsx`에는 `log()` 함수도, `/api/log` 호출도 **없다.** 근무표 화면은 서버와 통신하지 않는다.

**❓ 그래도 유보해야 하는 두 가지 (전문가 검토 항목):**

1. **`/p/{slug}` 체크리스트는 카톡으로 개인폰에 공유된다** (`CLAUDE.md`). 개인폰이면 `sop:sid`는 **사실상 한 사람에 1:1로 붙는 영구 가명 식별자**가 된다. 서버는 그 사람의 열람 시각·설문 답변을 무기한 누적한다. `sessionId` 단독이 개인정보인지는 다툼의 여지가 있다 → **처리방침에 "익명"이라고 단정하지 말고 "가명 처리된 이용 기록"으로 쓰는 쪽을 검토할 것.**
2. **같은 태블릿의 localStorage 안에 `sop:sid`와 `sop:roster`가 함께 있다.** 서버에서는 연결이 안 되지만, **그 기기에 접근할 수 있는 사람은 둘을 함께 볼 수 있다.** 동일 출처(origin)의 스크립트도 마찬가지다.

### 4-4. `/api/log`는 인증·검증이 없다

`route.ts:23`은 `{ ...body, at }` — **받은 JSON을 그대로 쓴다. 필드 화이트리스트가 없다.**
따라서 누구든 임의 JSON을 POST해 서버 파일에 아무 내용이나 쓸 수 있다. 지금은 클라이언트가 위 11종만 보내지만, **"수집 항목"을 코드가 보장하지 않는다.**
→ 처리방침의 신뢰성을 위해서라도 서버에서 필드를 화이트리스트로 걸러야 한다. (상세는 `06_보안설계.md` 소관)

## 5. 제3자에게 나가는 것 — ⚠️ 가장 심각한 지점

### 5-1. `buildEmailBody`가 만드는 메일 본문에 무엇이 들어가는가

`src/lib/roster.ts:125-171`을 그대로 읽은 결과. 본문은 **두 덩어리**다.

**① `[ 직원 명단 ]` — 전 직원의 섹션·이름·이메일·전화번호가 평문으로 들어간다.**
```
로직 (roster.ts:141-148):
  for (const s of data.staff) {
    out.push(
      pad(s.section || "-", 8) +
      pad(s.name, 12) +
      pad(s.email || "-", 26) +   ← 이메일 평문
      (s.phone || "-")             ← 전화번호 평문
    );
  }
```
`data.staff` 전체를 돈다. 필터가 없다. **이메일이 없는 직원도 `-`로 한 줄 나가고, 전화번호는 무조건 들어간다.**

**② `[ 이번 주 근무 ]`** — 섹션별로 묶어 이름 + 요일별 조/휴무 (`roster.ts:152-167`).

### 5-2. bcc는 이 문제를 막지 못한다

```
RosterView.tsx:103-108
  // 받는 사람을 숨은참조로 넣는다. 직원끼리 서로의 주소가 노출되지 않게.
  const bcc = withEmail.map((s) => s.email).join(",");
  const url = `mailto:?bcc=…&subject=…&body=${encodeURIComponent(body)}`;
```

**bcc는 수신자 헤더만 가린다. 본문은 가리지 못한다.**
결과: **근무표 메일을 받은 직원 한 명은 나머지 전 직원의 이메일과 전화번호를 전부 얻는다.** bcc의 보호 효과는 실질적으로 무효다.

**화면 안내 문구가 사실과 다르다.** `RosterView.tsx:383-384`:
> "받는 사람은 숨은참조로 넣어서 직원끼리 서로 주소가 보이지 않습니다."

본문에 이메일 표가 그대로 들어가므로 **이 문장은 이용자를 오인하게 한다.** 처리방침을 쓰기 전에 **코드나 문구 중 하나를 반드시 고쳐야 한다.**
바로 옆 `RosterView.tsx:380-381`은 "직원 명단(섹션·이름·이메일·전화번호)"이 들어간다고 정확히 적어놨다. **같은 화면의 두 문장이 서로 모순된다.**

### 5-3. "복사 (카톡용)"은 같은 본문을 더 넓게 퍼뜨린다

`RosterView.tsx:111-118`: 같은 `buildEmailBody()` 결과를 클립보드에 복사하고 **"단톡방에 붙여넣으세요"** 라고 안내한다.
→ 전 직원의 이메일·전화번호가 담긴 표가 **단체 대화방에 그대로 올라간다.** 메일보다 확산 범위가 넓고 회수가 불가능하다.

### 5-4. 단일 파일 버전도 같은 문제다

`presentation/app.html:1111` — `p(s.email || "-", 26) + (s.phone || "-")` 로 같은 표를 만들고, `:1188`에서 같은 `mailto:?bcc=…&body=…` 를 쓴다. **시연용으로 게시된 Artifact 버전에도 동일한 결함이 있다.**

### 5-5. 이 전송의 성격

| 항목 | 사실 |
|---|---|
| 누가 보내는가 | **이용자 본인**. `mailto:`로 이용자의 메일 앱이 열리고, 이용자가 직접 "보내기"를 누른다 |
| 서비스가 대신 보내는가 | **아니다.** 서버를 경유하지 않는다. 메일 발송 코드·SMTP·API 키가 없다 |
| 서비스가 수신자 주소를 아는가 | **아니다.** 이용자 기기 안에만 있다 |
| ❓ 법적 성격 | 서비스의 "제3자 제공"이 아니라 **이용자 본인의 전송**으로 볼 여지가 크지만, 서비스가 그 표를 자동 생성해 유도한다는 점 때문에 단정할 수 없다. **전문가 검토 필요.** |

**단정할 수 없는 부분과 별개로, 이용자에게는 "이 버튼을 누르면 전 직원의 이메일·전화번호가 본문에 평문으로 들어갑니다"를 화면에서 알려야 한다.**

## 6. 외부 리소스 — 이용자 IP가 제3자에게 가는가

`grep`으로 `src/`와 `presentation/`의 모든 외부 URL을 뽑았다. 결과가 **갈린다.**

### 6-1. Next.js 앱 (`src/`) — 외부 요청 **0건**

| 확인 항목 | 결과 |
|---|---|
| Google Fonts | **없다.** `next/font` 미사용, `globals.css`에 `@import` 없음 |
| 글꼴 처리 | 기기에 있는 것만 쓴다: `"Pretendard", "Apple SD Gothic Neo", "Malgun Gothic", system-ui, sans-serif` (`globals.css:3-6`) |
| CDN·분석 도구·태그매니저 | 없다 |
| 외부 이미지 | 없다. `next.config.ts`의 `remotePatterns: []` — 비어 있다 |
| 사진·영상 | `public/media/`의 로컬 파일만 (`src/lib/mediaProbe.ts:50`) |
| 유일한 외부 URL 문자열 | `.env.example`의 `NEXT_PUBLIC_SITE_URL=http://localhost:3000` — 공유 링크 og 태그용 |

→ **Next.js 앱을 쓰는 동안 이용자 IP가 제3자에게 전달되는 구조는 없다.**

### 6-2. 시연용 단일 파일 버전 — Google로 간다 ⚠️

`presentation/app.html:2-4`, `presentation/프렙노트.html:11-13`:
```html
<link rel="preconnect" href="https://fonts.googleapis.com">
<link rel="preconnect" href="https://fonts.gstatic.com" crossorigin>
<link rel="stylesheet" href="https://fonts.googleapis.com/css2?family=IBM+Plex+Mono:…&family=IBM+Plex+Sans+KR:…">
```

**페이지를 열면 브라우저가 Google 서버에 직접 요청을 보낸다.** 그 요청에 이용자의 **IP 주소, User-Agent, Referer**가 포함된다. 서비스가 보내는 게 아니라 브라우저가 보내므로 서버를 거치지 않고도 전달된다.

**이 파일이 Claude Artifact로 게시된 시연용 버전이다.** 즉 **현재 외부에서 접근 가능한 유일한 버전에 이 전송이 있다.**

| 항목 | 내용 |
|---|---|
| 제3자 | Google LLC (`fonts.googleapis.com`, `fonts.gstatic.com`) |
| 전달되는 것 | IP 주소, User-Agent, Referer (브라우저가 자동 전송) |
| 목적 | 웹폰트(IBM Plex Sans KR / Mono) 로딩 |
| 처리방침 반영 | **필요하다.** 이 버전을 계속 쓰는 한 적어야 한다 |
| 없앨 방법 | 글꼴 파일을 파일 안에 넣거나(base64), Next.js 앱처럼 기기 글꼴만 쓰기 |

❓ **확인 필요:** Claude Artifact 호스팅 자체의 접속 로그·쿠키는 이 저장소 코드로 확인할 수 없다. 게시를 유지한다면 그 플랫폼의 정책을 확인해 처리방침에 반영해야 한다.

## 7. 보관 기간 — "날짜 기반 초기화"는 실제 삭제가 아니다

**이 장이 이번 조사에서 가장 중요한 발견 중 하나다.**

### 7-1. 화면 문구와 코드가 다르다

화면은 이렇게 말한다:
- `ChecklistView.tsx:296` — "체크 상태는 이 휴대폰에만 저장되며 **날짜가 바뀌면 초기화됩니다.**"
- `PrepView.tsx:480` — "체크 상태는 이 기기에만 저장되며 **날짜가 바뀌면 초기화됩니다.**"
- `ChecklistView.tsx:281` — "내일 다시 접속하면 체크리스트가 초기화됩니다."

코드가 하는 일은 다르다. 저장 키에 오늘 날짜가 들어간다:

ChecklistView.tsx:62   sop:{shareSlug}:{todayKey()}
PrepView.tsx:133       prep:{slug}:{todayKey()}

날짜가 바뀌면 **새 키를 읽는다.** 화면이 비어 보이는 이유는 새 키가 비어 있기 때문이다.
**어제 키는 지워지지 않는다.** 삭제 코드가 실행되지 않는다.

→ **결과: 매일 키가 하나씩 늘어나고, 브라우저 저장 공간에 무기한 누적된다.**
→ 처리방침에 "매일 삭제됩니다" / "1일 후 파기" 라고 쓰면 **사실과 다르다.**

### 7-2. 항목별 실제 보관 기간

| 데이터 | 코드상 삭제 시점 | 실제로 지워지는가 |

## 8. 삭제 경로 — 이용자가 자기 데이터를 지울 방법이 화면에 있는가

| 데이터 | 화면에 삭제 방법이 있는가 | 위치 / 동작 |
|---|---|---|
| **직원 1명** (이름·이메일·전화번호 + 그 사람의 배정 전체) | ✅ **있다** | 근무표 표 오른쪽 `×` 버튼 → `"{이름} 님을 명단에서 뺄까요?"` 확인 → `removeStaff()` (`RosterView.tsx:355-366`, `81-85`). `assign`에서도 함께 지운다 (`:82-83`) |

| 직접 추가한 레시피 1건 | ✅ 있다 | `"{이름} 레시피를 삭제할까요?"` 확인 후 삭제 (`LocalRecipeView.tsx:45-55`) |

| 체크리스트 **과거 날짜** | ❌ 없다 | 브라우저 데이터 삭제밖에 없다 |
| **프렙 체크 (오늘·과거 모두)** | ❌ **없다** | 삭제 버튼도, 삭제 코드도 없다. `PrepView.tsx`에 `removeItem` 0건 |
| `sop:sid` (익명 id) | ❌ 없다 | 어느 화면에서도 못 지운다 |
| 서버 `data/events.jsonl` | ❌ 없다 | 이용자용 삭제·열람·정정 경로가 전혀 없다 |
| 전체 데이터 일괄 삭제 | ❌ 없다 | "모든 데이터 지우기" 화면이 없다 |

### 처리방침 작성자에게

정보주체의 열람·정정·삭제 요구권을 처리방침에 적으려면, **위 ❌ 항목들을 어떻게 처리할지 답이 있어야 한다.** 현재는:
- 서버 로그(`events.jsonl`)에 대한 이용자 경로가 **아무것도 없다.**
- 개인정보 본체(`sop:roster`)는 기기에만 있어 **운영자가 직접 지우는 것 외에 방법이 없다.**

지금 구조에서 가장 정직한 서술은 **"개인정보는 서버에 저장되지 않고 이용자 기기에만 있으므로, 삭제는 이용자가 직접 하며 사업자는 대신 삭제할 수단이 없다"** 는 사실을 그대로 쓰는 것이다.
❗ 단, 이 서술은 5장의 메일·클립보드 유출 경로를 **면제해주지 않는다.** 한 번 나간 표는 회수할 수 없다.

## 9. 만 14세 미만 이용자가 있을 수 있는가

### 코드에서 확인된 사실

- **나이를 묻는 화면이 없다.** `Staff` 타입에 나이·생년월일 필드가 없다 (`roster.ts:11-19`).

### 판단

**근로기준법 제64조(최저 연령과 취직인허증)**: 15세 미만인 사람(초·중등교육법상 중학교 재학 중인 18세 미만 포함)은 근로자로 사용할 수 없고, 고용노동부장관이 발급한 취직인허증을 받은 13세 이상 15세 미만은 예외다.
→ 출처: 근로기준법 제64조, 국가법령정보센터 <https://law.go.kr/법령/근로기준법/제64조> / 찾기쉬운 생활법령정보 <https://www.easylaw.go.kr/CSP/CnpClsMain.laf?csmSeq=1381&ccfNo=1&cciNo=1&cnpClsNo=1>

### 그래도 처리방침에 넣어야 하는 것

**개인정보 보호법 제22조의2**: 개인정보처리자는 만 14세 미만 아동의 개인정보를 처리하기 위해 동의를 받아야 할 때 **그 법정대리인의 동의를 받아야 하고, 동의했는지 확인해야 한다.**
→ 출처: 개인정보 보호법 제22조의2, 국가법령정보센터 <https://www.law.go.kr/법령/개인정보보호법> / 찾기쉬운 생활법령정보 <https://easylaw.go.kr/CSP/CnpClsMain.laf?popMenu=ov&csmSeq=659&ccfNo=2&cciNo=1&cnpClsNo=2>

**권고 서술 (이게 사실에 맞다):**
> 이 서비스는 만 14세 미만 아동의 개인정보를 수집하지 않습니다. 서비스는 사업장 근로자의 근무 관리를 목적으로 하며, 만 14세 미만인 사람의 정보를 입력하지 않도록 안내합니다.

**쓰면 안 되는 서술:** "만 14세 미만은 법정대리인의 동의를 받아 가입할 수 있습니다."
→ **가입 기능이 없고 동의 절차도 없다.** 없는 절차를 적는 것은 과다 기재다.

### ❓ 전문가 검토가 필요한 지점

연령 확인 절차가 **없다**는 사실이, 만 14세 미만 정보가 실수로 입력될 경우 처리자의 책임에 어떤 영향을 주는지는 이 문서가 판단할 수 없다.

| 직원 이름 | 필수 (근무표 기능 이용 시) | 운영자가 근무표 화면에 직접 입력 | 이용자 기기 (localStorage `sop:roster`) | 근무표 작성·공유 |
| 직원 소속 섹션 | 선택 | 같음 | 같음 | 근무표 분류 |
| 직원 이메일 | 선택 | 같음 | 같음 | 근무표 메일 발송 대상 지정 |
| 직원 전화번호 | 선택 | 같음 | 같음 | ⚠️ **코드상 이용처가 없다. 필드 삭제를 먼저 검토할 것** |
| 직원별 근무 배정 | 선택 | 근무표 표에서 선택 | 같음 | 근무표 작성·공유 |

**공통 사실 (처리방침에 명시할 것):**
- 서버로 전송되지 않는다. 사업자는 이 정보를 보유하지 않는다.
- 정보주체(직원)가 아니라 **매장 운영자가 입력**한다.
- 회원가입·계정이 없다.

### B. 서버에 수집되는 이용 기록 (개인정보 아님 / ❓ 가명정보 여부 검토)

| 항목 | 내용 |
|---|---|
| 이벤트 종류 | `view`, `survey`, `training_start`, `critical_confirm`, `training_complete`, `prep_view`, `prep_check`, `prep_scale`, `recipe_view`, `recipe_scale` (10종, `survey`는 2개 화면에서 발생) |
| 함께 저장되는 값 | `sessionId`(익명 난수·8종만), `runId`, `positionSlug`, `prepSlug`, `recipeSlug`, `taskId`, `totalTasks`, `confirmedCount`, `durationSec`, `scale`, `recoverable`, `askedSenior`, `mode`, `at`(수집 시각) |
| 수집하지 않는 것 | **IP 주소, User-Agent, Referer, 쿠키, 이름·이메일·전화번호** (코드에 없음) |
| 목적 | 서비스 개선 (교육 소요 시간·선배 문의 횟수 측정) |
| 보관 | ⚠️ **현재 파기 코드가 없다. 방침 작성 전 정해야 한다** |

### C. 제3자 전송 (⚠️ 반드시 고지)

| 대상 | 무엇이 | 어떻게 |
|---|---|---|
| 근무표 메일·카톡 수신자 | **전 직원의 섹션·이름·이메일·전화번호 + 근무 배정** | 이용자가 자기 메일 앱·단톡방으로 직접 전송. 서비스가 본문을 자동 생성 |
| Google LLC | 이용자 **IP·User-Agent·Referer** | 시연용 단일 파일 버전만. 웹폰트 로딩 시 브라우저가 직접 전송 |

### D. 수집하지 않는 것 (오해 방지용 — 명시하면 좋다)

주민등록번호 · 생년월일·나이 · 주소 · 성별 · 계정/비밀번호 · 결제·금융 정보 · 위치 정보 · 사진·영상(이용자 업로드 기능이 **없다**. `public/media/` 파일은 운영자가 서버 파일 시스템에 직접 넣는다 — `mediaProbe.ts`, `ShootBoard.tsx`에 업로드 코드 0건) · 쿠키 · 광고 식별자
