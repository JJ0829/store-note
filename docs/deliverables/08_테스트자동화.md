## 2. 도구 선택

### 2-1. 후보 4개를 실제로 설치해 보고 골랐다

추측이 아니라 `npm install --dry-run`으로 **이 프로젝트에** 넣었을 때의 실측값이다.

| 도구 | 추가 패키지 | 설정 파일 | `.ts` 직접 실행 | 커버리지 | watch |
|---|---|---|---|---|---|
| **`node --test` (채택)** | **0개** | **없음** | ✅ 내장 | ✅ `--experimental-test-coverage` | ✅ |
| tsx (보조 러너) | +3 | 없음 | ✅ | 별도 | ✅ |
| **Vitest** | **+30** | `vitest.config.ts` 필요 | ✅ | ✅ | ✅ |
| **Jest + ts-jest + @types/jest** | **+278** | `jest.config` + transform 설정 | 변환기 경유 | ✅ | ✅ |

> 빈 폴더에 넣으면 Vitest 37개 / Jest 292개다. 위 표는 이 프로젝트의 기존
> 의존성과 겹치는 것을 뺀 **순증**이라 더 작다. 현재 이 프로젝트의 전체 패키지는
> **45개**다(04번 실측). Jest를 고르면 **패키지 수가 7배가 된다.**

### 2-2. `node --test`를 고른 이유 셋

**(1) 이미 있다.** Node 22.18부터 타입 스트리핑이 기본으로 켜져 있어서
`.ts` 파일을 플래그 없이 그대로 실행한다. 이 PC의 Node는 **v24.19.0**이고,
스크래치 폴더에서 실제로 돌려 확인했다.

**(2) 04번 라이선스 감사를 다시 안 해도 된다.** → 10장. 발표 2주 전에
패키지 목록을 갈아엎을 이유가 없다.

**(3) 이 프로젝트의 성격에 맞다.** 런타임 의존성 3개짜리 프로젝트다.
"의존성을 적게 유지한다"는 것이 04번·06번이 계속 근거로 쓰는 성질인데,
테스트 도구로 그걸 스스로 깨는 건 앞뒤가 안 맞는다.

### 2-3. 이 선택의 대가 (숨기지 않는다)

| 제약 | 실제 영향 | 어떻게 했나 |
|---|---|---|
| **`.tsx`를 못 읽는다** | 타입은 벗기지만 JSX는 못 벗긴다. `ERR_UNKNOWN_FILE_EXTENSION` | 계산 함수를 `.ts`로 꺼냈다 (3장). 이건 대가가 아니라 오히려 이득이었다 |
| **`@/` 경로 별칭이 안 먹는다** | Node는 `tsconfig.json`의 `paths`를 안 본다 | 테스트만 `../src/lib/scale.ts` 처럼 상대경로 + 확장자로 쓴다. 앱 코드는 그대로 `@/` |
| **Node 22.18 이상 필요** | 그 아래에서는 `npm test`가 바로 죽는다 | `package.json`에 `"engines": { "node": ">=22.18" }` 명시. CI·매장 PC에도 파급 → 07번 §3-4 |
| **커버리지가 실험적 플래그** | 출력 형식이 바뀔 수 있다 | 품질 게이트로 안 쓴다. 참고용으로만 본다 |

**언제 이 결정을 다시 봐야 하나:** 컴포넌트 렌더링을 자동으로 검사해야 할 때다.
그때는 Vitest + Testing Library가 맞다. 그 시점은 "화면이 더 이상 매주 바뀌지 않을 때"다.
지금은 매주 바뀐다.

## 3. 코드를 옮겼다 — 그리고 화면이 그대로인지 확인했다

### 3-1. 옮기지 않으면 테스트가 물리적으로 불가능했다

`readyAt` / `arrivesIn` / `daysApart` / `triggerLabel` 네 개가
`src/components/PrepView.tsx` 안의 **모듈 전용(비-export) 함수**였다.
컴포넌트 파일은 `.tsx`라서 러너가 파일 자체를 열지 못한다.

이건 도구를 바꿔도 반쯤은 그대로다 — Vitest를 깔면 파일은 읽히지만,
`export`가 없으니 여전히 밖에서 부를 수 없다. **함수를 꺼내는 것이 전제였다.**

### 3-2. 무엇을 어디로

| 새 파일 | 옮긴 것 | 원래 위치 |
|---|---|---|
| `src/lib/leadTime.ts` (108줄) | `WEEKDAY`, `daysApart`, `readyAt`, `arrivesIn`, `triggerLabel` | `PrepView.tsx` 53–120행 |

`PrepView.tsx`는 8행에서 `import { arrivesIn, readyAt, triggerLabel } from "@/lib/leadTime";`
한 줄로 받는다. `git diff --numstat` 기준 **+14 / −73줄**이다
(대부분이 함수 삭제이고, 추가분은 import 1줄 + `arrival` 계산 4줄 + 이동 사유 주석 3줄 + 호출부 정리).

### 3-3. 옮기면서 바꾼 것 — 기준 시각 주입

옮기기만 하면 안 됐다. 원래 `readyAt`과 `arrivesIn`은 **함수 안에서 `new Date()`를 불렀다.**
그대로 두면 테스트가 "오늘이 무슨 요일이냐"에 따라 통과했다 실패했다 한다.
금요일에만 통과하는 테스트는 테스트가 아니다.

```
readyAt(hours)              →  readyAt(hours, now = new Date())
arrivesIn(days)             →  arrivesIn(days, now = new Date())
```

기본값을 뒀으므로 **인자를 안 넘기면 이전과 완전히 같이 동작한다.**
다만 화면 쪽은 이미 `now` 상태를 들고 있어서(서버 렌더에서 시각을 박지 않으려고
클라이언트에서 `setNow(new Date())` 한다) 그걸 그대로 넘기도록 고쳤다.

### 3-4. 덤으로 정리된 것

`arrivesIn`이 **렌더마다 두 번 호출되고 있었다** — 373행에서 라벨용, 377행에서
`overWeekend` 판정용. 각 호출이 별도로 `new Date()`를 만들었다.
지금은 항목 하나당 한 번만 계산해 `arrival` 변수에 담는다 (`PrepView.tsx` 211–214행).

### 3-5. 화면이 안 깨졌는지 확인한 방법

빌드는 하지 않았다(다른 에이전트와 `.next`가 충돌한다 — CLAUDE.md 기록).
대신 셋 다 했다.

**(1) 타입 검사** — `.next`를 안 건드리는 방법으로


## 4. 무엇을 테스트하고 무엇을 안 하는가

### 4-0. 기준: 커버리지가 아니라 "틀리면 누가 손해를 보나"

이 제품에서 계산이 틀렸을 때 생기는 일은 등급이 다르다.

| 등급 | 뜻 | 예 |
|---|---|---|
| **되돌릴 수 없음** | 시간을 되돌려야 하므로 어떤 방법으로도 못 메운다 | 어제 안 걸어둔 콜드브루·반죽·르방 |
| 돈으로 메움 | 쿠팡·다른 거래처로 메운다. 손해는 돈이다 | 우유·부자재 발주 누락 |
| 표시 품질 | 보기 나쁘지만 장사는 된다 | 뱃지 문구, 열 정렬 |

`data/seed.json`의 `recoverable` 필드가 이 구분이고, **1등급에 걸리는 계산부터 테스트했다.**
커버리지 99%는 그 결과로 따라온 숫자지 목표가 아니었다.

### 4-1. 테스트한 것

| 순위 | 대상 | 파일 | 틀렸을 때 |
|---|---|---|---|
| 1 | `arrivesIn` — 발주 도착일, 주말 건너뛰기 | `leadTime.ts:63` | 금요일 발주를 화요일 도착으로 안내 → 월요일 원두 없음 |
| 2 | `readyAt` + `daysApart` — 리드타임 | `leadTime.ts:30, 23` | "내일 06:00"이 틀리면 반죽이 안 나옴. **되돌릴 수 없음** |
| 3 | `scaled` — 배수 환산 | `scale.ts:25` | 반죽 배합이 틀림. 한 판 폐기 |
| 4 | `mondayOf` / `weekDays` / `ymd` | `roster.ts:78, 86, 71` | 근무표가 하루 밀림 → **사람이 안 나온다** |
| 5 | `buildEmailBody` / `bySection` | `roster.ts:125, 99` | 잘못된 근무표 발송 |
| 6 | `loadRoster` 구버전 마이그레이션 | `roster.ts:37` | 이미 입력한 직원 명단이 통째로 사라짐 |
| 7 | 시드 무결성 (slug 참조·중복·파일명) | `repo.ts` + `seed.json` | **9/18 시연 중 링크 404** |
| 8 | `triggerLabel` — 주기 뱃지 | `leadTime.ts:93` | 표시 품질 |
| 9 | `mediaProbe` — 사진·영상 파일명 매칭 | `mediaProbe.ts:47` | 찍어 온 사진이 안 붙는다. 화면은 아무 말도 안 한다 |

**7번(시드 무결성)에 대해 한마디.** 이건 계산 버그가 아니라 데이터 오타를 잡는다.
지금 DB는 `seed.json` 파일 하나이고 화면 연결은 전부 slug 문자열이다. 오타 하나면
홈 화면 버튼이 404로 간다. **9/18 심사 시연 중 그 사고를 막는 유일한 자동 검사다.**

**10번(copyText)에 대해.** 조사 단계에서는 "실제 태블릿에서 한 번 눌러 보는 게 싸다"고
제외 후보였다. 실제로 붙여 보니 **브라우저 환경을 흉내 낼 필요가 없었다** —
이 함수가 쓰는 전역은 `navigator`·`document`·`window` 셋뿐이라 그것만 갈아끼우면
jsdom 없이 세 갈래가 다 재현된다(`tests/copyText.test.ts` 8개). 값이 있는 이유는 따로 있다:
**이 함수의 정상 경로(clipboard API)는 개발자 노트북에서만 돌고, 매장에서 실제로 도는 건
폴백 쪽인데 그쪽이 손으로 확인하기 가장 번거롭다.**

| **성능·부하** | 사용자가 매장 한 곳, 동시 접속 한 자릿수다 |

## 5. 테스트가 실제로 찾아낸 버그

**구분되는 결함은 2건이다. 둘 다 고쳤고, `npm test`가 지금 그것을 지키고 있다.**

> **먼저 분명히 해둔다 — 지금 화면이 틀렸다는 뜻이 아니다.**
> 현재 시드(`data/seed.json`) 실측: 재료 수량 13개와 레시피 `yield` 4개
> (`americano` 1 / `cafe-latte` 1 / `cold-brew` 2000 / `shokupan` 6)가 **전부 정수**다.
> `scaled()` 호출부는 `PrepView.tsx:379,400`과 `RecipeDetail.tsx:106,136` **네 곳뿐**이고
> 모두 이 정수들만 받는다. 이 10개 값 × 화면 버튼 5개(`SCALES = [0.5, 1, 1.5, 2, 3]`)
> **50가지 조합을 수정 전·후 구현으로 전부 돌려본 결과 출력이 다른 경우는 0건**이었다.
> `leadTimeDays`가 있는 프렙 항목도 `p-5`=1, `p-6`=4 둘뿐이라 `arrivesIn(0)`은
> 애초에 호출되지 않는다.
>
> 즉 **둘 다 "지금 눈에 보이는 오작동"이 아니라 "입력이 한 칸 넓어지면 바로 나오는 오작동"**이다.
> 그 입력 경로는 이미 열려 있다 — `RecipeForm.tsx:226`의 재료 양 입력칸은
> `type="number" inputMode="decimal"`이라 소수를 그대로 받는다.
> (당일배송 리드타임 쪽은 아직 입력 화면이 없어 `data/seed.json`을 고쳐야 들어간다.)

### 5-1. 증거 — 수정 전 코드에는 이 단언들이 실패한다

수정 전 함수 본문을 그대로 복사해 같은 단언을 돌린 결과다.

```
FAIL  scale: 1배 항등성 (2.55)       기대 "2.55"  / 실제 "2.5"
FAIL  scale: 1배 항등성 (0.35)       기대 "0.35"  / 실제 "0.3"
FAIL  scale: 0.5배 7.5g              기대 "3.75"  / 실제 "3.8"
FAIL  scale: 부동소수 0.35x3         기대 "1.05"  / 실제 "1.0"
FAIL  scale: NaN 방어                기대 "0"     / 실제 "NaN"
FAIL  arrivesIn: 당일배송 토요일      기대 "9/7(월)" / 실제 "9/5(토)"
FAIL  arrivesIn: 당일배송 일요일      기대 "9/7(월)" / 실제 "9/6(일)"
PASS  arrivesIn: 음수 방어            기대 "9/2(수)" / 실제 "9/2(수)"

수정 전 구현으로 실패하는 단언: 7 / 8
```

마지막 한 줄은 정직하게 적어둔다 — **음수 방어는 원래 코드에서도 우연히 통과했다.**
`while (-3 > 0)`이 아예 안 돌기 때문이다. 버그가 아니라 그냥 테스트가 없던 자리였다.

### 5-2. 버그 1 — `scaled()`가 1배에서도 숫자를 바꿨다 (`src/lib/scale.ts`)

**수정 전**

```ts
const v = amount * scale;
return Number.isInteger(v) ? String(v) : v.toFixed(1);
```

소수는 무조건 소수점 한 자리로 잘렸다.

| 입력 | 수정 전 | 문제 |
|---|---|---|
| `scaled(2.55, 1)` | `"2.5"` | **1배인데 입력값과 다른 값이 뜬다** |
| `scaled(0.35, 1)` | `"0.3"` | 부동소수 표현 때문에 내림 |
| `scaled(7.5, 0.5)` | `"3.8"` | 3.75여야 한다. 0.05g이 사라진다 |
| `scaled(NaN, 2)` | `"NaN"` | 화면에 `NaN g`이 그대로 뜬다 |

**왜 지금까지 안 터졌나.** 현재 시드(`data/seed.json`)의 재료 수량이 전부 정수라서다.
그런데 `src/components/RecipeForm.tsx`가 `amount: Number(i.amount) || 0`으로
**사장님이 직접 입력한 값을 그대로 받는다.** 소금 2.5g, 이스트 1.8g을 넣는 순간부터
화면 숫자가 입력값과 달라진다. **베이커리에서 소수점 g은 예외가 아니라 기본이다.**

**수정 후** (`src/lib/scale.ts:25`)

```ts
const v = amount * scale;
if (!Number.isFinite(v)) return "0";
// 1.275 * 100 은 127.49999999999999라서 그냥 반올림하면 1.27이 된다
const cents = Number((v * 100).toPrecision(12));
return String(Math.round(cents) / 100);
```

규칙 둘: **① 1배는 입력값 그대로 ② 부동소수 찌꺼기는 지운다.**
저울이 읽는 단위가 0.1g이므로 소수 둘째 자리에서 반올림하고 불필요한 0은 안 붙인다.

**화면에 미치는 영향:** 현재 시드는 전부 정수라 **표시가 하나도 안 바뀐다**(3-5절에서 확인).
바뀌는 건 앞으로 사장님이 소수를 입력했을 때다.

### 5-3. 버그 2 — `arrivesIn(0)`이 주말에 도착한다고 했다

**수정 전** (`PrepView.tsx` 87–103행, 지금은 `leadTime.ts`)

```ts
while (left > 0) { ... }   // days === 0 이면 루프가 아예 안 돈다
```

주말 배송이 없다는 게 이 함수의 존재 이유인데, **0일 입력에서만 그 규칙이 통째로 빠졌다.**
토요일에 `arrivesIn(0)` → `"9/5(토)"`, `overWeekend: false`.

지금 시드에 `leadTimeDays: 0`은 없다(`p-5`=1, `p-6`=4). 그러나 사장님이
"당일배송 거래처"를 넣는 순간 나온다. 그리고 그건 **주말에 발주하면서 확인하게 된다.**

**수정 후** (`src/lib/leadTime.ts:63`) — 마지막에 주말 밀어내기를 한 번 더 돌린다.

```ts
// 0일(당일배송)이어도 토·일에는 오지 않는다
while (isWeekend(d)) { d.setDate(d.getDate() + 1); skipped += 1; }
```

`days > 0`일 때는 앞 루프가 이미 평일에서 끝나므로 이 루프는 아무 일도 안 한다.
기존 동작은 그대로다(테스트 12–16번이 그걸 지킨다).

### 5-4. 덧붙여 넣은 입력 방어 (5-2·5-3의 하위 항목)

**이건 세 번째 버그가 아니다.** 위 두 건을 고치면서 같은 함수에 함께 넣은 방어라
번호를 따로 주지 않는다.

`arrivesIn`은 `Math.max(0, Math.round(days))`, `scaled`는 `Number.isFinite` 검사를 넣었다.
5-1의 실측대로 **음수는 원래 코드에서도 사고가 안 났다**(`while (-3 > 0)`이 아예 안 돈다).
버그가 아니라 테스트가 없던 자리다. `NaN`은 새어 나갔지만 그건 별개 결함이 아니라
5-2 표의 네 번째 행과 같은 항목이다.

## 5-A. 2026-09-04 — 운영 기능에서 테스트가 잡은 것

### 5-A-1. ★ 아메리카노 원두가 두 번 계산되는 길이 있었다

**이게 이번에 가장 값어치 있는 발견이다.** 그리고 **테스트를 쓰기 전에는 몰랐다.**

`data/seed.json`의 아메리카노에는 재료가 셋이다.

```
원두 (도징)  18 g   ← 산다
추출량       36 g   ← 사는 게 아니다. 원두 18g에서 나온 결과다
물          200 ml  ← 수돗물
```

거래처 화면은 **"레시피에는 있는데 단가가 없는 재료"를 먼저 띄워 채우라고 권한다.**
그 목록에 `추출량`이 들어갔다. 사장님이 권유대로 채우면:

| | 원가 |
|---|---|
| 원두 18g만 (맞는 값) | **504원** |
| + 추출량 36g까지 (권유대로 채운 결과) | **1,512원** |

원가율이 3배가 되고, 그 숫자로 판매가를 정한다.

**테스트로 못 박은 방식** — 고친 동작만 검사하면 왜 그렇게 했는지가 사라진다.
그래서 **틀린 동작도 함께 테스트에 남겼다.**

```
★ 제외한 재료는 0원으로 세고 missing에 넣지 않는다
★ 제외하지 않으면 원두가 두 번 계산된다 (제외가 필요한 이유)
   → costOfRecipe(r, items).total          === 1512
   → costOfRecipe(r, items, ["추출량"]).total === 504
```

두 번째 테스트는 **버그를 검사하는 것이 아니라 그 버그가 왜 생기는지를 기록한다.**
나중에 누가 `excluded`를 지우려 하면 이 테스트가 이유를 말해준다.

> ⚠️ **이건 우회로다.** 근본 해법은 `Ingredient`에 "구매 대상인가 / 계산 결과인가"
> 판별 칸을 두는 것이다(`PrepTask.kind`처럼). → `03_ERD.md` 3-21절. **미결정.**

### 5-A-2. 단일 파일 이식에서 잡은 것 2건 — 테스트가 아니라 브라우저가 잡았다

정직하게 적어둔다. **이 둘은 `node --test`가 못 잡는 종류였다.**

| 무엇 | 왜 테스트가 못 잡나 |
|---|---|
| `prices[r.id]` — 단일 파일 시드에 `id`가 없어 **네 메뉴가 판매가 한 칸을 공유**했다 | 테스트는 `src/lib/`의 순수 함수를 본다. 단일 파일 HTML은 대상이 아니다 |
| `t.kind === "order"` — 단일 파일 시드에 `kind`가 없어 **발주 목록이 통째로 비었다** | 같음 |

**→ §11에 "단일 파일 HTML은 테스트 대상 밖이다"를 추가했다.** 지금 방어 수단은
`node --check`(문법)와 브라우저에서 렌더 함수를 직접 호출해보는 것뿐이다.

### 5-A-3. 문서를 쓰다가 잡은 것 1건

`ownerGate.ts`의 `lock()`이 **아무 데서도 호출되지 않았다.** 수동으로 잠글 방법이 없어
한 번 열면 브라우저를 닫을 때까지 열린 채였다. 매장 태블릿은 하루 종일 켜져 있다.

**테스트로는 못 잡는다** — 함수가 정상 동작하고, 안 부르는 것이 결함이다.
"내보내지만 아무도 안 쓰는 함수"를 찾는 검사가 있으면 잡힌다(§11 #10).

## 6. 경계값을 어떻게 골랐나

무작위 값이 아니다. **달력이 실제로 이상하게 구는 지점**과 **주방에서 실제로 나오는 값**만 골랐다.

### 6-1. 날짜 — "빼기가 안 되는 곳"

| 경계 | 왜 | 실제 테스트 |
|---|---|---|
| **월말** 8/31 → 9/1 | 날짜를 그냥 빼면 −30이 나온다 | `daysApart`, `readyAt(16)`, `mondayOf` |
| **연말** 12/31 → 1/1 | 연도까지 바뀐다 | `daysApart`, `readyAt(15)`, `arrivesIn(1)`, `weekDays` |
| **윤년** 2028-02-28 → 02-29 | 4년에 한 번 | `daysApart` |
| **자정 넘김** 23:45 + 0.5h | 30분인데 "내일"이 된다 | `readyAt(0.5)` |
| **23:59 발주** | 시각이 섞이면 `setDate` 반복에서 오차가 난다 | `arrivesIn` |
| **정확히 24h / 48h** | "오늘/내일/모레"가 갈리는 지점 | `readyAt` |
| **72h(3일)** | 이 지점부터 요일 대신 날짜로 바뀐다 | `readyAt` |
| **일요일 입력** | `mondayOf`가 6일을 거슬러야 한다. `day - 1`로 쓰면 토요일이 나온다 | `mondayOf` |

기준 날짜는 **2026-09-04(금)** 주간으로 통일했다. 발표(9/18)와 같은 달이고,
그 주가 월말(8/31 월요일 시작)을 물고 있어서 월말 경계를 공짜로 얻는다.

### 6-2. 주말 건너뛰기 — 요일별로 전부

| 발주 요일 | 리드타임 | 기대 | 왜 이 조합인가 |
|---|---|---|---|
| 월 8/31 | 1일 | 9/1(화), 주말 없음 | 정상 경로 |
| 금 9/4 | 1일 | 9/7(월), 주말 넘김 | **실제 시드의 발주 요일**(`weekday: [1,2,3,4,5]`) |
| 토 9/5 | 1일 | 9/7(월) | 주말에 발주하는 경우 |
| 화 9/1 | 4일 | 9/7(월) | **시드 `p-6`(원두)의 실제 리드타임 4일** |
| 목 12/31 | 1일 | 1/1(금) | 연말 + 주말 없음 |
| 토 9/5 | **0일** | 9/7(월) | 버그가 있던 지점 |
| 수 9/2 | 0일 | 9/2(수) | 0일이 평일이면 오늘이 맞다 |
| 수 9/2 | −3일 | 9/2(수) | 잘못된 데이터 방어 |

### 6-3. 배수 — 화면 버튼 5개 × 실제 재료값

`SCALES = [0.5, 1, 1.5, 2, 3]`이 화면 버튼이므로 그 5개만 쓴다. 곱할 값은:

| 값 | 출처 |
|---|---|
| 2000 | 콜드브루 물 2000ml, 식빵 강력분 2000g (시드) |
| 18, 40, 120 | 소금 40g, 설탕 120g (시드) |
| **7.5, 2.55, 0.35, 1.05** | 사장님이 입력할 법한 소수. **버그가 여기 있었다** |
| 0 | `RecipeForm`의 `Number(x) \|\| 0` 폴백 |
| NaN, Infinity | 입력 칸에 이상한 게 들어왔을 때 |

**1배 항등성**을 따로 테스트로 뺀 이유: 이건 계산이 아니라 **약속**이다.
아무것도 안 눌렀는데 숫자가 바뀌면 사람은 화면을 안 믿는다.

### 6-4. 주기 뱃지 — 단위가 바뀌는 지점

`29 / 30`(일↔개월)과 `364 / 365`(개월↔년)를 양쪽에서 찍었고,
시드에 실제로 있는 `7 / 30 / 90 / 120 / 180 / 365`도 전부 넣었다.
`730`(2년)은 지금 `"1년마다"`로 뭉치는데, **알려진 한계로 테스트에 명시**해 두었다.
2년 주기 항목이 생기면 그 테스트가 실패하면서 고치라고 알려준다.

### 6-5. 파일명 매칭 — 헷갈릴 수 있는 조합

| 경계 | 왜 |
|---|---|
| `p-1-good.jpg` vs `p-1-good.png` 동시 존재 | 우선순위가 정의대로인지 (jpg → jpeg → png → webp) |
| `p-1` 요청에 `p-10-good.jpg`만 있음 | **접두사 매칭이면 여기서 다른 업무 사진이 붙는다** |

## 8. 실행 방법

### 8-1. 명령 셋

```bash
npm test          # 전부 한 번 실행          (약 2초)
npm run test:watch # 파일이 바뀌면 다시 실행   (개발 중)
npm run test:cov  # 커버리지까지
npm run typecheck # 타입 검사 (tsc --noEmit) — .next를 안 건드린다
```

`package.json`의 실제 내용:

```json
"typecheck": "tsc --noEmit",
"test":      "node --disable-warning=MODULE_TYPELESS_PACKAGE_JSON --test",
"test:watch":"node --disable-warning=MODULE_TYPELESS_PACKAGE_JSON --test --watch",
"test:cov":  "node --disable-warning=MODULE_TYPELESS_PACKAGE_JSON --test --experimental-test-coverage"
```

**`--disable-warning=...`이 붙은 이유:** 이 프로젝트의 `package.json`에는
`"type": "module"`이 없다(Next 기본값). 그래서 `.ts` 테스트를 돌릴 때마다
Node가 "모듈 형식이 명시되지 않았다"는 경고를 파일마다 찍는다. 기능에는 영향이 없고
경고 하나만 끈다. `"type": "module"`을 넣는 쪽은 Next 설정 파일들에 파급이 커서 안 했다.

**파일 경로를 안 적은 이유:** `node --test`는 인자가 없으면 프로젝트 루트에서
`*.test.ts` 같은 이름을 재귀로 찾고 `node_modules`는 건너뛴다. 경로를 박아두면
나중에 `src/` 아래 테스트를 추가했을 때 **조용히 안 돌아간다.** 그게 더 위험하다.

> **다만 이 선택은 스스로를 지키지 못한다.** 경로를 안 박아도, 탐색이 어긋나면
> `node --test`는 **0개를 실행하고 종료 코드 0을 낸다**(실측 → 14장). 로컬에서는
> `ℹ tests 97` 줄을 눈으로 보면 되지만 CI는 아무도 안 본다.
> **그래서 개수 가드는 CI 스텝 쪽에 넣었다 → 9-0절.**

## 9. CI에 넣는 법 (07번 §5-3과 연결)

07번이 `.github/workflows/check.yml` 초안을 이미 써 두었고, **테스트 두 줄이 주석 처리된 채**
이 문서를 기다리고 있다. `tests/`가 커밋되면 주석만 풀면 된다.

```diff
       - name: 타입 검사
-        run: npx tsc --noEmit
+        run: npm run typecheck

-      # - name: 테스트
-      #   run: npm test
+      - name: 테스트
+        shell: bash
+        run: |
+          set -o pipefail
+          npm test 2>&1 | tee test.log
+          grep -qE 'tests [1-9]' test.log \
+            || { echo "::error::테스트가 0개 실행됐다"; exit 1; }

       - name: 빌드
         run: npm run build
```

**테스트를 빌드보다 앞에 두는 이유:** 2초 만에 끝나고, 실패했을 때 원인 범위가 훨씬 좁다.

### 9-0. `run: npm test` 한 줄로 두면 안 되는 이유 — **0개 실행도 초록불이다**

`node --test`는 **테스트 파일을 하나도 못 찾아도 종료 코드가 0이다.** 빈 폴더 실측:

```
> node --test
ℹ tests 0
ℹ pass 0
ℹ fail 0
EXIT=0
```

그래서 8-1절이 걱정한 "조용히 안 돌아가는" 상황의 증상은 **빨간불이 아니라
`초록불 + 0개 실행`**이다. `npm test`만 걸어두면 정상 통과와 구분이 되지 않는다.
위 스텝의 세 줄이 각각 그걸 막는다.

| 줄 | 막는 것 | 실측 |
|---|---|---|
| `grep -qE 'tests [1-9]'` | 0개 실행(조용한 실패) | 빈 폴더 → `grep` 종료 1 ✅ / 저장소 → 0 ✅ |
| `set -o pipefail` | **파이프가 실패를 삼키는 것** | 없으면 실제 실패도 종료 0 ❌ / 있으면 1 ✅ |
| `shell: bash` | GitHub 기본 셸에는 `pipefail`이 없다 | — |

**`set -o pipefail`이 특히 중요하다.** `npm test | tee test.log`의 종료 코드는 기본적으로
**`tee`의 것**이다. 이걸 빼면 개수 가드를 붙이느라 **오히려 진짜 테스트 실패가 초록불로 넘어간다.**
실측으로 확인했다 — 일부러 실패하는 테스트를 넣고 돌렸을 때
`pipefail` 없이는 종료 코드 `0`, 넣으면 `1`이었다.

**`^`로 줄머리를 고정하지 않은 이유:** 요약 줄은 `ℹ tests 97`인데 `ℹ`가 **3바이트**
(`E2 84 B9`)다. CI 로케일에 따라 `^. tests`의 `.`이 한 바이트만 먹어서 **매칭이 통째로
빗나간다**(실측: `grep -cE '^. tests [1-9]'` → 0, `grep -cE 'tests [1-9]'` → 1).
현재 테스트 이름 중에 `tests <숫자>`를 포함한 것은 없어서 오탐도 없다(실측 0건).

> **경로를 박는 방법(`node --test tests/`)은 이 Node에서 안 된다 — 검토했고 버렸다.**
> 위치 인자가 **디렉터리 탐색이 아니라 글롭**으로 처리되기 때문이다
> (어느 버전부터 그런지는 확인하지 않았다. 아래는 v24.19.0 실측이다).
> `node --test tests/`는 `tests/`를 모듈로 읽으려다
> `Error: Cannot find module ...\tests`로 죽는다 — `tests/` 안에 파일 6개가
> 멀쩡히 있는데도 **실제로 돈 테스트는 0개**다. 글롭을 제대로 써서
> `node --test "tests/**/*.test.ts"`로 하면 97개가 돌지만, 이번엔
> **아무것도 매칭 안 되는 글롭이 종료 코드 0**이라(`"nope/**/*.test.ts"` → EXIT 0)
> 원래 막으려던 조용한 실패가 그대로 돌아온다. 그래서 경로 고정이 아니라 **개수 가드**를 쓴다.

### 9-1. `node-version`에 대한 주의 (07번에 넘기는 사항)

07번 초안은 `node-version: "22"`다. `engines`가 `>=22.18`이므로 논리적으로는 맞다.
다만 **이 문서가 실제로 확인한 것은 v24.19.0 하나뿐이다.** Node 22에서
타입 스트리핑·`--disable-warning`·`--experimental-test-coverage`가 전부 같은 형태로
도는지는 **검증하지 않았다.**

> **권장:** CI를 `node-version: "24"`로 두는 것이 안전하다. 개발 PC가 24이고,
> 실측이 24에서만 이뤄졌다. **"engines가 22.18이니 22로 돌린다"는 추론만으로 두면 안 된다.**

**22로 내릴 때의 수용 기준 — "초록불"이 아니라 "`ℹ tests 97`이 찍히는가"다.**

이 절이 걱정하는 실패 방식이 정확히 **초록불로 위장하는 종류**이기 때문이다.
Node 22의 기본 글롭이 `.ts`를 안 잡으면 증상은 빨간불이 아니라 `tests 0` + 종료 코드 0이고,
초록불만 보는 기준으로는 **정상 통과와 구분이 안 된다.** 그래서:

| | 기준 |
|---|---|
| ❌ 이것으로는 부족 | CI에서 `npm test`가 초록불 |
| ✅ 이것을 확인 | CI 로그에 **`ℹ tests 97`**(현재 개수)이 실제로 찍히고, `fail 0` |

9-0절의 개수 가드를 넣어두면 이 확인이 자동으로 이뤄진다 — 22에서 0개가 돌면
`grep`이 걸어서 **빨간불로 바뀐다.** 개수 가드 없이 `node-version`을 내리는 것이 가장 위험하다.

### 9-2. CI 없이 지금 할 수 있는 것

원격 저장소가 아직 없다(07번 §4-1). 그때까지는 커밋 전에 손으로 두 줄이면 된다.

```bash
npm run typecheck && npm test
```
