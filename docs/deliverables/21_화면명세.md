### 두 숫자가 다른 것은 일부러다 — 헷갈리지 말 것

- **`전체`** 는 `list.tasks.length` 다. 시드에 든 줄 수.
- **`화면에 세는 수`** 는 `repo.countedTasks()` 다. **옵션과 묶음 머리를 뺀다.**
  르방을 안 쓰는 매장에서 `9/10` 이 영영 안 채워지면 아무도 진행률을 안 본다.
- **빨간 안내(되돌릴 수 없음)는 옵션까지 센다.** 르방을 *쓰는* 매장에서
  "다 했습니다" 가 거짓이 되면 안 되기 때문이다. → CLAUDE.md `optionOf` / `optional`

✅ **촬영에서 묶음 머리 3개를 뺐다 (2026-09-12).** 전에는 `/shoot` 이 `l.tasks` 를
그대로 돌아서 `기계 · 설비 점검` 같은 **이름표를 찍을 것으로 셌다.**
지금은 `repo.filmableTasks()` 를 쓴다 → 할 일에서 **24**.
★ **합계 91 은 안 바뀌었다** — 중간 점검 6개가 프렙에서 포지션으로 옮겨갔을 뿐
둘 다 촬영 대상이기 때문이다.

**촬영은 옵션을 센다 — 진행률과 분모가 또 다르고, 이것도 일부러다.**

| | 옵션 (`optional`) | 묶음 머리 |
|---|---|---|
| 진행률 `countedTasks` | ⛔ 뺀다 | ⛔ 뺀다 |
| 빨간 안내 (되돌릴 수 없음) | ✅ 센다 | ⛔ 뺀다 |
| **촬영 `filmableTasks`** | ✅ **센다** | ⛔ 뺀다 |

르방 갱신은 **실제로 찍을 수 있는 일**이고, 르방을 쓰는 매장에서는 오히려
**기준이 가장 안 맞는 항목**이다(`day-flow` 의 1순위 4개 중 하나).
진행률에서 뺐던 건 *안 하는 매장의 분모* 때문이지 찍을 값어치가 없어서가 아니다.

## 2. 상태 정의 — 모든 화면이 이 여섯 중에서만 고른다

화면마다 다른 말을 쓰면 만드는 사람도 쓰는 사람도 헷갈린다. 여섯으로 고정한다.

| 상태 | 언제 | 무엇을 보여주나 | 코드 표식 |
|---|---|---|---|
| **L 로딩** | `localStorage` 를 아직 못 읽음 (SSR → 클라이언트 사이) | 회색 네모 (`animate-pulse`) | `if (!now \|\| !data) return <skeleton>` |
| **N 정상** | 데이터가 있다 | 본문 | — |
| **Z 비었음** | 데이터가 0건 | **다음에 뭘 할지 알려주는 문장 + 버튼** | `<Empty>` |
| **X 오류** | 저장 실패 · 형식이 안 맞음 | 빨간 글, `role="alert"` | `role="alert"` |
| **G 잠김** | PIN 안 풀림 | PIN 입력칸만 | `OwnerGate` / `StoreGate` |
| **C 주의** | 정상인데 **믿으면 안 되는 값** | 회색 작은 글 | `<Caveat>` |

**C(주의)가 이 제품에 특히 많은 이유:** 인건비는 추정이고(4대보험·소득세 없음),
원가는 단가를 못 구한 재료가 있으면 낮게 나온다. **숫자를 보여주되 그 숫자를
얼마나 믿어도 되는지 같이 보여준다.** 이게 없으면 사장님이 틀린 숫자로 가격을 정한다.

⚠️ **자정을 넘는 조가 있으면 `shiftClock.isOnDuty()` 로 판정해야 한다.**
평소 마감조는 22:30 에 끝나지만 **01:00 퇴근이 예외로 있다.** 그날 근무조를
`14:30~01:00` 으로 잡으면 옛 판정(`cur >= start && cur < end`)에서 **통째로 사라진다.**

### S-04 `/prep/[slug]` 프렙 — 제품이 종이를 이긴다고 주장하는 화면

| | |
|---|---|
| 목적 | **오늘 안 하면 내일 아침에 터지는 것**을 오늘 눈에 보이게 한다 |
| 진입 | S-01 프렙 행 3개 / 근무조 `focus` |
| 데이터 | `seed.prepLists` (서버) + 체크 상태 `prep:{slug}:{영업일}` |
| 날짜 | **`businessDay()`** — 자정이 아니라 새벽 4시에 바뀐다 |
| 경로 | `/prep/midday` · `/prep/afternoon` · `/prep/cycle` (3개, 정적 생성) |

**화면 순서 — 위에서 아래가 곧 중요도다**

1. 진행률 막대 + `n/전체`
2. 🔴 **`recoverable:false` 안내** — "까먹지 말고 해야 할 것 n개". 다 하면 초록으로 바뀐다
3. 목록 안내문 (`list.note`)
4. 항목 카드들

**항목 카드 안에서 조건부로 뜨는 것**

| 조건 | 표시 |
|---|---|
| `critical` | 🏷 `꼭 지키기` |
| `quantityVaries` | 🏷 `수량 매일 다름` ← **종이로 못 하는 이유** |
| `!recoverable` | 카드에 빨간 테두리 |
| `leadTimeHours !== null` | `지금 시작하면 → 내일 07:43 부터 사용 가능 (16시간)` |
| `leadTimeDays !== null` | `오늘 주문 → 목요일 도착 (주말 배송 없음)` |
| `recipeSlug !== null` | **레시피 전체** — 배수 계산기 + **만드는 순서**. 27개 중 **8건**. 옵션 안에서도 뜬다 |
| `kind === "routine"` | **리드타임 줄이 아예 안 뜬다** ← 없는 약속을 만들지 않기 위해 |
| `optionOf !== null` | **독립 카드가 아니라 부모 카드 안**에 그려진다 |
| 자식이 `optional:false` | 그 카드는 **「묶음 머리」** — 누를 수 없고 분모에도 안 들어간다 |

**두 숫자의 분모가 다르다 — 일부러다 (2026-09-09)**

| 숫자 | 무엇을 세나 | 옵션(`optionOf`)을 |
|---|---|---|
| `n/전체` · 진행률 막대 | 오늘 이 목록에서 할 일 | ⛔ **뺀다** |
| 「까먹지 말고 해야 할 것 n개」 | `recoverable:false` 인 것 | ✅ **센다** |

**왜 나눴나.** 매장마다 하거나 안 하는 일이 있다 — 사워도우를 안 하는 카페에
르방은 뜻이 없다. 그게 분모에 들어가면 **`9/10` 이 영영 안 채워지고 진행률이
거짓이 된다.** 그러면 사람은 곧 진행률을 안 본다.

**그리고 옵션은 흩어놓지 않는다** (사장님 지적: *"따로말고 한곳에 모아서 해줘"*).
바에서 만드는 부재료 다섯은 **`바 부재료 점검 · 제조` 한 카드**에 모여 있다.
그래서 오후 프렙은 **카드 6개 + 옵션 6개**다 — 카드 12개가 아니다.
(2026-09-18 에 `우유·식자재 발주` 를 **우유 / 식자재** 둘로 쪼갰다 — 사장님 지적. 거래처가 다르면 주문하는 곳도 마감 시각도 다르다.)

### 주기 점검도 같은 방식으로 묶었다 (2026-09-08 요청)

13개가 한 줄로 늘어서 있어서, 저울 영점(**7일**)과 소화기 점검(**1년**)이 나란히
있었다. 세 묶음으로 나누고 **묶음 안은 주기가 짧은 것부터** 세웠다.

| 묶음 (누를 수 없다) | 안에 든 것 |
|---|---|
| **기계 · 설비 점검** | 저울 영점 7일 · 정수 필터 4개월 · 개스킷 6개월 · 그라인더 날 6개월 · 냉장 가스켓 6개월 · 머신 정기점검 1년 |
| **안 보이는 곳 청소** | 배수구·트렌치 7일 · 제빙기 1개월 · 방충·방역 1개월 · 후드·덕트 3개월 🔴 |
| **서류 · 법정** | 보건증 1년 · 소화기·소방 1년 · 위생교육 1년 |

**진행률은 `n/13` 이다 — 16이 아니다.** 묶음 머리는 할 일이 아니라 이름표라서
누를 수 없고 분모에도 안 들어간다. 부모까지 세면 같은 일을 두 번 센다.

**그리고 이건 옵션이 아니다.** 주기 점검에 *"매장에 따라 안 하기도 합니다"* 를
붙이면 거짓이다 — 보건증·소방·위생교육은 안 하면 과태료다. 그래서 같은 자리에
`이 묶음의 항목 n개` 를 쓴다. (`tests/seed.test.ts` 가 `optional: false` 를 못 박는다)

### 오후 프렙

| 카드 | 옵션 |

| 내일용 콜드브루 시작하기 🔴 | — |

실측: 오후 프렙에서 옵션을 체크하면 `0/9` 는 그대로, 안내는 `7개 → 6개`.

### 프렙 안에 레시피가 통째로 들어왔다 (2026-09-10)

사장님 요청: *"프렙이랑 레시피랑 같이 있어야 하는데 합쳐줘."*

전에는 프렙에 **재료와 배수만** 있었다. 만드는 순서를 보려면 `/r/{slug}` 로
나가야 했고, **그 화면은 매장 PIN 이 걸려 있다.** 주방에서 크림폼을 올리다 말고
화면을 나갔다가, 번호를 넣고, 다시 프렙으로 돌아와 체크해야 했다.
**젖은 손으로 네 번이다.** 재료와 순서는 한 몸인데 나눠 놨던 것이다.

- `만드는 순서 n단계 ▾` 를 누르면 그 자리에서 펼쳐진다 (기본은 접힘)
- 접어 두는 이유: 오후 프렙에만 레시피 붙은 항목이 여덟이다. 전부 펼치면
  목록을 못 훑는다. **한 번 누르는 것과 화면을 옮기는 것은 다르다** —
  번호도 안 묻고 보던 자리를 잃지도 않는다
- 사진 자리는 레시피 화면과 **같은 id**(`step.id`)를 쓴다. 한 번 찍어 넣으면 두 화면에 뜬다

✅ **그래서 `/prep/` 도 게이트 뒤로 들어갔다 (2026-09-10).** 레시피가 프렙 안으로
들어오면서 재료·중량뿐 아니라 **만드는 순서까지** 거기 있게 됐는데, `/prep/` 은
잠금이 없었다. 당시 이 자리에는 *"매장 PIN 이 더 얇아졌다"* 고 적혀 있었다.

같은 날 두 가지가 같이 해결됐다 — `ServerStoreGate` 가 `/prep` · `/prep/[slug]` 에도
붙었고(§4), 그 게이트가 **서버에서** 막으므로 *"잠긴 상태에서도 페이지 소스에
재료가 있다"* 는 조건 자체가 사라졌다. `tests/builtPages.test.ts` 의 라우트 목록
주석이 `/prep/[slug]` 를 **"2026-09-10 에 빠져 있던 곳"** 이라고 적어둔 것이 이것이다.

⚠️ 단 `STORE_PIN` 을 안 넣고 배포하면 막지 않는다 — §4 의 세 단서를 볼 것.

**화면이 하는 약속:** *"체크 상태는 이 기기에만 저장되며 영업일이 바뀌면
초기화됩니다. 하루의 경계는 새벽 4시입니다."* — 이 문장이 참이 되도록
`pruneDayKeys` 가 지난 날짜 키를 실제로 지운다. **약속만 하고 안 지우던 버그였다.**

## 4-b. 이동 규칙 — 홈으로 가는 길 ⚠️ **오늘 정함**

| 장치 | 어디에 | 동작 |
|---|---|---|
| `‹ 뒤로` | `Screen` 을 쓰는 **모든 화면** | `history.length > 1` 이면 `router.back()`, 아니면 `/` 로 |
| `처음으로` | ⚠️ **`/r` · 프렙 · 교육 모드 3곳뿐** | `/` 로 |
| 하단 탭바 | ✅ **두 앱 모두** (2026-09-10). `오늘 · 프렙 · 발주 · 출퇴근 · 운영` | 교육 모드·체크리스트에서는 안 그린다 |

**왜 이게 문제인가:** 매장 태블릿은 **전체화면 키오스크라 주소창이 없는 경우가 많다**
(`BackButton.tsx` 주석에 이미 적혀 있다). 그 상태에서 `/attendance` → `/sales` 처럼
두세 번 들어가면 **`‹ 뒤로` 를 그만큼 눌러야 나온다.**

**기준: 하단 탭바를 표준으로 삼는다.** → ✅ **2026-09-10 두 앱 모두 구현.**

★ **탭은 매일 누르는 것만 둔다.** 옛 6칸(`오늘·프렙·레시피·근무표·교육·운영`)은
근무표(주 1회)·교육(신입 올 때만)이 탭에 있고 **하루 두 번 찍는 출퇴근과
매일 아침 여는 발주가 탭에 없었다.** 매일 누르는 게 탭에 없고 한 달에 한 번
쓰는 게 탭에 있었던 것이다 (CLAUDE.md — *"매일 열리는 이유를 늘리는지 먼저 따질 것"*).

| 탭 | 경로 | 켜지는 하위 화면 |
|---|---|---|
| 오늘 | `/` | — |
| **프렙** | `/prep` | `/prep/*` · `/r/*` |
| 발주 | `/order` | — |
| 출퇴근 | `/attendance` | — |
| 운영 | `/sales` | `/cost` · `/vendors` · `/contracts` · `/roster` · `/backup` |

**프렙과 레시피를 `프렙` 탭 하나로 합쳤다** (사장님 지적: *"아이콘이 왜 아직
프렙, 레시피 따로 있노"*). 프렙 항목 안에 레시피가 통째로 들어간 뒤로 둘을
나란히 두면 무엇이 다른지 알 수 없다. 실제로 다른 것은
**오늘 할 것(프렙)** 과 **주문 받고 찾는 것(레시피)** 인데,
그건 탭 두 개가 아니라 한 화면의 두 묶음이면 된다.

⚠️ **교육 모드(`/t/`)와 체크리스트(`/p/`)에는 탭바를 안 그린다.**
ⓐ 교육 모드는 한 장씩 넘기는 **한 방향 흐름**이라 중간에 새는 문이 있으면 안 된다.
ⓑ 체크리스트는 카카오톡 링크로 **직원 개인 폰**에서 여는 화면이다 —
거기에 매출·출퇴근 탭을 띄우면 남의 매장 사람에게 문을 여는 셈이다.

## 4. 잠금 규칙 — 세 겹

| 겹 | 무엇을 지키나 | 어디서 막나 | 키 | 열린 상태 | 화면 |
|---|---|---|---|---|---|
| **없음** | — | — | — | — | S-01·02·03·11·**13**·18 |
| 🔑 **매장 PIN** | **레시피 = 영업비밀** | ★ **서버** | `STORE_PIN` (환경변수) | `httpOnly` 쿠키 `sn_store` | **S-04**·05·06·07·08·**17**·**19** |
| 🔒 **사장님 PIN** | **인건비 · 사람 · 개인정보** (급여·계약·직원/거래처 연락처) | 브라우저 | `sop:ownerPin` | `sessionStorage` `sop:ownerOpen` | S-10·12·14·15·16 (+ S-09 인건비만) |

**규칙 네 가지**

1. ⚠️ **"사장님 PIN 이 풀리면 매장 PIN 도 풀린다" 는 이제 조건부다.**
   그 배려(번호를 두 개 외우게 하지 않는다)는 `storeGate.isUnlocked()` 에 있는데,
   그 함수를 쓰는 것은 **브라우저 폴백 `StoreGate` 뿐**이다. **`STORE_PIN` 이 설정돼
   있으면 서버는 쿠키만 본다** — 사장님 PIN 을 풀어도 레시피는 안 열린다.
   반대 방향은 예나 지금이나 아니다 (매장 PIN 으로 매출이 열리지 않는다)
2. **열린 상태는 브라우저를 닫으면 사라진다** — 공용 태블릿이라서.
   사장님 PIN 은 `sessionStorage`, 매장 PIN 은 세션 쿠키다
3. **사장님 PIN 은 단방향 요약값(FNV-1a)으로만 저장한다.** 원문을 안 남긴다
4. ★ **`STORE_PIN` 이 설정돼 있으면 매장 PIN 은 브라우저에 아예 없다.**
   서버 환경변수와 `httpOnly` 쿠키뿐이라 브라우저 스크립트로는 읽지도 못한다.
   비교는 `timingSafeEqual`(타이밍 공격 차단). 설정이 없을 때만 `sop:storePin` 폴백을 쓴다

### ★ 매장 PIN 은 2026-09-10 에 진짜 접근 통제가 됐다 (`fb1389a`)

전에는 **서버가 잠금과 무관하게 레시피를 그려서 보냈다.** `curl` 이나 [페이지 소스
보기] 로 PIN 없이 읽혔다. 이제 `ServerStoreGate` 가 **서버에서** 쿠키를 보고,
없으면 `children` 을 **아예 렌더하지 않는다.** 안 그리면 하이드레이션 페이로드에도
안 실린다 — **보낼 것이 없으니 받아갈 것도 없다.**

`tests/builtPages.test.ts` 가 둘 다 못 박는다 — 빌드 산출물에 배합이 안 나오는 것(**결과**)과

**그래도 과장하면 안 되는 것 셋**

| | |
|---|---|

### 2026-09-10 전체 점검에서 두 가지가 더 나왔다

**ⓐ 성공 한 번이 다른 기록의 실패 경고를 지웠다.** `report(ok)` 가 대상을 몰라서
`failed` 가 boolean 하나였다 — 계약 저장이 실패한 채로 설정을 고치면 경고가 사라졌다.

**ⓑ 재시도 버튼이 화면당 하나라 엉뚱한 것을 다시 저장했다.** 계약서 화면에서
**설정** 저장이 실패했는데 버튼은 **계약**을 다시 저장했다. 거래처·발주도 같았다.

→ `report(what, ok, retry)` 로 바꾸고 `failures: SaveFailure[]` 를 돌려준다.
같은 `what` 이 성공하면 그 경고만 사라지고, **동시에 여러 개가 실패하면 전부 그린다.**

**기준(2026-09-09 정함):** `sop:punch` · `sop:contracts` · `sop:vendors` · `sop:sales` ·
`sop:roster` · `sop:settings` · `sop:orderLog` 처럼 **나중에 다시 읽어야 하는 기록**은
실패를 반드시 알린다. 체크리스트·프렙처럼 **그날 지나면 지워질 것**은 조용해도 된다.

### 무엇을 만들었나

`src/components/ui.tsx` 에 둘을 넣고 여덟 화면이 같이 쓴다.

| `SaveFailed` | 빨간 띠 + `role="alert"` + **`다시 시도`** 버튼. `Screen` 이 머리말 바로 아래에 띄운다 |

**실측으로 잡은 것:** 배너를 강제로 띄워 브라우저에서 보니
`발주 기록발주 기록은 아직 남지 않았습니다` 가 나왔다.
`eun()` 이 조사만이 아니라 **낱말까지 같이** 돌려준다(`"발주 기록은"`).
`{what}{eun(what)}` 이 아니라 `{eun(what)}` 이어야 한다. 고쳤다.

**아직 안 한 것:** 단일 파일(`presentation/app.html`)은 `store.set` 이
`localStorage` 실패 시 **메모리에 담아두고 조용히 넘어간다.** 발표용 시연 파일이라
새로고침 뒤에 남아야 할 것이 없어서 그대로 뒀다.

### ⑧ 주기 점검 체크가 매일 지워졌다 → ✅ **고침 (2026-09-08)**

**주기 점검을 묶는 작업을 하다가 찾았다. 묶는 것보다 이게 훨씬 큰 문제다.**

프렙 화면은 체크를 `prep:{slug}:{영업일}` 에 저장하고, 영업일이 바뀌면
`pruneDayKeys()` 가 지난 키를 지운다. **주기 점검도 같은 규칙을 탄다.**

```
2026-09-08  정수 필터 교체 ✅ 체크        → prep:cycle:2026-09-08
2026-09-09  화면을 열면 — 체크가 없다      → prep:cycle:2026-09-09 (빈 키)
```

**즉 `4개월마다` 라고 적혀 있지만 앱은 그 4개월을 세지 않는다.**
마지막으로 언제 했는지를 아무데도 남기지 않으므로, 이 화면은 지금
**읽을 거리 13줄**이지 기능이 아니다.

`day-flow.md` 가 이 항목들을 이렇게 설명한다 — *"며칠 걸러도 티가 안 납니다.
그래서 아무도 기억 못 합니다."*
**기억을 대신하는 것이 이 화면의 존재 이유인데, 그걸 못 하고 있다.**

**고치려면 무엇이 필요한가**

| | |
|---|---|
| 저장 | 날짜별 체크가 아니라 **마지막 실행일** — 예: `sop:cycleDone` = `{ "c-1": "2026-05-11" }` |
| 지우기 | `pruneDayKeys` 대상에서 **빼야 한다** (`sop:punch` 처럼 보존) |
| 화면 | `4개월마다` 옆에 **`마지막 5/11 · 27일 남음`**, 지났으면 **`13일 지났습니다`** |
| 정렬 | 남은 날짜가 적은 것부터 — 오늘 할 게 위로 온다 |
| 내보내기 | `/backup` 에 넣을지 결정 필요 (보건증·소방은 점검 기록이 증빙이 된다) |

### 무엇을 만들었나 — `src/lib/cycleDone.ts`

| | |
|---|---|
| 저장 | `sop:cycleDone` = `{ "c-1": "2026-05-11" }`. **날짜가 키가 아니라 값이라서** `pruneDayKeys` 에 안 걸린다 |
| 체크의 뜻 | "오늘 했다". 오늘 것을 다시 누르면 취소되고, **지난 기록을 누르면 오늘로 갱신**된다 (취소가 아니다) |
| 화면 | `마지막 5/11 · 1일 지났습니다`(빨강) / `마지막 9/8 · 6일 남음` / `마지막 5/11 · 121일 전`(주기 미정) / `기록 없음 — 언제 했는지 모릅니다`(빨강) |
| 입력 | 항목마다 **`마지막 [날짜]` + `주기 [n]일`**. 날짜 칸이 있어야 **지난 기록을 채워 넣을 수 있다** |
| 상단 | `되돌릴 수 없는 것` 안내를 **`지금 해야 할 것 n개`** 로 바꿨다 — 13개 중 1개만 되돌릴 수 없어서 그 안내는 여기서 뜻이 약했다 |
| 진행률 | `n/13` 의 `n` 은 **기한 안에 있는 것**이다. "오늘 체크한 개수" 는 4개월 주기에서 늘 0 이라 뜻이 없다 |
| 정렬 | 급한 것부터. **기록 없는 것이 맨 앞** |

**기록이 없으면 `null` 로 둔다.** 0 으로 채우면 "오늘 해야 함", 큰 수로 채우면
"여유 있음" 으로 보인다. **둘 다 거짓이다** — 모른다는 것을 화면이 그대로 말한다.
소화기 점검을 3년 전에 했는지 어제 했는지 모르는 상태가 가장 위험하고,
그걸 목록 뒤로 밀면 사장님이 영영 안 채운다.

### ★★ 주기 숫자는 시드에서 뺐다 — 2026-09-08

사장님 지적: *"제빙기 청소 1개월마다 체크도 지우지 — 더럽게. 매일 청소하는 곳도
있는데. 6개월마다 이런 거도 쓰는 곳마다 다 달라서 굳이 없어도 될 거 같은데."*

**맞는 지적이다.** 제빙기를 매일 닦는 매장에 `1개월마다` 를 띄우면 그 화면은
**처음부터 틀린 말**을 한다. `4개월마다`·`6개월마다` 도 기계·계약·업종에 따라 다르다.
**내가 모르는 숫자를 박아놓고 앱이 단정하면, 사장님이 그 숫자를 믿는다.**

| 무엇이 바뀌었나 | |
|---|---|
| 시드의 `everyDays` | 13개 전부 **`null`** (`tests/seed.test.ts` 가 못 박는다) |
| 주기 뱃지(`1개월마다`) | 주기 항목에서는 **안 그린다** |
| 주기를 안 정했을 때 | 기한을 판단하지 **않는다.** `마지막 5/11 · 121일 전` 만 |
| 주기를 넣으면 | 그때부터 `27일 남음` / `13일 지났습니다` 로 바뀐다 |
| 정렬 | 기록 없음 → 기한 급한 것 → **주기 미정(판단 불가)은 맨 아래** |

**주기가 없어도 값이 남는다.** `day-flow.md` 가 말하는 문제는
*"며칠 걸러도 티가 안 나서 아무도 기억 못 한다"* 인데,
**마지막으로 한 날만 있으면 그 문제는 이미 풀린다.** 기한 판정은 그 위의 덤이다.

### ⑨ 법정 주기를 앱이 단정하지 않는다 ⚠️ **사장님 확인 필요**

**확실하지 않습니다. 그래서 앱에서 숫자를 뺐습니다.**

| | 제가 아는 것 | 왜 못 박을 수 없나 |
|---|---|---|
| **보건증** (건강진단결과서) | 식품위생법상 식품접객업 종사자는 **1년** 주기가 표준으로 알려져 있다 | 업종·직무에 따라 대상과 항목이 다르다. **결과서에 유효기간이 찍혀 나오므로 그걸 보는 게 정확하다** |
| **위생교육** | **영업자**는 매년 교육이 표준. 신규 영업자는 별도(사전 교육) | **영업자와 종업원의 대상·시간이 다르다.** 업종별 협회에 따라 운영도 다르다 |
| **소방시설** | 소화기 **육안 점검은 월 1회** 권장, 내용연한이 따로 있다. 자체점검(작동/종합)은 **연 단위** | ★ **자체점검 대상 여부와 주기가 건물 규모·용도에 따라 갈린다.** 소규모 근린생활시설은 대상이 아닐 수도 있다. **관할 소방서에 물어야 한다** |

**저는 법을 확인해 드릴 수 없습니다** — 조문 번호까지 외워서 말하면 그게 맞는지
제가 검증할 방법이 없고, 틀리면 과태료가 나갑니다.
**관할 보건소·소방서·업종 협회에서 확인한 값을 화면의 `주기` 칸에 넣어 주세요.**
그러면 그때부터 앱이 셉니다.

테스트(작성 시점 21개, `tests/cycleDone.test.ts`). 그중 하나는
**영업일이 바뀌어도 안 지워지는지**를 `pruneDayKeys` 를 직접 돌려 확인한다.

⚠️ 오후 프렙은 **하루 단위가 맞다.** 이 문제는 주기 점검만의 것이었다.

## 8. Figma — 어디까지 됐나
