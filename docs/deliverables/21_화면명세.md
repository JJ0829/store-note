> **이 문서가 정하는 것:** 다음 개발 단계에서 쓸 **화면·상태·이동의 기준**.
> **이 문서가 정하지 않는 것:** 데이터베이스, 배포, 서버.
>
> 2026-09-09 작성. [20_기능흐름도.md](20_기능흐름도.md)의 흐름을 화면 단위로 내린 것이다.

## 2. 상태 정의 — 모든 화면이 이 여섯 중에서만 고른다

화면마다 다른 말을 쓰면 만드는 사람도 쓰는 사람도 헷갈린다. 여섯으로 고정한다.

| 상태 | 언제 | 무엇을 보여주나 | 코드 표식 |
|---|---|---|---|
| **L 로딩** | `localStorage` 를 아직 못 읽음 (SSR → 클라이언트 사이) | 회색 네모 (`animate-pulse`) | `if (!now \|\| !data) return <skeleton>` |
| **N 정상** | 데이터가 있다 | 본문 | — |
| **Z 비었음** | 데이터가 0건 | **다음에 뭘 할지 알려주는 문장 + 버튼** | `<Empty>` |
| **X 오류** | 저장 실패 · 형식이 안 맞음 | 빨간 글, `role="alert"` | `role="alert"` |
| **G 잠김** | PIN 안 풀림 | PIN 입력칸만 | `OwnerGate` / `StoreGate` |
| **C 주의** | 정상인데 **믿으면 안 되는 값** | 회색 작은 글 | `<Caveat>` |

**C(주의)가 이 제품에 특히 많은 이유:** 인건비는 추정이고(4대보험·소득세 없음),
원가는 단가를 못 구한 재료가 있으면 낮게 나온다. **숫자를 보여주되 그 숫자를
얼마나 믿어도 되는지 같이 보여준다.** 이게 없으면 사장님이 틀린 숫자로 가격을 정한다.

## 3. 핵심 화면 5개 — 상세

고른 기준: **매일 열린다 + 발표 시연 동선에 있다.**

### S-01 `/` 오늘 — 허브

| | |
|---|---|
| 목적 | **메뉴를 뒤지지 않게 한다.** 지금 시각에 근무 중인 조와, 그 조가 열 화면만 위에 올린다 |
| 진입 | 태블릿 첫 화면 / `‹ 뒤로` 의 폴백 / `처음으로` (⚠️ **3개 화면에만 있다** — §4-b) |
| 데이터 | `seed.shifts` (서버) + `new Date()` (클라이언트) |
| 날짜 | — (시각만 씀) |

**상태**

| | 조건 | 화면 |
|---|---|---|
| L | 클라이언트 시각 읽기 전 | 회색 네모 |
| N-a | 근무 중인 조가 1개 이상 | `지금 HH:MM · 근무 중` + 조 카드들. **방금 시작한 조가 맨 위** |
| N-b | 근무 중인 조가 없음 (22:30~05:00) | `근무 시간이 아닙니다` + **다음 조** |

**이동** — 각 조의 `focus[]` 순서대로 버튼이 뜬다. 이게 이 화면의 전부다.

| 조 | 시각 | 버튼 |
|---|---|---|
| 제빵 | 05:00~13:00 | 제빵 순서 보기 `/t/bakery-morning` → 레시피 찾기 `/r` |
| 오픈조 | 07:30~15:30 | 오픈 체크리스트 `/p/cafe-open` → 오후 프렙 `/prep/afternoon` |
| 미들 | 11:00~19:00 | 레시피 찾기 `/r` |
| 마감조 | 14:30~22:30 | 오후 프렙 `/prep/afternoon` → **마감 준비 `/prep/evening`** → 마감 체크리스트 `/p/cafe-close` |

⚠️ **자정을 넘는 조가 있으면 `shiftClock.isOnDuty()` 로 판정해야 한다.**
평소 마감조는 22:30 에 끝나지만 **01:00 퇴근이 예외로 있다.** 그날 근무조를
`14:30~01:00` 으로 잡으면 옛 판정(`cur >= start && cur < end`)에서 **통째로 사라진다.**

### S-04 `/prep/[slug]` 프렙 — 제품이 종이를 이긴다고 주장하는 화면

| | |
|---|---|
| 목적 | **오늘 안 하면 내일 아침에 터지는 것**을 오늘 눈에 보이게 한다 |
| 진입 | S-01 프렙 행 3개 / 근무조 `focus` |
| 데이터 | `seed.prepLists` (서버) + 체크 상태 `prep:{slug}:{영업일}` |
| 날짜 | **`businessDay()`** — 자정이 아니라 새벽 4시에 바뀐다 |
| 경로 | `/prep/afternoon` · `/prep/evening` · `/prep/cycle` (3개, 정적 생성) |

**화면 순서 — 위에서 아래가 곧 중요도다**

1. 진행률 막대 + `n/전체`
2. 🔴 **`recoverable:false` 안내** — "까먹지 말고 해야 할 것 n개". 다 하면 초록으로 바뀐다
3. 목록 안내문 (`list.note`)
4. 항목 카드들

**항목 카드 안에서 조건부로 뜨는 것**

| 조건 | 표시 |
|---|---|
| `critical` | 🏷 `꼭 지키기` |
| `quantityVaries` | 🏷 `수량 매일 다름` ← **종이로 못 하는 이유** |
| `!recoverable` | 카드에 빨간 테두리 |
| `leadTimeHours !== null` | `지금 걸면 → 내일 07:43 부터 사용 가능 (16시간)` |
| `leadTimeDays !== null` | `오늘 주문 → 목요일 도착 (주말 배송 없음)` |
| `recipeSlug !== null` | **배수 계산기** (0.5·1·1.5·2·3배). 27개 중 **8건**. 옵션 안에서도 뜬다 |
| `kind === "routine"` | **리드타임 줄이 아예 안 뜬다** ← 없는 약속을 만들지 않기 위해 |
| `optionOf !== null` | **독립 카드가 아니라 부모 카드 안**에 그려진다 |
| 자식이 `optional:false` | 그 카드는 **「묶음 머리」** — 누를 수 없고 분모에도 안 들어간다 |

**두 숫자의 분모가 다르다 — 일부러다 (2026-09-09)**

| 숫자 | 무엇을 세나 | 옵션(`optionOf`)을 |
|---|---|---|
| `n/전체` · 진행률 막대 | 오늘 이 목록에서 할 일 | ⛔ **뺀다** |
| 「까먹지 말고 해야 할 것 n개」 | `recoverable:false` 인 것 | ✅ **센다** |

**왜 나눴나.** 매장마다 하거나 안 하는 일이 있다 — 사워도우를 안 하는 카페에
르방은 뜻이 없다. 그게 분모에 들어가면 **`9/10` 이 영영 안 채워지고 진행률이
거짓이 된다.** 그러면 사람은 곧 진행률을 안 본다.

**그리고 옵션은 흩어놓지 않는다** (사장님 지적: *"따로말고 한곳에 모아서 해줘"*).
바에서 만드는 부재료 다섯은 **`바 부재료 점검 · 제조` 한 카드**에 모여 있다.
그래서 오후 프렙은 **카드 5개 + 옵션 6개**다 — 카드 11개가 아니다.

### 주기 점검도 같은 방식으로 묶었다 (2026-09-08 요청)

13개가 한 줄로 늘어서 있어서, 저울 영점(**7일**)과 소화기 점검(**1년**)이 나란히
있었다. 세 묶음으로 나누고 **묶음 안은 주기가 짧은 것부터** 세웠다.

| 묶음 (누를 수 없다) | 안에 든 것 |
|---|---|
| **기계 · 설비 점검** | 저울 영점 7일 · 정수 필터 4개월 · 개스킷 6개월 · 그라인더 날 6개월 · 냉장 가스켓 6개월 · 머신 정기점검 1년 |
| **안 보이는 곳 청소** | 배수구·트렌치 7일 · 제빙기 1개월 · 방충·방역 1개월 · 후드·덕트 3개월 🔴 |
| **서류 · 법정** | 보건증 1년 · 소화기·소방 1년 · 위생교육 1년 |

**진행률은 `n/13` 이다 — 16이 아니다.** 묶음 머리는 할 일이 아니라 이름표라서
누를 수 없고 분모에도 안 들어간다. 부모까지 세면 같은 일을 두 번 센다.

**그리고 이건 옵션이 아니다.** 주기 점검에 *"매장에 따라 안 하기도 합니다"* 를
붙이면 거짓이다 — 보건증·소방·위생교육은 안 하면 과태료다. 그래서 같은 자리에
`이 묶음의 항목 n개` 를 쓴다. (`tests/seed.test.ts` 가 `optional: false` 를 못 박는다)

## 6. E — 거래처: 세 값이 어디에 있는가 ⚠️ **결정 필요**

> `day-flow.md` 가 "리드타임 기능의 핵심 입력값"으로 표시해둔 항목이다.
> **아직 0건이다.** 오늘 확인한 것은 *"그 값을 앱이 받을 자리가 있는가"* 다.

| 값 | 지금 어디에 | 사장님이 화면에서 고칠 수 있나 |
|---|---|---|
| **주문 마감 시각** | `Vendor.cutoff` (`sop:vendors`) | ✅ `/vendors` |
| **입고 소요일** | `Vendor.leadDays` | ✅ `/vendors` |
| **배송 요일** | `Vendor.deliverDays` | ✅ `/vendors` |

### 무엇이 문제인가

**첫째, 발주 요일을 사장님이 못 고친다.** `p-5 우유·식자재 발주` 의
`trigger: {type:"weekday", days:[…], at:"15:00"}` 안에 있고, 프렙 항목을 고치는
화면이 없다. 거래처가 요일을 바꾸면 **코드를 배포해야 한다.**

**둘째, 마감 시각이 두 군데 있다.** 프렙 트리거의 `at`(15:00)과
`Vendor.cutoff`(15:00). 지금은 우연히 같지만 **한쪽만 고치면 조용히 갈린다.**

**셋째 — 이게 화면에 바로 보이는 결과다.** `/order` 의 "오늘 주문 마감" 카드는
**모든 거래처를 매일 세운다.** 오늘 주문하지 않는 거래처까지 카운트다운이 돈다.
거래처가 6곳이면 아침마다 6개 중 5개가 관계없는 줄이다 → **사람은 곧 안 읽는다.**

### 제안 (사장님 결정 대기)

| | 안 | 장점 | 단점 |
|---|---|---|---|
| **가** | `Vendor` 에 `orderDays` 를 더하고 `/order` 가 **오늘 주문하는 곳만** 세운다 | 세 값이 한 군데(거래처)로 모인다. 사장님이 화면에서 다 고친다 | 프렙의 발주 항목과 거래처 중 **어느 쪽이 발주의 주인인지** 다시 정해야 한다 |
| **나** | 그대로 두고 프렙 트리거만 쓴다 | 코드 안 바뀜 | 사장님이 못 고친다. 값이 계속 두 군데 |

**저는 (가)를 권합니다.** 다만 **바꾸기 전에 실제 거래처 값이 필요합니다** —
값을 모르는 채로 필드만 만들면 맞는지 확인할 방법이 없습니다.

`{what}{eun(what)}` 이 아니라 `{eun(what)}` 이어야 한다. 고쳤다.

**아직 안 한 것:** 단일 파일(`presentation/app.html`)은 `store.set` 이
`localStorage` 실패 시 **메모리에 담아두고 조용히 넘어간다.** 발표용 시연 파일이라
새로고침 뒤에 남아야 할 것이 없어서 그대로 뒀다.

### ⑧ 주기 점검 체크가 매일 지워졌다 → ✅ **고침 (2026-09-08)**

**주기 점검을 묶는 작업을 하다가 찾았다. 묶는 것보다 이게 훨씬 큰 문제다.**

프렙 화면은 체크를 `prep:{slug}:{영업일}` 에 저장하고, 영업일이 바뀌면
`pruneDayKeys()` 가 지난 키를 지운다. **주기 점검도 같은 규칙을 탄다.**

```
2026-09-08  정수 필터 교체 ✅ 체크        → prep:cycle:2026-09-08
2026-09-09  화면을 열면 — 체크가 없다      → prep:cycle:2026-09-09 (빈 키)
```

**즉 `4개월마다` 라고 적혀 있지만 앱은 그 4개월을 세지 않는다.**
마지막으로 언제 했는지를 아무데도 남기지 않으므로, 이 화면은 지금
**읽을 거리 13줄**이지 기능이 아니다.

`day-flow.md` 가 이 항목들을 이렇게 설명한다 — *"며칠 걸러도 티가 안 납니다.
그래서 아무도 기억 못 합니다."*
**기억을 대신하는 것이 이 화면의 존재 이유인데, 그걸 못 하고 있다.**

**고치려면 무엇이 필요한가**

| | |
|---|---|
| 저장 | 날짜별 체크가 아니라 **마지막 실행일** — 예: `sop:cycleDone` = `{ "c-1": "2026-05-11" }` |
| 지우기 | `pruneDayKeys` 대상에서 **빼야 한다** (`sop:punch` 처럼 보존) |
| 화면 | `4개월마다` 옆에 **`마지막 5/11 · 27일 남음`**, 지났으면 **`13일 지났습니다`** |
| 정렬 | 남은 날짜가 적은 것부터 — 오늘 할 게 위로 온다 |
| 내보내기 | `/backup` 에 넣을지 결정 필요 (보건증·소방은 점검 기록이 증빙이 된다) |

### 무엇을 만들었나 — `src/lib/cycleDone.ts`

| | |
|---|---|
| 저장 | `sop:cycleDone` = `{ "c-1": "2026-05-11" }`. **날짜가 키가 아니라 값이라서** `pruneDayKeys` 에 안 걸린다 |
| 체크의 뜻 | "오늘 했다". 오늘 것을 다시 누르면 취소되고, **지난 기록을 누르면 오늘로 갱신**된다 (취소가 아니다) |
| 화면 | `마지막 5/11 · 1일 지났습니다`(빨강) / `마지막 9/8 · 6일 남음` / `기록 없음 — 언제 했는지 모릅니다`(빨강) |
| 상단 | `되돌릴 수 없는 것` 안내를 **`지금 해야 할 것 n개`** 로 바꿨다 — 13개 중 1개만 되돌릴 수 없어서 그 안내는 여기서 뜻이 약했다 |
| 진행률 | `n/13` 의 `n` 은 **기한 안에 있는 것**이다. "오늘 체크한 개수" 는 4개월 주기에서 늘 0 이라 뜻이 없다 |
| 정렬 | 급한 것부터. **기록 없는 것이 맨 앞** |

**기록이 없으면 `null` 로 둔다.** 0 으로 채우면 "오늘 해야 함", 큰 수로 채우면
"여유 있음" 으로 보인다. **둘 다 거짓이다** — 모른다는 것을 화면이 그대로 말한다.
소화기 점검을 3년 전에 했는지 어제 했는지 모르는 상태가 가장 위험하고,
그걸 목록 뒤로 밀면 사장님이 영영 안 채운다.

테스트 21개 (`tests/cycleDone.test.ts`). 그중 하나는
**영업일이 바뀌어도 안 지워지는지**를 `pruneDayKeys` 를 직접 돌려 확인한다.

⚠️ 오후 프렙·마감 준비는 **하루 단위가 맞다.** 이 문제는 주기 점검만의 것이었다.

⚠️ **아직 안 정한 것:** 이 기록을 `/backup` 에 넣을지. 보건증·소방·위생교육은
점검 기록 자체가 증빙이 된다.

## 8. Figma — 어디까지 됐나 ⚠️ **1/5 에서 막혔다**

| | |
|---|---|
| 파일 | **매장수첩 · 핵심 화면 5 (와이어프레임)** |
| 주소 | https://www.figma.com/design/3beANZEtkFcdfgaan2ZJZR |
| 만든 것 | 제목 블록 + **S-01 오늘** 아트보드 (375×656, 오토레이아웃, Noto Sans KR) |
| 못 만든 것 | **S-04 프렙 · S-03 체크리스트 · S-11 발주 · S-09 출퇴근 (4개)** |

**막힌 이유:** Figma **Starter 요금제의 MCP 호출 한도**에 걸렸다.
`You've reached the Figma MCP tool call limit on the Starter plan.`
화면 하나를 만든 직후 한도가 닫혀서 **스크린샷 검증도 못 했다** — 즉
S-01 아트보드가 눈으로 보기에 제대로 나왔는지 **확인 안 됐다.**

**대안은 이미 있다.** [../wireframes/와이어프레임.html](../wireframes/와이어프레임.html) 에
**5개 화면이 전부** 들어 있고 주석까지 붙어 있다. Figma 는 같은 내용을 옮기는 작업이다.

**풀 방법 셋:**

| | 방법 | 비고 |
|---|---|---|
| 가 | 한도가 풀릴 때까지 기다렸다가 이어서 만든다 | 언제 풀리는지는 Figma 쪽 정책이라 내가 모른다 |
| 나 | 요금제를 올린다 | 발표(9/18) 하나 때문에 올릴 값어치가 있는지는 사장님 판단 |
| 다 | **HTML 와이어프레임으로 간다** | 이미 완성돼 있고 인쇄도 된다. **저는 이걸 권합니다** |

★ **Figma 가 이 프로젝트에 꼭 필요한 물건은 아니다.** 화면을 만드는 사람과
보는 사람이 같은 한 사람이고, 디자이너에게 넘길 계획이 아직 없다.
**"화면·상태·이동의 합의문"이라는 목적은 HTML 쪽이 이미 채웠다.**
