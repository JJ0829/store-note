## 1. 총평 — 결론부터

**차단해야 할 오픈소스 리스크는 발견되지 않았다. 강한 카피레프트(GPL·AGPL) 라이선스 패키지는 45개 중 0건이다.**
근거는 `docs/deliverables/_라이선스_원자료.json`의 `licenseCounts`이며, 실제 값은 MIT 32 / Apache-2.0 4 / ISC 3 / MPL-2.0 2 / `Apache-2.0 AND LGPL-3.0-or-later` 1 / CC-BY-4.0 1 / BSD-3-Clause 1 / 0BSD 1로, `GPL-*` 또는 `AGPL-*` 단독 선언은 한 건도 없다. 즉 **"이 제품의 소스를 공개해야 한다"는 의무를 발생시키는 패키지가 없다.** 45개 중 41개(91%)가 MIT·Apache·ISC·BSD·0BSD 계열의 허용형(permissive) 라이선스로, 고지문 한 장이면 의무가 끝난다. 나머지 4건(주의)은 ① 약한 카피레프트 1건(`@img/sharp-win32-x64` — LGPL-3.0-or-later 바이너리 포함), ② 파일 단위 카피레프트 2건(`lightningcss` ×2 — MPL-2.0), ③ 저작자 표시 1건(`caniuse-lite` — CC-BY-4.0)인데, **네 건 모두 "우리가 그 코드를 수정하지 않고, 제3자에게 그 코드를 배포하지도 않는다"는 사실 때문에 실질 의무가 발생하지 않는다** (근거 상세 → 5절). 다만 **아무것도 안 해도 된다는 뜻은 아니다.** 지금 미이행 상태인 것이 두 가지 있다: **(가) 허용형 라이선스 41건이 요구하는 저작권 고지문이 저장소에 없다** (`LICENSE`·`NOTICE`·`THIRD-PARTY-NOTICES` 파일 존재 확인 결과 0건), **(나) 프로젝트 자체의 라이선스가 정해져 있지 않다** (`package.json`에 `license` 필드 없음, `"private": true`만 있음). 둘 다 **파일 두 개를 추가하면 끝나는 작업**이고, 2026-09-18 발표 전에 처리 가능하다 (→ 10절, 11절).

## 2. 감사 개요

### 2-1. 목적

「바이브코딩 필수 산출물 진행표」 4번 항목의 정의에 따른다 (`docs/deliverables/00_진행표.md`).

> "사용 라이선스 검토를 통해 개발 착수 전 오픈소스 리스크 차단"

구체적으로 이 감사가 답해야 하는 질문은 셋이다.

1. **이 제품을 유료로 팔 수 있는가?** — 카피레프트가 소스 공개를 강제하면 팔 수 없다.
2. **지금 이행하지 않고 있는 의무가 있는가?** — 고지 누락은 가장 흔한 위반이고 가장 싸게 고쳐진다.
3. **앞으로 패키지를 추가할 때 무엇을 보고 판단하는가?** — 1회성 감사는 다음 `npm install`에 무너진다.

**부수 목적:** 2026-09-18 정부지원사업 심사에서 라이선스 항목이 실제로 검토될 가능성이 높다 (`docs/deliverables/00_진행표.md` "심사에서 실제로 볼 가능성이 높은 것은 4번(라이선스), 10번(개인정보처리방침), 3번(ERD)").

| 단계 | 무엇을 | 어떻게 |
|---|---|---|
| 1 | 설치된 전체 의존성 목록화 | `node_modules/` 실측 → `_라이선스_원자료.json` (45개) |

| 4 | 위험 등급 부여 | SPDX 식별자 기준 4등급 (2-4절) |

| 6 | 실제 사용 방식 확인 | 소스 코드 grep — 해당 패키지를 코드가 부르는지 |

> **읽는 법:** "빌드"는 개발·빌드할 때만 쓰이고 배포 산출물에 들어가지 않는 것, "런타임"은 서버에서 실제로 도는 것이다. 판정 근거는 `package-lock.json`의 `dev` 플래그다.
>
> **Apache-2.0 1건(`typescript`)에 대한 메모:** Apache-2.0은 MIT에 없는 조항이 두 개 있다. **§4(b) 변경 파일 표시 의무**, **§3 특허 소송 시 특허 라이선스 자동 종료**. 우리는 TypeScript를 **수정하지 않고 그대로 쓰므로 §4(b)는 발생하지 않는다.** §3은 우리가 Microsoft를 상대로 특허 소송을 걸지 않는 한 무해하다.
>
> 다만 Apache-2.0 패키지는 **`NOTICE` 파일이 있으면 그 내용을 전달할 의무**가 있다(§4(d), `node_modules/typescript/LICENSE.txt` 제4항 넷째 소항목). **실측 결과 `node_modules/typescript/`의 파일 구성은 다음과 같다:**
>
> ```
> LICENSE.txt                  ← Apache-2.0 전문
> README.md
> SECURITY.md
> ThirdPartyNoticeText.txt     ← 제3자 저작권 고지 (193줄. 첫 줄 "TypeScript ThirdPartyNotices")
> bin/
> lib/
> package.json
> ```
>
> **파일명이 정확히 `NOTICE`인 파일은 없다. 따라서 §4(d)의 엄격한 의무(NOTICE 사본 포함)는 문언상 발동하지 않는다.** 그러나 `ThirdPartyNoticeText.txt`에 DefinitelyTyped 등 제3자 고지가 실제로 담겨 있으므로, **고지문(THIRD-PARTY-NOTICES.md)을 만들 때 그 내용을 함께 옮기는 것이 안전하다** (→ 11-3절 4-5항).
>
> Apache-2.0 나머지 3건(`@swc/helpers`, `detect-libc`, `sharp`)도 실측했다 — 세 패키지 모두 `LICENSE` 파일만 있고 `NOTICE`·제3자 고지 파일이 **없다.** 즉 Apache-2.0 4건 중 전달할 고지 내용을 가진 것은 `typescript` 하나뿐이다.

## 5. 주의 4건 상세 분석

각 건을 **① 라이선스가 요구하는 의무 → ② 우리가 실제로 어떻게 쓰는가 → ③ 그래서 의무가 발생하는가**의 순서로 본다.
②를 건너뛰면 판정이 불가능하다. LGPL·MPL 의무는 대부분 **"배포(convey/distribute)"라는 행위에 붙어 있기 때문**이다.

### 5-1. `@img/sharp-win32-x64` 0.35.4 — `Apache-2.0 AND LGPL-3.0-or-later`

가장 무거운 건이다. **45개 중 유일하게 카피레프트 바이너리를 실제로 담고 있다.**

#### ① 라이선스가 요구하는 의무

이 패키지는 SPDX 표현식 `Apache-2.0 AND LGPL-3.0-or-later`로 선언돼 있다. `AND`는 **두 라이선스를 모두 지켜야 한다**는 뜻이다(`OR`이면 택일). 패키지 자신의 설명이 구조를 명시한다.

`node_modules/@img/sharp-win32-x64/README.md`:

```
## Licensing
Copyright 2013 Lovell Fuller and others.
Licensed under the Apache License, Version 2.0 (the "License");
...
This software contains third-party libraries
used under the terms of the following licenses:

| Library       | Used under the terms of |
| libvips       | LGPLv3                  |
| glib          | LGPLv3                  |
| pango         | LGPLv3                  |
| librsvg       | LGPLv3                  |
| libheif       | LGPLv3                  |
| libexif       | LGPLv3                  |
| fribidi       | LGPLv3                  |
| proxy-libintl | LGPLv3                  |
| cairo         | Mozilla Public License 2.0 |
| harfbuzz, expat, cgif, lcms, libffi, libnsgif,
  libultrahdr, libxml2, pixman                | MIT License |

"any later version" clause of the LGPLv2 or LGPLv2.1.

즉 **sharp 자신의 래퍼 코드는 Apache-2.0이고, 그 안에 동봉된 이미지 처리 엔진 libvips 및 그 하위 라이브러리 8종이 LGPLv3**이다. 실제로 파일이 들어 있는 것도 확인했다 — `node_modules/@img/sharp-win32-x64/` 디렉터리 구성:

```
LICENSE                     ← Apache-2.0 전문
README.md                   ← 위 서드파티 표
versions.json               ← 동봉된 28개 라이브러리 버전 (vips 8.18.6 등)
index.cjs
lib/
libvips-42.dll              ← LGPLv3 · 동적 라이브러리
libvips-cpp-8.18.6.dll      ← LGPLv3 · 동적 라이브러리
sharp-win32-x64-0.35.4.node ← 네이티브 애드온
```

**LGPL-3.0-or-later가 요구하는 것** (원문 https://www.gnu.org/licenses/lgpl-3.0.html):

| 조항 | 의무 | 언제 발동하는가 |
|---|---|---|
| §4 (Combined Works) | LGPL 라이브러리를 쓴다는 **눈에 띄는 고지**를 하고, GNU GPL·LGPL 사본을 함께 제공 | 결합 저작물을 **convey(배포)** 할 때 |
| §4(d) | 사용자가 **LGPL 라이브러리를 수정한 버전으로 교체·재링크**할 수 있게 할 것 (동적 링크면 공유 라이브러리 방식으로 충족) | 위와 동일 |
| §2 (Conveying Modified Versions) | LGPL 라이브러리 **자체를 수정**해 배포하면 그 수정본을 LGPL로 공개 | 라이브러리를 고쳐서 배포할 때 |

**결정적으로, LGPL의 모든 핵심 의무는 "convey"(GPLv3 §0 정의: 타인이 사본을 만들거나 받게 하는 행위)를 전제한다.** LGPL은 AGPL과 달리 **네트워크를 통한 이용 제공(SaaS)을 배포로 보지 않는다.** 이 차이가 이 건 판정의 전부다.
- AGPL-3.0 §13(원격 네트워크 상호작용 조항) 원문 — https://www.gnu.org/licenses/agpl-3.0.html
- GPL FAQ, 웹 서비스와 GPL — https://www.gnu.org/licenses/gpl-faq.html#UnreleasedMods

#### ② 우리가 이 패키지를 어떻게 쓰는가

네 가지를 코드에서 확인했다.

**(가) 우리가 직접 설치한 적이 없다 — `next`의 선택적 의존성이다.**
`package.json` `dependencies`에는 `next`, `react`, `react-dom` 3개뿐이고 sharp는 없다. `package-lock.json`의 `node_modules/next` 항목:

```
optionalDependencies: {
  "@next/swc-darwin-arm64": "15.5.24",  ... ,
  "sharp": "^0.34.3 || ^0.35.3"          ← 여기
}
```

그리고 `node_modules/sharp` 항목은 `"optional": true`이며, 그 아래 `optionalDependencies`로 25개 플랫폼 패키지가 걸려 있고 그중 Windows x64용인 `@img/sharp-win32-x64`만 설치됐다.
Next.js가 sharp를 쓰는 용도는 **`next/image` 컴포넌트의 프로덕션 이미지 최적화** 하나다.

**(나) 우리 컴포넌트는 `next/image`를 쓰지 않는다.**
`src/` 전체에서 `next/image` import는 **0건**이다. 이미지는 표준 `<img>` 태그로 직접 그린다.

```tsx
// src/components/MediaSlot.tsx:42-50
{/* eslint-disable-next-line @next/next/no-img-element */}
<img
  src={p.src}
  alt={p.label}
  loading="lazy"
  className={[...]}
/>
```

`eslint-disable`로 Next의 `no-img-element` 규칙을 명시적으로 끈 것이 `next/image`를 의도적으로 안 쓴다는 증거다. 영상도 마찬가지로 표준 `<video>`다(`MediaSlot.tsx:75-81`).

**❓ 확인 필요 — 그렇다고 "sharp 코드 경로가 절대 진입하지 않는다"고 단정할 수는 없다.** Next의 이미지 최적화는 `next/image` 컴포넌트 import와 별개로 **`next.config.ts`의 `images` 설정과 `/_next/image` 엔드포인트가 지배**한다. 실측한 `next.config.ts`는 다음과 같다.

```ts
// next.config.ts
const nextConfig: NextConfig = {
  // 체크리스트 사진은 Supabase Storage 등 외부 호스트로 옮길 수 있으므로
  // 여기에 도메인을 추가한다.
  images: { remotePatterns: [] },
};
```

**`images` 블록이 실제로 존재하고, `unoptimized: true`가 설정돼 있지 않다.** 즉 이미지 최적화가 명시적으로 꺼진 상태가 아니다. `/_next/image?url=...` 엔드포인트에 직접 요청이 들어오면 sharp가 호출되는지는 **배포본에서 직접 확인해야 하며, 이번 감사에서 확인하지 못했다.** (→ 15절 미해결 #15)

따라서 이 절이 근거로 삼는 사실은 **"우리 컴포넌트가 `next/image`를 쓰지 않는다"까지**다. 실행 경로가 물리적으로 존재하지 않는다는 뜻은 아니다.

**(다) 우리는 libvips DLL을 수정하지 않는다. 재컴파일도 안 한다.**
`node_modules/`는 `.gitignore` 대상이라 저장소에 포함되지 않는다.

```
# .gitignore
node_modules/
.next/
out/
```

`git ls-files` 결과 추적 파일은 76개이며 여기에 `.dll`·`.node` 바이너리는 없다.

**(라) 현재 배포 형태는 배포(convey)가 아니다.**
현재까지의 유일한 게시물은 **Claude Artifact로 1회 시연 게시한 단일 HTML 파일**(`presentation/매장수첩.html`)이다. 이 파일은 서버·npm 의존성 없이 브라우저만으로 도는 단일 파일이므로 **sharp도 libvips도 애초에 들어 있지 않다.** Vercel 정식 배포는 아직 하지 않았고, 하더라도 사용자는 브라우저로 접속할 뿐 바이너리를 받아가지 않는다.

#### ③ 그래서 의무가 발생하는가 — **발생하지 않는다**

| LGPL 의무 | 발동 조건 | 현재 상태 | 판정 |
|---|---|---|---|
| §2 수정본 공개 | libvips를 **수정**해 배포 | 수정 0건. DLL 그대로 | ❌ 미발동 |
| §4 고지 + 라이선스 사본 첨부 | 결합 저작물을 **convey** | 바이너리를 제3자에게 전달한 적 없음 | ❌ 미발동 |
| §4(d) 재링크 가능성 보장 | 결합 저작물을 **convey** | 위와 동일. 게다가 `.dll`은 이미 동적 링크라 요건 자체는 쉽게 충족되는 형태 | ❌ 미발동 |
| Apache-2.0 §4(b) 변경 파일 표시 | sharp 래퍼 코드 수정 | 수정 0건 | ❌ 미발동 |
| Apache-2.0 §4(a)·(d) 라이선스·NOTICE 사본 전달 | 배포 시 | 배포 없음. 단 **11절 고지문에 선제 반영 권장** | △ |

**결론: 현재 구조에서 `@img/sharp-win32-x64`는 라이선스 의무를 발생시키지 않는다.** 이 결론은 **"바이너리를 제3자에게 전달(convey)하지 않는다"** 하나로 성립하며, sharp가 실행되는지 여부에 의존하지 않는다.

> **"죽은 의존성"이라는 표현은 쓰지 않는다.** 위 (나)에서 적었듯 `next.config.ts`에 `images` 블록이 있고 `unoptimized`가 설정돼 있지 않아, `/_next/image` 경로에서 sharp가 호출될 가능성을 배제하지 못했다. **실측(배포본에서 `/_next/image` 접근 결과 확인) 전까지 이 단정은 보류한다.** 다만 실행되더라도 위 표의 판정은 바뀌지 않는다 — LGPL 의무는 실행이 아니라 배포에 붙기 때문이다.

**❗ 이 판정이 뒤집히는 조건 세 가지** — 하나라도 해당되면 즉시 재검토한다.

| 조건 | 왜 뒤집히는가 | 대응 |
|---|---|---|
| **Docker 이미지 / 압축 배포판을 제3자에게 전달** | 이미지 안에 `libvips-42.dll`(또는 Linux `.so`)이 들어간 채 전달됨 = **convey 성립** → LGPL §4 고지·라이선스 사본·재링크 보장 의무 발생 | 고지문에 LGPL 절 추가 + LGPL/GPL 전문 동봉 + libvips 소스 취득 경로 명시 |
| **온프레미스(매장 서버) 설치형 판매** | 위와 동일하게 convey | 위와 동일 |
| **`next/image`를 쓰기 시작** | 의무 자체는 여전히 배포에 붙지만, sharp가 실행 경로에 확실히 들어오고 `--omit=optional` 회피책(13-3절)을 더는 쓸 수 없게 된다 | 사용 시점에 재감사 |

**❗ 추가 리스크 (지금은 무해, 배포 시 재확인):** libvips는 `versions.json`에서 확인되듯 **28개 서드파티 라이브러리의 집합체**다. LGPLv3 8종 외에 MPL-2.0(cairo), AOM 특허 라이선스(aom), IJG 라이선스(mozjpeg) 등이 섞여 있다. 바이너리를 실제로 배포하게 되면 **이 28개 전부의 고지가 필요**해진다. sharp README의 표를 그대로 고지문에 옮기는 것이 가장 안전한 방법이다.

> **가장 깔끔한 대안:** 배포 시 `npm install --omit=optional`로 sharp를 아예 설치하지 않으면, LGPL·MPL·특허 라이선스 검토가 **통째로 사라진다.** `next/image`를 쓰지 않는 현재로서는 기능 손실이 0이다. → 13절 정책에 반영.
> ❓ 확인 필요 — Vercel 등 호스팅 플랫폼이 빌드 시 `--omit=optional`을 지원하는지, sharp 부재 시 빌드가 경고만 내는지 실제 검증 필요. **`next.config.ts`에 `images: { unoptimized: true }`를 명시하면 `/_next/image` 경로 자체가 사라져 더 확실하다** — 이 설정 변경 여부도 함께 결정할 것.

### 5-2. `lightningcss` 1.32.0 · `lightningcss-win32-x64-msvc` 1.32.0 — MPL-2.0 (2건)

#### ① 라이선스가 요구하는 의무

Mozilla Public License 2.0. 원문 — https://www.mozilla.org/en-US/MPL/2.0/ · 공식 FAQ — https://www.mozilla.org/en-US/MPL/2.0/FAQ/

MPL-2.0은 **"파일 단위(file-level) 카피레프트"**다. GPL처럼 결합 저작물 전체를 오염시키지 않고, **MPL 고지가 붙은 그 파일(및 그 바이너리·수정본)에만** 의무가 붙는다. "파일 단위"는 *결합한 우리 코드로 번지지 않는다*는 뜻이지, *소스 파일만 대상*이라는 뜻이 아니다 — §1.4 정의 전문은 아래 ③ 참조.

| 조항 | 의무 |
|---|---|
| §1.4 "Covered Software" | 의무의 대상은 **MPL 고지가 붙은 소스 코드 파일, 그 Executable Form(바이너리), 그리고 그 수정본**이다 (전문은 아래 ③ 참조) |
| §3.1 | Covered Software를 Source Code Form으로 배포하면 **수정본을 포함해 전부 MPL 조건 하에서** 배포해야 하고, 수령자에게 라이선스 취득 방법을 알려야 한다 |
| §3.2 | Executable Form으로 배포할 때는 소스 취득 방법을 고지해야 한다 |
| §3.4 (Notices) | Covered Software 안의 **라이선스 고지(저작권·특허·면책 고지)를 제거하거나 변경하지 말 것** |
| **§3.3 (Larger Works)** | Covered Software를 **더 큰 저작물의 일부로 결합**할 수 있고, **그 더 큰 저작물은 다른 라이선스(사유 라이선스 포함)로 배포해도 된다** — 단 Covered Software 부분은 계속 MPL |

**§3.3이 MPL을 "안전한 카피레프트"로 만드는 조항이다.** 우리 코드가 MPL로 끌려가지 않는다는 근거가 여기에 있다.

#### ② 우리가 이 패키지를 어떻게 쓰는가

**(가) 빌드 전용 도구다. 우리 코드가 import하지 않는다.**
의존 경로를 `package-lock.json`에서 추적하면:

```
package.json (devDependencies)
  └─ @tailwindcss/postcss  4.3.3
       └─ @tailwindcss/node  4.3.3
            └─ lightningcss  1.32.0      ← dev: true
                 └─ lightningcss-win32-x64-msvc  1.32.0   (optional, dev: true)
```

`node_modules/@tailwindcss/node`의 선언된 의존성에 `"lightningcss": "1.32.0"`이 고정 버전으로 들어 있다. 그리고 `package-lock.json`의 `node_modules/lightningcss` 항목은 **`dev: true`** 다 — 즉 프로덕션 설치(`npm ci --omit=dev`) 시 아예 설치되지 않는다.

`src/` 전체에서 `lightningcss` import는 **0건**이다. Tailwind가 내부적으로 CSS 파싱·최적화에 쓰는 것이고, 우리는 `postcss.config.mjs` 한 줄로 Tailwind만 부른다.

```js
// postcss.config.mjs
const config = {
  plugins: { "@tailwindcss/postcss": {} },
};
export default config;
```

**(나) 소스를 수정하지 않는다.** `node_modules/`는 `.gitignore`되어 저장소에 없고, 포크·패치·`patch-package` 사용 이력이 없다.

**(다) 재배포하지 않는다.** 빌드 산출물은 `.next/` 안의 **컴파일된 CSS 문자열**이다. `.next/`도 `.gitignore` 대상이다.

#### ③ 그래서 의무가 발생하는가 — **발생하지 않는다**

| MPL 의무 | 발동 조건 | 현재 상태 | 판정 |
|---|---|---|---|
| §3.1 소스 제공 | Covered Software를 배포 | lightningcss 자체를 배포하지 않음 | ❌ 미발동 |
| §3.2 소스 취득 방법 고지 | Executable Form 배포 | 위와 동일 | ❌ 미발동 |
| §3.1 수정본도 MPL 조건으로 배포 | 파일을 수정해서 배포 | 수정 0건 | ❌ 미발동 |
| §3.4 고지 제거·변경 금지 | Covered Software를 다룰 때 상시 | `node_modules/` 파일 미수정. 고지 손댄 적 없음 | ❌ 위반 없음 |
| §3.3 Larger Work | — | 애초에 결합 자체가 없음 | 해당 없음 |

**핵심 논거 두 가지:**

1. **빌드 도구의 출력물은 Covered Software가 아니다.** lightningcss가 처리한 결과물(컴파일된 CSS)은 **우리가 쓴 CSS를 변환한 것**이지 lightningcss의 소스 코드가 아니다. 컴파일러의 출력물에 컴파일러의 라이선스가 전파되지 않는 것과 같은 구조다.

   MPL §1.4 "Covered Software"의 **정의 전문**은 다음과 같다 (`node_modules/lightningcss/LICENSE:18-22`. §3.1은 같은 파일 160행, §3.4는 198행).

   ```
   1.4. "Covered Software"
   means Source Code Form to which the initial Contributor has attached
   the notice in Exhibit A, the Executable Form of such Source Code
   Form, and Modifications of such Source Code Form, in each case
   including portions thereof.
   ```

   **정의는 좁지 않다.** Source Code Form뿐 아니라 **그것의 Executable Form(즉 `lightningcss-win32-x64-msvc`의 네이티브 바이너리)과 수정본까지** Covered Software에 포함된다. 그러므로 이 바이너리가 무해한 이유를 "정의에 안 들어가서"로 설명하면 틀린다. **무해한 진짜 이유는 그 바이너리가 `dev: true`라 프로덕션 설치(`npm ci --omit=dev`)에 들어가지 않고, 따라서 제3자에게 전달(배포)되지 않기 때문이다.**

   반면 **우리가 만들어 내보내는 CSS 출력물**은 lightningcss의 소스도, 그 Executable Form도, 그 수정본도 아니다. 이 결론은 그대로 유지된다.
   > ❓ 확인 필요 — 이 논리는 일반적으로 통용되는 해석이지만, lightningcss가 **자신의 코드 조각(런타임 폴리필 등)을 출력 CSS에 삽입**하는 기능을 쓰면 달라질 수 있다. 현재 우리는 Tailwind 기본 설정만 쓰고 lightningcss를 직접 구성하지 않으므로 그 경로에 해당하지 않는 것으로 판단한다. 실제 출력 CSS를 대조 검증하지는 않았다.

2. **설령 배포 대상이 되더라도 §3.3에 의해 우리 소스는 공개 의무가 없다.** MPL은 상용·사유 소프트웨어와 결합 가능하도록 설계된 라이선스다.

**❗ 이 판정이 뒤집히는 조건:**

| 조건 | 대응 |
|---|---|
| lightningcss를 **포크·패치**해서 쓰기 시작 | §3.1 — 수정본(Modifications)도 MPL 조건으로 배포해야 함. 더불어 §3.4에 따라 원 고지를 지우면 안 됨 |
| lightningcss를 **직접 dependency로 올려** 런타임에 사용 | §3.1·3.2 — 배포 형태에 따라 소스 고지 필요 |
| Docker 이미지에 `node_modules`를 **dev 포함해서** 담아 전달 | Covered Software를 convey → §3.2 고지 필요 (프로덕션 빌드는 `--omit=dev`로 회피) |

> **권장:** 배포 시 `npm ci --omit=dev`를 표준으로 못박는다. 그러면 MPL 2건이 배포물에서 **구조적으로 사라진다.** → 13절 정책.

## 6. 자체 검증 — GPL/AGPL 0건은 어떻게 확인했나

"강한 카피레프트 0건"은 이 보고서에서 가장 중요한 주장이므로 확인 방법을 남긴다.

| 검증 | 방법 | 결과 |
|---|---|---|
| 1 | `_라이선스_원자료.json`의 `licenseCounts` 키 8종 전수 확인 | `GPL`·`AGPL` 문자열을 포함하는 키 **0개** |
| 2 | `packages[]` 45건의 `license` 필드 전수 확인 | 동일 — `LGPL`은 `@img/sharp-win32-x64` 1건에만 **`AND` 결합으로** 등장 |
| 3 | `package-lock.json`(선언 기준 100개 항목) 전수에서 `license` 필드 조회 | `@img/sharp-libvips-*` 계열 **10종**이 `LGPL-3.0-or-later` **단독 선언** — 전부 `optional: true`, `dev: false`이며 현재 PC 미설치. 여기에 **`AND` 결합으로 LGPL을 포함한 4종**(`@img/sharp-win32-x64`(설치본), `@img/sharp-win32-arm64`, `@img/sharp-win32-ia32`, `@img/sharp-wasm32`)이 더 있어 **LGPL 문자열 포함 항목은 총 14개**다 |
| 4 | 주의 4건의 `node_modules/<pkg>/LICENSE` 원문 직접 열람 | 선언 필드와 실제 텍스트 일치 확인 |

**검증 3의 재현 명령** (제3자가 숫자를 그대로 확인할 수 있게 남긴다):

```bash
# LGPL-3.0-or-later 단독 선언 → 10
node -e "const p=require('./package-lock.json').packages; console.log(Object.entries(p).filter(([,v])=>v.license==='LGPL-3.0-or-later').length)"

# license 문자열에 LGPL을 포함하는 항목 전체 → 14 (설치본 @img/sharp-win32-x64 제외 시 13)
node -e "const p=require('./package-lock.json').packages; Object.entries(p).filter(([,v])=>String(v.license||'').includes('LGPL')).forEach(([k,v])=>console.log(k,'|',v.license))"
```

> **경고 (검증 3의 함의):** `package-lock.json`에는 `@img/sharp-libvips-linux-x64`, `@img/sharp-libvips-linuxmusl-x64` 등 **LGPL-3.0-or-later로 선언된 항목이 10개** 더 있다(순수 LGPL 단독 선언 기준. LGPL 문자열을 포함하는 항목까지 세면 설치본 `@img/sharp-win32-x64`를 제외하고 **13개**). 지금은 Windows x64 PC라 설치되지 않았을 뿐이다. **Linux 서버(Vercel·Docker)에 배포하면 이들이 설치된다.** 라이선스 계열은 동일(LGPL)하고 판정 논리도 동일하지만, **감사 대상 목록 45개는 그때 달라진다.** → 14-2절 재감사 사유 1번.
>
> **Linux만의 문제가 아니다.** `@img/sharp-win32-arm64`·`@img/sharp-win32-ia32`도 `Apache-2.0 AND LGPL-3.0-or-later` 결합 선언이고, `@img/sharp-wasm32`는 `Apache-2.0 AND LGPL-3.0-or-later AND MIT`다. 즉 **Windows ARM·32비트 환경이나 WASM 런타임에 배포할 때도 5-1절과 동일한 검토가 필요하다.** 현재 감사가 "Windows x64" 기준이라는 한계가 여기서 드러난다.

## 8. 웹폰트 라이선스

폰트는 코드와 라이선스 체계가 다르고(대개 SIL OFL), **"파일을 재배포하는가"가 판정 기준**이므로 별도로 본다.

### 8-1. 실측 — 프로젝트에 폰트 파일은 0개다

저장소 전체(`node_modules` 제외)에서 `*.woff`, `*.woff2`, `*.ttf`, `*.otf` 검색 결과 **0건**. 즉 **우리가 폰트 바이너리를 재배포하고 있지 않다.** 이것이 8절 전체의 결론을 결정한다.

### 8-2. 두 버전이 폰트를 다르게 다룬다

| | Next 앱 (`src/`) | 단일 파일 버전 (`presentation/`) | **`public/app.html`** |
|---|---|---|---|
| 정체 | React 컴포넌트 렌더링 | 서버 없이 도는 단일 HTML | **단일 파일 버전의 사본. Next가 `/app.html` 경로로 그대로 서빙한다** |
| 지정 방식 | CSS `font-family` 이름만 | Google Fonts CSS API 링크 | **Google Fonts CSS API 링크** |
| 근거 | `src/app/globals.css:3-5` | `presentation/매장수첩.html:11-13`, `presentation/app.html:2-4` | `public/app.html:11-13` |
| 폰트 파일 전송 | **없음** | Google 서버 → 방문자 브라우저 | **Google 서버 → 방문자 브라우저** |
| 라이선스 의무 | **없음** | **우리에겐 없음** (아래) | **우리에겐 없음** (아래) |

> **❗ `public/app.html`을 별도 열로 뺀 이유.** 실측 결과 **`public/app.html`은 `presentation/매장수첩.html`과 바이트 단위로 동일하다**(둘 다 76,749바이트, `diff` 차이 0). `public/`은 Next가 사이트 루트로 그대로 서빙하므로, **Vercel에 배포하면 `/app.html`이 공개 URL이 되고 그 방문자의 IP가 Google 서버로 나간다.** 즉 아래 8-4절의 개인정보 쟁점은 "단일 파일 버전만의 문제"가 아니라 **Next 앱 배포본에도 그대로 해당한다.**

**Next 앱 (React 화면) — 폰트를 로드하지 않는다.**

```css
/* src/app/globals.css:3-5 */
@theme {
  --font-sans: "Pretendard", "Apple SD Gothic Neo", "Malgun Gothic", system-ui,
    sans-serif;
}
```

`src/` 안에는 `@font-face` 선언도, CDN `<link>`도, `next/font` import도 **전부 0건**이다. 즉 **"Pretendard"는 이름으로만 적혀 있고, 사용자 기기에 Pretendard가 설치돼 있지 않으면 그냥 시스템 폰트로 폴백한다.** 폰트 파일을 배포하지 않으므로 **어떤 폰트 라이선스 의무도 발생하지 않는다.**

> ⚠️ **단, "Next 앱 배포본이 폰트를 전혀 불러오지 않는다"는 뜻은 아니다.** 위에서 적었듯 같은 배포본의 `/app.html`(= `public/app.html`)이 Google Fonts를 불러온다. **라이선스 결론은 그대로**(폰트 파일 재배포 아님 → OFL 의무 없음)지만, **개인정보 관점의 범위는 `src/`가 아니라 배포본 전체다.**

- Pretendard 자체는 SIL OFL 1.1이다 — https://github.com/orioncactus/pretendard (저장소 `LICENSE`)
- ⚠️ 실무적 함의: 라이선스 문제가 아니라 **디자인 문제**다. 대부분의 방문자에게 Pretendard는 적용되지 않는다. 셀프호스팅하기로 결정하면 그때 OFL 고지 의무가 생긴다(8-4절).

**단일 파일 버전 — Google Fonts CSS API로 IBM Plex를 로드한다.**

```html
<!-- presentation/매장수첩.html:11-13 -->
<link rel="preconnect" href="https://fonts.googleapis.com">
<link rel="preconnect" href="https://fonts.gstatic.com" crossorigin>
<link rel="stylesheet" href="https://fonts.googleapis.com/css2?family=IBM+Plex+Mono:wght@400;500;600&family=IBM+Plex+Sans+KR:wght@400;500;600;700&display=swap">
```

```css
/* presentation/매장수첩.html:42-43 */
--sans: "IBM Plex Sans KR", system-ui, -apple-system, "Malgun Gothic", sans-serif;
--mono: "IBM Plex Mono", ui-monospace, "Consolas", monospace;
```

**OFL 1.1이 요구하는 것과, 우리에게 발생하는지:**

| OFL 조항 | 의무 | 우리 경우 |
|---|---|---|

| §5 | OFL 폰트의 파생물도 OFL로 | 해당 없음 |

**판정: 웹폰트에서 발생하는 오픈소스 라이선스 의무는 현재 0건이다.**
상업적 이용도 문제없다 — OFL 1.1은 상업 이용을 명시적으로 허용하며, Google Fonts FAQ도 "all the fonts are ... free to use in commercial products"를 밝히고 있다(https://developers.google.com/fonts/faq).

### 8-4. ❗ 라이선스가 아닌 별개의 리스크 — Google Fonts와 개인정보

**이건 라이선스 문제가 아니라 개인정보 문제이므로 여기서는 지적만 하고 `10_개인정보처리방침.md`로 넘긴다.**

Google Fonts를 CDN으로 부르면 **방문자의 IP 주소가 Google 서버로 전송된다.** 유럽에서는 이를 두고 GDPR 위반을 인정한 하급심 판결이 있었다(독일 뮌헨 지방법원, 2022년, Google Fonts 동적 임베딩 사건). 국내법이 곧바로 적용되는 사안은 아니지만, 개인정보처리방침의 "국외 이전" 항목과 충돌할 소지가 있다.

**❗ 인계 시 범위를 축소하지 말 것 — 단일 파일 버전만의 문제가 아니다.**

| 대상 | Google Fonts 로드 | 배포 시 공개 경로 |
|---|---|---|
| Claude Artifact로 게시한 단일 파일 버전 | ✅ 한다 | 게시된 Artifact URL |
| **`public/app.html`** (= 단일 파일 버전과 바이트 동일한 사본) | ✅ 한다 | **Next 앱 배포본의 `/app.html`** |
| Next React 화면 (`src/`) | ❌ 안 한다 | — |

즉 **Vercel 정식 배포를 하면 Next 앱 배포본에서도 `/app.html` 경로를 통해 동일한 IP 국외 전송이 발생한다.** `10_개인정보처리방침.md`에는 이 범위로 인계한다. `public/app.html`을 배포에서 제외하거나 삭제하면 이 경로는 사라진다.

> ❓ 확인 필요 — 위 독일 판결의 사건번호·판결문 출처 URL을 확인하지 못했다. 개인정보 문서에서 인용할 경우 원 출처를 반드시 확인할 것.

**대응 선택지 (라이선스 관점에서의 가능 여부):**

| 방안 | 개인정보 리스크 | 라이선스 영향 |
|---|---|---|
| 현행 유지 (Google CDN) | IP 국외 전송 발생 | 의무 없음 |
| **폰트 셀프호스팅** (`.woff2` 직접 배포) | 외부 전송 제거 | **OFL §2 발동** → 저작권 고지 + OFL 전문 동봉 필요. **OFL이 허용하므로 법적으로는 문제없다** |
| 시스템 폰트만 사용 | 외부 전송 없음 | 의무 없음 |

셀프호스팅은 OFL이 명시적으로 허용하는 사용 방식이므로 **라이선스가 막지 않는다.** 다만 그 순간 고지 의무가 생기므로 11절 고지문에 OFL 절을 추가해야 한다.

## 10. 프로젝트 자체 라이선스 — 현재 없음

### 10-1. 실측

| 확인 항목 | 결과 |
|---|---|
| 저장소 루트 `LICENSE` / `LICENSE.md` / `LICENSE.txt` | **없음** |
| 저장소 루트 `COPYING` | **없음** |
| 저장소 루트 `NOTICE` | **없음** |
| `package.json`의 `license` 필드 | **없음** |
| `package.json`의 `"private"` | `true` |
| `README.md`의 라이선스 절 | **없음** |

```json

  "scripts": { ... },
  "dependencies": { ... },
  "devDependencies": { ... }
}
```

### 10-2. 현재 상태의 법적 의미

**라이선스를 붙이지 않은 저작물은 "자유롭게 쓸 수 있는 것"이 아니라 "모든 권리 유보(all rights reserved)" 상태다.** 저작권은 등록이나 표시 없이 창작과 동시에 발생한다 — 저작권법 제10조 제2항: 저작권은 "저작물을 창작한 때부터 발생하며 어떠한 절차나 형식의 이행을 필요로 하지 아니한다" (국가법령정보센터 https://www.law.go.kr/법령/저작권법).

따라서 **지금 상태에서도 제3자가 이 코드를 가져다 쓸 권리는 없다.** "라이선스가 없으니 위험하다"가 아니라, **의도가 문서화돼 있지 않은 것이 문제**다.

**`"private": true`는 라이선스가 아니다.** npm 레지스트리에 실수로 publish되는 것을 막는 플래그일 뿐이며(https://docs.npmjs.com/cli/v11/configuring-npm/package-json#private), 제3자의 권리 범위에 대해 아무것도 말하지 않는다.

### 10-3. 무엇을 정해야 하는가

| 결정 항목 | 선택지 | 이 프로젝트에 대한 판단 |
|---|---|---|
| **A. 공개 여부** | 사유(proprietary) / 오픈소스 | **사유 권장** — 유료 판매를 전제로 한 제품이고, 45개 의존성 중 이를 막는 라이선스가 없다 |
| **B. 저작권자 표기** | 개인명 / 사업자명 / 법인명 | ❓ 확인 필요 — 사업자 등록 여부에 따라 다름. 정부지원사업 신청 주체와 일치시킬 것 |
| **C. 소스 저장소 공개 여부** | 비공개 / 공개 | ❓ 확인 필요 — 심사 제출 요건 확인 필요 |
| **D. 발표·심사 제출본의 취급** | | 제출은 라이선스 부여가 아니다. 표기로 명확히 할 것 |

**(1) `package.json` 수정** — SPDX 규약상 사유 소프트웨어는 `UNLICENSED`로 표기한다(https://docs.npmjs.com/cli/v11/configuring-npm/package-json#license).

  "version": "0.1.0",

  제3자 저작권 고지를 동봉하고 있습니다. 파일명이 `NOTICE`가 아니므로
  Apache-2.0 §4(d)의 문언상 의무는 발동하지 않으나, 안전을 위해 그 내용을
  여기에 그대로 옮깁니다.
    출처: node_modules/typescript/ThirdPartyNoticeText.txt
```

> **3-1절을 채우는 법** (수작업 32줄을 손으로 옮기지 않는다):
>
> ```bash
> node -e "const fs=require('fs');JSON.parse(fs.readFileSync('docs/deliverables/_라이선스_원자료.json','utf8')).packages.forEach(p=>{const d='node_modules/'+p.name;let f=null;try{f=fs.readdirSync(d).find(x=>/^(LICENSE|LICENCE|COPYING)/i.test(x))}catch(e){};if(!f){console.log(p.name+'\t(라이선스 파일 없음)');return}const line=fs.readFileSync(d+'/'+f,'utf8').split(/\r?\n/).find(l=>/copyright/i.test(l));console.log(p.name+'\t'+(line||'(Copyright 줄 없음)').trim())})"
> ```
>
> 이 명령이 3-1절 표의 세 번째 열을 그대로 만들어 준다. 45건 중 42건에서 Copyright 줄이 나오고, 3건(`@next/env`, `@next/swc-win32-x64-msvc`, `client-only`)은 라이선스 파일이 없다 (실행해서 확인함).
>
> ⚠️ **출력을 그대로 붙여넣지 말 것.** 이 명령은 "copyright"라는 단어가 처음 나오는 줄을 집으므로, **Apache-2.0 패키지에서는 라이선스 본문의 정의 문장이 잡힌다** (예: `@img/sharp-win32-x64` → `"Licensor" shall mean the copyright owner...`). Apache-2.0 4건은 저작권 줄을 눈으로 확인해 따로 적는다. MIT·ISC·BSD는 첫 Copyright 줄이 곧 저작권 고지라 그대로 쓸 수 있다.

**CI에 붙일 검사 (8번 산출물 `08_테스트자동화.md`와 연계):**

```
1. npm ci
2. 의존성 라이선스 추출
3. 금지 목록(GPL-*, AGPL-*, SSPL-*, BUSL-*, 라이선스 미상)에 해당하면 빌드 실패
4. THIRD-PARTY-NOTICES.md 와 실제 목록이 다르면 경고
5. 04_라이선스감사.md 의 "N절" 상호참조를 절 제목 목록과 대조 (부록 A-2)
```

**5번을 넣은 이유:** 이 문서에서 실제로 절 상호참조 오류가 **11건** 나왔다. 12절(생성형 AI)이 뒤에 삽입되면서 그 뒤 절 번호가 하나씩 밀렸는데, 본문의 "→ N절" 안내가 따라가지 못했다. **조치 지시가 대부분 "→ N절" 형태이므로, 이 오류는 곧 개발자가 엉뚱한 절을 읽는다는 뜻이다.** 절을 삽입·이동한 커밋에서는 반드시 대조한다.

## 12. 생성형 AI로 작성한 코드의 저작권 쟁점

**이 프로젝트는 코드 상당 부분이 생성형 AI(Claude)와의 협업으로 작성됐다** (`docs/deliverables/00_진행표.md`: "AI로 *개발*했을 뿐, 제품이 AI를 *쓰지는* 않는다"). 이 사실이 라이선스·저작권에 미치는 영향을 정리한다.

> **⚠️ 이 절은 결론을 내리지 않는다.** 이 영역은 각국에서 판례·행정해석이 형성되는 중이고, 확립된 답이 없다. **쟁점과 실무적 대응만 적는다.** 단정적 서술을 발표 자료에 옮기지 말 것.

### 12-1. 쟁점 1 — AI가 만든 코드에 저작권이 발생하는가

| 근거 | 내용 | 출처 |
|---|---|---|
| 저작권법 제2조 제1호 | 저작물은 "**인간의 사상 또는 감정을 표현한 창작물**"로 정의된다 | https://www.law.go.kr/법령/저작권법 |
| 미국 저작권청 | AI 생성물의 등록에는 **인간 저작자성(human authorship)** 이 필요하며, 인간의 기여가 있는 부분만 보호된다는 입장 | https://www.copyright.gov/ai/ |
| 문화체육관광부·한국저작권위원회 | 「생성형 AI 저작권 안내서」(2023.12) — AI 산출물의 저작물성, 프롬프트 입력만으로는 저작자로 보기 어렵다는 취지의 안내 | ❓ 확인 필요 — 문서명·발간연월은 확인했으나 **직접 다운로드 URL은 확인하지 못했다.** 인용 전 https://www.copyright.or.kr 에서 원문 확인 필요 |

**실무적 의미 (본 프로젝트):**
- **"AI가 짰으니 저작권이 없다"는 결론으로 곧바로 이어지지 않는다.** 요구사항 정의, 아키텍처 결정, 반복적 수정·검수는 인간의 창작적 기여다. 이 프로젝트에는 그 기록이 이례적으로 많이 남아 있다 — `docs/08_DECISION_LOG.md`(의사결정 로그), `CLAUDE.md`("확정된 결정, 그리고 이유"), git 커밋 76개 추적 파일.
- **반대로, 보호 범위가 통상의 저작물보다 좁을 가능성을 배제할 수 없다.**
- **10절의 사유 라이선스 표기가 무의미해지지는 않는다.** 저작권으로 보호되지 않는 부분이 있더라도 계약(이용약관)·영업비밀·접근통제로 보호할 수 있다.

### 12-2. 쟁점 2 — 학습 데이터에서 유래한 코드가 섞여 들어올 가능성

**쟁점:** 생성형 AI가 학습 데이터의 코드를 상당 부분 그대로 재현하면, 그 원본이 GPL 등 카피레프트였을 경우 의무가 딸려올 수 있다는 지적이 있다. 이 문제는 소송으로 다투어지고 있으며 확립된 판단이 없다.

**본 프로젝트의 실제 리스크 평가:**

| 요인 | 상태 | 리스크 |
|---|---|---|
| 코드 규모 | `src/` 33개 파일. 대형 알고리즘 없음 | 낮음 |
| 코드 성격 | Next.js/React 관용구, 폼·리스트·localStorage 처리 | **낮음** — 표현의 선택 폭이 좁아 애초에 저작물성이 약한 영역 |
| 유명 알고리즘·자료구조 이식 | 없음 | 낮음 |
| 코드 유사도 스캔 | **미실시** | ❓ 확인 필요 |

**즉 리스크는 낮게 평가되나, 검증은 하지 않았다.** 낮다고 판단한 근거를 적었을 뿐 스캔으로 확인한 것이 아니다.

### 12-3. 쟁점 3 — AI 제공자의 약관

Claude 등 상용 AI 코딩 도구의 이용약관은 일반적으로 산출물에 대한 권리를 사용자에게 귀속시킨다. 다만 **이는 AI 제공자와의 계약 문제이지 제3자 저작권 문제를 해결하지 않는다.**

> ❓ 확인 필요 — 실제 이용한 도구의 약관 조항을 확인하지 않았다. 상업적 이용·산출물 권리 귀속·면책 범위를 원문에서 확인할 것.

### 12-4. 실무적 대응 — 지금 할 수 있는 것

| # | 대응 | 상태 | 비고 |

> 원문을 읽지 않았다. 그럼에도 "금지"로 분류하는 것은 **라이선스 의미를 단정했기 때문이 아니라,

> 실제로 이들 중 하나를 꼭 써야 하는 상황이 오면, **위 원문 URL을 먼저 읽고** 5절 형식으로 분석한다.

> **금지 라이선스라도 예외가 성립하는 경우가 있다** — 예: GPL 도구를 **별도 프로세스로만 실행**하고 우리 코드와 링크하지 않는 경우. 그러나 **판단이 어렵고 실수의 대가가 크므로, 이 프로젝트에서는 예외를 두지 않는다.** 대체재를 찾는 편이 항상 싸다.

### 13-2. 판단 절차 (패키지 추가 시)

```
[1] 정말 필요한가?
     └ 표준 API·기존 의존성으로 되면 추가하지 않는다.
       (현재 직접 의존성 9개. 이 숫자가 이 프로젝트의 강점이다)
        ↓ 필요하다
[2] 라이선스 확인
     npm view <pkg> license
     npm view <pkg> dependencies        ← 전이 의존성도 함께 들어온다
        ↓
[3] 13-1 분류 대조
     ✅ 허용  →  [5]로
     ⚠️ 주의  →  [4]로
     ❌ 금지  →  중단. 대체재 탐색
        ↓
[4] 5절 형식으로 분석 → 04_라이선스감사.md에 항목 추가
     ① 라이선스가 요구하는 의무
     ② 우리가 어떻게 쓰는가 (수정? 재배포? 링크 방식? dev/런타임?)
     ③ 의무가 발생하는가, 아니면 왜 발생하지 않는가
        ↓
[5] 설치 위치 결정
     빌드에만 쓰나?  →  npm i -D  (devDependencies)
                          카피레프트 노출을 구조적으로 줄인다
     런타임 필요?    →  npm i
        ↓

        ↓
[7] 고지문 갱신 (THIRD-PARTY-NOTICES.md)

- [5] — `-D`로 설치하면 프로덕션 배포에서 제외되어 카피레프트 노출이 구조적으로 줄어든다. 실제로 이 프로젝트의 MPL-2.0 2건이 무해한 이유가 이것이다(5-2절).

## 부록 A. 이 감사의 재현 방법

이 보고서의 수치를 제3자가 재현하려면:

```bash
# 1. 의존성 설치
npm ci

# 2. 설치된 패키지 목록과 라이선스 확인
npm ls --all

# 3. 개별 패키지 라이선스 확인
cat node_modules/<패키지>/package.json   # license 필드
cat node_modules/<패키지>/LICENSE         # 실제 전문

# 4. dev / optional 구분 확인
#    package-lock.json 의 packages 객체에서 각 항목의
#    "dev": true, "optional": true 플래그를 본다

# 5. 카피레프트 검색
#    package-lock.json 에서 GPL / AGPL / LGPL / MPL / CC-BY 문자열 검색
#    (LGPL 개수 재현 명령은 6절 "검증 3의 재현 명령" 참조 — 단독 선언 10 / 문자열 포함 14)
```

**주의: 결과는 실행한 OS·아키텍처에 따라 달라진다.** 이 보고서는 **Windows 11 x64 / Node v24.19.0 / npm 11.17.0** 환경 기준이다.

### 부록 A-2. 이 문서의 절 상호참조 자체 검사

**"→ N절"로 안내해 놓고 엉뚱한 절을 가리키는 오류가 실제로 11건 있었다**(2026-09-04 수정). 절 번호는 절이 삽입·이동할 때마다 어긋나므로, **수정 후 반드시 기계적으로 재검사한다.**

```bash
# (1) 현재 절 번호와 제목을 뽑는다
grep -n "^## " docs/deliverables/04_라이선스감사.md

# (2) 본문의 모든 "N절" 참조를 뽑아 (1)과 대조한다
grep -n "[0-9]\+\(-[0-9]\+\)\?절" docs/deliverables/04_라이선스감사.md
```

> **주의 — (2)는 기계적으로 판정되지 않는다.** "10절"이 맞는지 틀렸는지는 *그 문장이 무엇을 가리키려 했는지*에 달려 있어 사람이 한 줄씩 봐야 한다. 스크립트는 **후보를 빠짐없이 나열하는 역할**만 한다. 절을 새로 삽입하거나 순서를 바꾼 커밋에서는 이 대조를 건너뛰지 말 것.
>
> 참고로 이 문서의 인용 블록 안에는 `## 1. 요약`처럼 **고지문 템플릿의 제목**도 들어 있어 (1)의 결과에 섞인다(11-3절, 5-1절 README 인용). 실제 절은 `## 1.`~`## 16.`과 부록 A·B다.
