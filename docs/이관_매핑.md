# 이관 매핑 — 지금 데이터를 v2 스키마로 어떻게 옮기나

작성 2026-09-11 · 매장수첩

> **이 문서가 하는 일**
> 지금 매장수첩의 데이터는 두 곳에 있다 — 서버의 `data/seed.json`(5덩어리)과
> 태블릿 브라우저의 `localStorage`(11덩어리). Supabase v2 로 가면 **표 37개**로 흩어진다.
> **"이 덩어리의 이 칸이 저 표의 저 칸으로 간다"** 를 미리 적어둔 것이다.
>
> 이게 없으면 연동하는 날 하나씩 헤매게 되고, 그때 빠뜨린 것은 **그대로 사라진다.**

---

## ✅ 갱신 (2026-09-11) — 「나」로 결정. 표 13개를 더했다

아래 §2 가 "갈 곳 없음" 으로 적었던 **9덩어리에 전부 자리가 생겼다.**
스키마는 **표 22 → 37**, 외래키 53 → 85, 정책 23 → 38 이 됐고
실제 PostgreSQL 에서 **동작 40건 · 대조 26건**을 통과한다.

| 갈 곳 없던 것 | 새로 생긴 표 |
|---|---|
| 프렙 | `prep_lists` · `prep_tasks` |
| 주기 점검 | `prep_cycle_state` |
| 체크리스트 · 교육 · 레시피의 만드는 순서 | `positions` · `sections` · `steps` |
| 근무조 | `shifts` · `shift_focus` |
| 직원 · 근무표 | `staff` · `shift_assignments` |
| 출퇴근 | `punches` |
| 근로계약 | `contracts` |
| 설정 | `store_settings` · `cost_excluded_items` |
| (새로) 그날 체크 | `daily_checks` |

**§2 는 그때의 기록으로 그대로 둔다** — 무엇이 왜 빠져 있었는지가 남아 있어야
다음에 같은 실수를 안 한다.

## ⚠️ 2026-09-11 이전의 기록 — 매핑을 만들다가 나온 것

**v2 스키마는 매장수첩의 절반만 받았다.**

| | 덩어리 | v2 에 갈 곳 |
|---|---|---|
| **덮인다** | 거래처 · 품목 · 단가 · 레시피 · 매출 · 발주 | ✅ **8덩어리** |
| **갈 곳 없음** | **프렙 · 체크리스트 · 근무조 · 직원 · 근무표 · 출퇴근 · 근로계약 · 설정 · 주기점검** | ⛔ **9덩어리** |

**왜 이렇게 됐나** — v2 는 심사 의견이 지목한 표 이름(`items`·`suppliers`·`sales_lines`·
`waste_lines`·`stock_counts`·`order_plans`…)을 근거로 만들었다. 그 목록은
**원가·재고·발주 축**이다. 매장수첩의 나머지 축(프렙·교육·근태)은 그 목록에 없었고,
따라서 v2 에도 없다.

**이게 왜 중요한가 — 두 가지다.**

1. **빠진 것 중에 법정 보존 대상이 있다.** 출퇴근과 근로계약은 근로기준법 제42조가
   **3년 보존**을 요구한다. 지금은 태블릿 안에만 있고, v2 에는 받을 표가 없다.
2. **빠진 것 중에 제품의 핵심이 있다.** 프렙은 **매일 아침 반드시 열리는 화면**이고,
   리드타임·`recoverable` 이 이 제품이 종이를 이긴다고 주장하는 근거 그 자체다.
   그게 데이터 설계에 없으면, 설계도가 제품을 설명하지 못한다.

> **심사에 v2 를 "매장수첩의 데이터 설계" 라고 내기 전에 이 사실을 알고 계셔야 합니다.**
> 지금 그대로 내면 "프렙이 핵심이라면서 왜 표가 없나" 를 물었을 때 답이 없습니다.

**두 가지 길이 있습니다 — 사장님이 고르셔야 합니다.**

| | 어떻게 | 장점 | 단점 |
|---|---|---|---|
| **가** | v2 는 **원가·발주 축 설계**라고 범위를 밝히고, 프렙·근태는 **2차 범위**로 명시 | 지금 만든 것을 그대로 쓴다. 정직하다 | 설계도가 제품의 절반만 설명한다 |
| **나** | **표 9개를 더 설계**해서 v2 를 완성시킨다 | 설계도가 제품과 일치한다 | 제가 반나절 더 걸립니다 |

## 1. 덮이는 것 — 그대로 옮길 수 있다

### 1-1. 매장

| 지금 | → v2 | 비고 |
|---|---|---|
| `seed.store.id / name / slug` | `stores.id / name / slug` | 그대로 |
| (없음) | `stores.business_day_start` | **`04:00` 으로 채운다** — 지금은 코드에 박혀 있다(`businessDay.ts`) |
| (없음) | `stores.timezone` | `Asia/Seoul` |

### 1-2. 거래처

| 지금 `sop:vendors.vendors[]` | → `suppliers` |
|---|---|
| `id` | `id` |
| `name` · `phone` · `contact` | 같은 이름 |
| `how` | `order_method` |
| `cutoff` | `cutoff_time` |
| `deliveryDays[]` | `delivery_days` |
| `leadDays` | `lead_days` |
| (없음) | `store_id` ← **매장 하나뿐이므로 전부 같은 값** |

### 1-3. 품목 — ★ 여기가 이관에서 제일 어렵다

| 지금 `sop:vendors.items[]` | → `items` + `item_versions` |
|---|---|
| `id` · `name` | `items.id` · `items.name` |
| `vendorId` | `items.supplier_id` |
| `packUnit` | `items.base_unit` + `items.base_family` ← **계열을 새로 채워야 한다** |
| `packAmount` | `item_versions.per_unit` |
| `packPrice` | `item_versions.unit_cost` |
| (없음) | `item_versions.validity` ← **`[이관일, )` 로 시작** |

> **★ 이관에서 제일 위험한 작업이 이것이다.**
> 지금 레시피의 재료는 **이름 문자열**로 거래처 품목과 이어져 있다
> (`findItemByName`, 앞뒤 공백만 무시). v2 는 **번호**로 잇는다.
>
> 그래서 이관할 때 **이름이 안 맞는 재료가 그대로 드러난다.**
> 지금은 조용히 원가에서 빠지던 것이 (예: "우유" vs "흰우유"),
> 이관 스크립트에서는 **"짝을 못 찾은 재료" 목록**으로 튀어나온다.
>
> **이 목록을 0건으로 만들기 전에는 이관을 끝내면 안 된다.**
> 0건이 아닌 채로 넘기면 원가가 계속 틀린 채로 서버로 옮겨갈 뿐이다.

### 1-4. 레시피 — 두 갈래로 갈라진다

지금은 `Recipe` 하나인데 v2 는 **파는 것**과 **만드는 부재료**를 나눈다.

| 지금 `seed.recipes[]` · `sop:recipes[]` | → v2 |
|---|---|
| `category` 가 음료/베이커리 = **파는 메뉴** | `menus` + `menu_recipe_versions`(version 1) + `menu_recipe_lines` |
| 바 부재료(르방·청·냉침차·밀크티·시럽·크림폼) | `items`(kind=`made`) + `make_recipe_versions` + `make_recipe_lines` |
| `yield.amount` · `yield.unit` | 메뉴 쪽은 안 씀 / 제조 쪽은 `yield_amount` · `yield_unit` |
| `ingredients[].name` | **`items.id` 로 바꿈** ← 1-3 의 그 작업 |
| `ingredients[].amount` · `unit` | `*_recipe_lines.amount` · `unit` + `unit_family` |
| `sections[]`(만드는 순서) | ⛔ **갈 곳 없음** — 아래 §2-7 |
| (없음) | `menu_prices` ← `sop:settings.prices[슬러그]` 에서 가져온다 |
| `settings.excluded` 에 든 재료 | `menu_recipe_lines.excluded_from_cost = true` |

### 1-5. 매출

| 지금 `sop:sales[날짜]` | → `daily_sales` |
|---|---|
| `date` | `business_date` |
| `total` | `total_amount` |
| `count` | `ticket_count` |
| `note` | `memo` |
| `material` (그날 재료비) | ⚠️ **v2 에 대응 칸이 없다.** v2 는 `received_lines` 에서 계산한다 — 이관 시 `memo` 에 남기고 나중에 버린다 |

> ⚠️ **매장수첩은 하루 합계만 받고, v2 는 메뉴별 줄(`sales_lines`)을 받는다.**
> 과거 데이터는 메뉴별로 쪼갤 수 없다. **`daily_sales` 만 채우고 `sales_lines` 는 비운다.**
> 이관 이후 날짜부터 메뉴별로 쌓인다.

### 1-6. 발주

| 지금 | → v2 |
|---|---|
| `sop:orderLinks[프렙항목id]` = 거래처id | `order_plans.supplier_id` |
| `sop:orderLog[날짜][프렙항목id].ordered` | `order_plans`(그 날짜에 한 줄) |
| `…received` | `received_lines`(계획을 가리킴) |
| `…memo` ("우유 12팩") | `order_plans.memo` |

> ⚠️ **지금은 수량이 사람이 읽는 문장(`memo`)이고 v2 는 숫자(`qty`)다.**
> "우유 12팩" 에서 12 를 자동으로 뽑으려 하면 안 된다 — "12팩 정도", "2박스+α" 같은 게 섞인다.
> **과거 발주는 `memo` 만 옮기고 `qty` 는 비운다.** 숫자를 지어내는 것보다 비는 게 낫다.

## 2. 갈 곳이 없는 것 — 표를 새로 만들어야 한다

### 2-1. ⛔ 프렙 (`seed.prepLists` · 목록 3 · 항목 30)

**제품의 핵심인데 v2 에 표가 없다.** 리드타임(`leadTimeHours`)·`recoverable`·
`optionOf`/`optional`·`trigger` 4분기가 전부 갈 곳이 없다.

필요한 표: `prep_lists` · `prep_tasks` (+ `trigger` 를 어떻게 담을지 결정)

### 2-2. ⛔ 체크리스트·교육 모드 (`seed.positions` · 3 · 섹션 9 · 스텝 26)

필요한 표: `positions` · `sections` · `steps`
※ 레시피의 `sections`(만드는 순서)도 같은 표를 쓸 수 있다.

### 2-3. ⛔ 근무조 (`seed.shifts` · 4)

`start`/`end` 와 `focus[]`(어느 화면을 띄울지). 자정을 넘는 마감조 처리 포함.

### 2-4. ⛔ 직원·근무표 (`sop:roster`)

`users` 는 **로그인 계정**이라 직원과 다르다 — 로그인 안 하는 알바가 대부분이다.
필요한 표: `staff` · `shift_assignments`

### 2-5. ⛔ 출퇴근 (`sop:punch`) — **법정 3년 보존**

### 2-6. ⛔ 근로계약 (`sop:contracts`) — **법정 3년 보존**
※ 주민등록번호 칸은 **v2 에도 만들지 않는다**(개인정보보호법 제24조의2).

### 2-7. ⛔ 설정 (`sop:settings`)

최저임금 · 5인 이상 여부 · 목표원가율 · 판매가 · 원가 제외 재료.
이 중 **판매가는 `menu_prices` 로 갈 수 있고**(§1-4), 나머지는 갈 곳이 없다.

### 2-8. ⛔ 주기 점검 (`sop:cycleDone` · `sop:cycleEvery`)

"마지막으로 한 날" 과 "매장이 정한 주기". **절대 안 지우는 기록**이라 잃으면 못 되찾는다.

### 2-9. ⛔ 레시피의 만드는 순서 (`Recipe.sections`)

§2-2 의 `sections`/`steps` 를 같이 쓰면 해결된다.

## 3. 안 옮겨도 되는 것

| 지금 | 왜 안 옮기나 |
|---|---|
| `sop:{슬러그}:{영업일}` · `prep:{슬러그}:{영업일}` | 그날 체크. 영업일 바뀌면 어차피 초기화된다 |
| `sop:run:{슬러그}` | 교육 모드 진도. `sessionStorage` 라 끝나면 사라진다 |
| `sop:ownerPin` · `sop:storePin` | **옮기면 안 된다.** v2 는 서버 인증을 쓴다 |
| `sop:ownerOpen` · `sop:storeOpen` | 잠금 해제 상태. 복원할 이유가 없다 |
| `sop:sid` | 지표용 임의 식별자. **기기마다 달라야 한다** |
| `sop:lastBackup` | 이 기기가 마지막으로 백업한 시각. 기기 고유 |

## 4. 옮기는 순서

> ★ **아래는 「줄을 넣는 순서」다.** 「마이그레이션을 어떤 차례로 올리고 앱의 무엇을
> 같이 고치나」는 [`deliverables/24_DB이관순서.md`](deliverables/24_DB이관순서.md) 에 있다.
> 거기 §1 이 **왜 로그인이 1번인지**를 적어뒀다 — RLS 가 `auth.uid()` 에 기대기 때문이다.

DB 에 넣는 순서는 **가리켜지는 쪽이 먼저**다. 아니면 외래키가 거부한다.

```
1. units                     (스키마에 이미 들어 있음)
2. stores                    ← seed.store
3. users                     ← 로그인 계정을 먼저 만든다
4. suppliers                 ← sop:vendors.vendors
5. items                     ← sop:vendors.items + 바 부재료(kind=made)
   ★ 여기서 "레시피 재료 이름 ↔ 품목 이름" 대조표를 만든다
   ★ 짝 못 찾은 것이 0 이 될 때까지 진행하지 않는다
6. item_versions             ← 지금 단가를 [이관일, ) 로
7. menus + menu_prices       ← seed.recipes(파는 것) + settings.prices
8. menu_recipe_versions/lines
9. make_recipe_versions/lines ← 바 부재료
10. daily_sales              ← sop:sales (sales_lines 는 비움)
11. order_plans / received_lines ← sop:orderLog (qty 비움, memo 만)
12. 나머지는 §2 의 표를 만든 뒤
```
